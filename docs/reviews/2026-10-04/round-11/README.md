## Главное уточнение приоритета

HTTP-BOUNDARY-01 расширяет известную предпосылку MAP-BOUNDARY-03: для сбоя
процесса не нужны аккаунт, кампания или администратор. В отдельном loopback
процессе Node v24.19.0 запрос в login с телом `null` не дал HTTP-статуса и
завершил сервер с кодом 1. Некорректный JSON `{` и массив `[]` в том же маршруте
дают контролируемый 401. Это конкретная проверка формы входа, а не заявление,
что любой неправильный JSON приводит к завершению процесса.

Независимо проверен второй аккаунт с campaign membership `player`: typing с
`null` приводит к тому же исходу, а с `[]` — к контролируемому 403. Общая
граница обработки ошибок нужна до синхронной подготовки dispatch, затем на
всём Promise пути. Она не заменяет валидацию тела и не должна повторно писать
JSON в уже начатый SSE/HTTP-ответ. Эти входы объединены в один кластер общей
очереди, а не суммируются как три независимых архитектурных дефекта.

## Что нельзя расширять за пределы доказательств

- В probe 44 команды исполняются настоящим Rules Engine и FileEventStore,
  но это не новый HTTP/browser сценарий создания героя. Существующий API-тест
  отдельно проверяет серверные броски, покупки, повтор и restart.
- Риск замены каталога в 44 статический: каталог между двумя replay не
  менялся. Будущая замена может затронуть повторную валидацию документа,
  применение события и нормализацию. Одного поля версии benefits недостаточно.
- В probe 45 отсутствующий hero в invite создан внутренним store API.
  Штатный HTTP issuer такую ссылку не выдаёт; операции удаления slot в этом
  scope не найдено. Проба подтверждает порядок записи при несогласованном
  входе, а не возможность игрока создать его обычным маршрутом.
- Выдача мест двум аккаунтам проверена последовательно. Межпроцессная гонка
  и takeover устаревшего auth lock не воспроизводились. Роль lock описана по
  коду с ограничением на общий локальный storage и отсутствие stale takeover.
