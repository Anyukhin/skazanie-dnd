# Клиент торговли: проверки ответа и неизвестного исхода

Срез `cb045a8466f35696ff24abe9020d6f39dee89462`. Проверены `loadMerchant` и
`executeMerchantCommand`, их вызывающая витрина и существующие тесты смены
кампании. Это дополнение к [серверному контракту](37-trade-contract.md),
а не новый вывод о двойной покупке.

## Работающие ограничения

Перед запросом callback требует котировку именно выбранного merchant/actor и
целую неотрицательную `expected_state_version`. Версия берётся из котировки,
а не подменяется более новой версией комнаты. Пока запрос выполняется,
`merchantBusyRef` не даёт отправить второй. При возврате ответа проверяются
epoch и кампания; после ошибки текущий запрос снимает блокировку через
`finally`. Старый запрос не снимает блокировку уже нового посещения
([`useGameSession.ts#L2030-L2104`](https://github.com/Anyukhin/skazanie-dnd/blob/cb045a8466f35696ff24abe9020d6f39dee89462/src/useGameSession.ts#L2030-L2104)).

Витрина дополнительно проверяет merchant, actor, место и версию. Котировка
старше состояния не считается пригодной, а effect запрашивает новую
([`MerchantView.tsx#L328-L348`](https://github.com/Anyukhin/skazanie-dnd/blob/cb045a8466f35696ff24abe9020d6f39dee89462/src/MerchantView.tsx#L328-L348)).
Серверный конфликт версии проходит через существующее `refreshFullRoom`, а не
только через строку ошибки
([`useGameSession.ts#L558-L578`](https://github.com/Anyukhin/skazanie-dnd/blob/cb045a8466f35696ff24abe9020d6f39dee89462/src/useGameSession.ts#L558-L578)).

## Исполнение callback-ов

[Проба](39-merchant-client-probe.mjs) компилирует настоящие тела двух callback-ов
локальным TypeScript, но сценарии ниже исполняют только `executeMerchantCommand`.
`loadMerchant` исполняют отдельно существующие `merchant-session-ui` tests.
`useCallback`, fetch, state writers, merger и обработчик
HTTP-ошибки заменены harness-ом. Нет React rerender, настоящего сервера, SSE
или фактического расхода монет; результат нельзя называть browser/HTTP proof.

| Сценарий | Наблюдение |
| --- | --- |
| Второй вызов при ожидающем первом | Новый fetch не отправляется |
| Сетевое отклонение первого promise | Блокировка снимается, ошибка передаётся writer-у |
| Успешный статус с неразбираемым JSON | Ошибка «Сервер не вернул итоговое состояние сделки»; lock снят |
| Успешный статус с состоянием, но без merchant view | Ошибка «Сервер не вернул обновлённые котировки торговца»; частичное состояние не передано в `applyRemote`, lock снят |
| Полный ответ с состоянием и котировкой | Оба переданы writers, room version обновлена, lock снят |
| Следующий вызов после сетевой ошибки, без новой котировки | Ключ меняется `request-1 → request-2`, обе команды сохраняют ожидаемую версию `1` |

В отличие от проверенного [REC-03 обычного narrate](../round-4/23-queued-room-state.md),
обработка ответа торговли уже находится внутри `try/finally`, поэтому
проверенные неполные ответы не оставляют тот же callback заблокированным.
Однако проверки наличия `authoritative_state` и `merchant_view` ещё не являются
полным runtime decoder-ом всех полей и идентификаторов этих структур.

## Что остаётся вопросом восстановления

`requestId` живёт внутри одного вызова; pending envelope неизвестного исхода,
как у тактической команды, здесь не сохраняется. При этом **один новый ключ
не доказывает вторую покупку**: старая котировка сохраняет старую ожидаемую
версию, а сервер отказывает при её конфликте. После обновления витрины
пользователь работает уже с новым контекстом. Чистая проба не моделирует SSE,
автоматическую перезагрузку витрины и следующий пользовательский выбор.

Callback использует обычный `fetch` без переданного `AbortSignal`; в выбранном
фрагменте нет прикладного timeout. Пока искусственный promise ожидал ответа,
busy оставался активен. Это проверка управления ожиданием, а не воспроизведение
бесконечного зависания конкретного браузера. Смена кампании отдельно сбрасывает
merchant-состояние; сетевой стек также имеет своё поведение.

Для следующего небольшого изменения можно переиспользовать уже имеющиеся
механизмы bounded fetch и pending request, сохранив merchant/actor/quote version
и точное тело. Timeout сам по себе недостаточен: commit мог уже пройти, и
следующий запрос должен восстанавливать прежний key, пока исход не установлен.
Явная новая покупка должна получить новый key и свежую котировку.

Не требуется объединять все callbacks в универсальную машину состояний.
Достаточно общего транспорта и хранения запроса с отдельным merchant decoder
и прежними epoch/version guards. Приёмка будущего изменения должна связать
реальный HTTP commit → обрыв ответа → тот же key → один расход, а также смену
кампании и обновление котировки другим действием. В этом проходе такая новая
сквозная приёмка не выполнялась.
