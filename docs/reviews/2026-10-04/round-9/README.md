## Разные уровни доказательств

Last-unit probe 37 вызывает Rules Engine и настоящий FileEventStore напрямую;
это не HTTP двух пользователей. Существующий `merchant-api` отдельно проверяет
HTTP: гонку одного героя с одинаковым key и разными товарами, поддельную цену,
права, устаревшую котировку, повтор и restart.

Probe 39 исполняет настоящую функцию `executeMerchantCommand`, но заменяет
React/сеть/writers и merger. В нём нет серверного commit и полного rerender.
`loadMerchant` покрыт отдельными имеющимися tests. Следовательно, ни второй
расход после неизвестного исхода, ни бесконечное зависание реального браузера
этими callback-проверками не заявляются.

Отсутствие `item_instance_id` в текущей записи не означает исчезновение всей
истории: `LootContainerCreated` и `LootContainerTaken` сохраняют связь в журнале.
Приватная история не должна автоматически становиться публичными полями
инвентаря. Новые поля требуют согласовать normalizer, catalog whitelist,
projection, input boundaries и лишь при необходимости client types.

## Выбор небольших дальнейших изменений

1. Переиспользовать работающую пару «серверная котировка + ожидаемая версия».
   Если возникнет проблема частых конфликтов из-за несвязанных действий,
   сначала измерить её. Ослабление общей версии до отдельной quote revision
   потребует сохранить проверки цены, остатка, доступа и актуальности лавки.
2. Расширять общий pending request на торговлю с отдельным decoder-ом результата;
   timeout должен различать отказ и неизвестный исход. Сохранённый key не
   должен случайно превращать явную новую покупку в replay старой.
3. Выбрать небольшой пилот истории именованной вещи, если он нужен продукту.
   Не менять все обычные стопки и их вместимость ради гипотетической provenance.
