## Приоритет и границы уверенности

RCV-01/02 — P1 для восстановления после потери файлов, а не удалённая атака
игрока. Проверка сравнивает сохранённую metadata/snapshot с фактически
найденным журналом. Более новый event head после падения до записи metadata
допустим; исчезнувшая ранее подтверждённая голова — другая ситуация и не должна
выглядеть как обычное состояние нулевой версии.

Повреждённый latest snapshot уже приводит к typed отказу. Это работающая
защита; выбор старого seed или восстановление replay должны быть отдельной
maintenance-операцией. Backup restore успешно возвращает исходные байты и
имеет healthy HTTP rehearsal; его domain-аудит и искусственный конфликт путей
в authenticated архиве не следует объявлять поломкой каждого восстановления.

WT-01 подтверждён парой контролей: одинаковый срок обещания остаётся open при
десятиминутном long cast, но разрешается при обычном AdvanceTime тех же десяти
минут. Это не требование, чтобы вся игровая симуляция была ассоциативна при
любом разбиении времени. Courier promises, созданные внутри скачка, и внешний
clock пленных требуют отдельно выбранной семантики.

REC-02/04 остаются гипотезами интеграции. Новый request key не доказывает новый
общий бросок: сервер может отклонить уже закрытое решение. Reduced-модель очереди
также не заменяет реальный mounted hook с effects, epoch и сменой кампании.
Предложения по этим пунктам начинаются с проверки, не с нового coordinator.

## Проверки

Повторно выполнены `client-recovery-probe.mjs`, `replay-recovery-probe.mjs` и
`18-world-time-probe.mjs`. Все завершились с exit 0; проверки фиксируют
архивное поведение среза, а не заменяют regression tests будущих исправлений.

Браузерный сценарий использовал настоящий сервер, production build, обычного
тестового игрока и отдельный fault proxy. В квитанциях два движения и их
повторы имеют версии **2, 2, 4, 4**, на диске — два commit файла. После reload
сохранились и pending-карточка, и исходный ключ. Подробная область проверки и
ограничения — в [отчёте 20](20-browser-recovery.md).

Временные стенды остановлены; каталог последнего lifecycle smoke удалён
самим helper. Никакие рабочие `.env`, `storage/` или backup не использовались.
Синтетические login-данные helper относятся только к создаваемому им стенду.

Финальный `pnpm verify` этого прохода завершился с **exit 0**: 13 бюджетных,
5 662 функциональных и 5 MVP-проверок — всего **5 680 passed, 6 skipped,
0 failed**. Typecheck сервера и production build успешны. Запомненный переход
между этажами в этом запуске занял 12,95 мс медианы при прежнем пороге 20 мс.
Функциональная часть заняла 252,054 с, параллельный MVP — 82,141 с; Vite —
8,56 с. Предупреждение о крупных чанках осталось.

Отдельно прошли syntax checks четырёх `.mjs` прохода, проверка квитанций
браузерных повторов и проверка 68 локальных/377 закреплённых source-ссылок.
Третий проход не добавляет новый постоянный gate на воспроизведение дефектов:
после исправления такие probes должны сменить ожидаемые результаты.
