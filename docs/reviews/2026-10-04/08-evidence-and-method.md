## Что означает «весь проект» в этом аудите

Инвентаризированы все отслеживаемые файлы; затем выполнено ревью по подсистемам
с прослеживанием важных вызовов, событий, проекций и соответствующих тестов.
Это архитектурный и риск-ориентированный аудит всего репозитория, а не
построчная сертификация каждого файла или доказательство отсутствия ошибок.
Конкретные прочитанные области указаны в тематических отчётах.

Порядок работы: первичные интернет-источники похожих проектов → фиксация среза
и требований → независимые проверки подсистем → перепроверка ключевых находок
→ замеры и проверки → сводный план. Внешние проекты сравниваются по отдельным
решениям, а не по популярности или недоказанному общему превосходству.

Работа выполнена в отдельном worktree от `origin/main`. Исходная ветка
`claude/maps-depth`, её коммиты и незавершённые изменения генераторов, рендеринга
и документации в проверяемый срез не включены. Их нельзя считать прошедшими это
ревью; предложения по картам следует сверить с ними перед реализацией.

В PR входят отчёты и свидетельства. Он не меняет механику, схемы событий,
промпты, зависимости, рабочие сохранения или согласованный roadmap.

## Классы утверждений

| Метка | Основание | Как использовать |
| --- | --- | --- |
| Подтверждённый дефект | Прослеженный путь и воспроизведение либо однозначно нарушаемый контракт | Исправить отдельным PR с регрессионной проверкой |
| Ограничение | Осознанный предел реализации, нередко уже документированный | Выбрать расширение по продуктовой ценности |
| Риск конструкции | Наблюдаемый разрыв контракта; вред в реальной эксплуатации ещё не измерен | Сначала закрепить сценарий и критерий |
| Гипотеза оптимизации | В коде есть потенциально дорогой путь | Сначала замерить; размер файла и число вызовов сами по себе не доказывают тормоза |
| Предложение | Возможное улучшение с альтернативами | Не является согласованием реализации |

P1 в отчётах означает работу до расширения затронутого пути, P2 — плановое
улучшение, P3 — отложенный вариант. Это приоритет рекомендаций, а не CVSS или
объявление критической уязвимости. S/M/L — относительный размер отдельного
изменения/серии изменений; сроки не оценивались.

## Воспроизведение привязки броска

```powershell
node docs/reviews/2026-10-04/roll-probes.mjs
```

[Проба](roll-probes.mjs) использует реальные `RollRegistry`,
`GameOrchestrator` и `RulesEngine` с детерминированным DiceService и маленьким
in-memory event-store double. Она не запускает HTTP, не пишет сохранения и
не вызывает LLM. Связь с HTTP-маршрутом проверена отдельно по вызовам в коде
([SEC-01 и SEC-04](03-persistence-and-security.md)). Результат:

```json
{"generic_success":{"total":20,"difficulty":15,"kept":20,"success":true,"player_rolled":true},"precommit_failure":{"orchestratorFailure":"STATE_VERSION_CONFLICT","sameKeyRetry":"allowed","newKeyRetry":"ROLL_ALREADY_USED"}}
```

Первая часть подтверждает применение generic броска без `check_id` к обычной
проверке. Вторая ограничивает серьёзность finding: orphan consume возможен,
но повтор с исходным ключом уже разрешён. Это не доказательство потери
карточки при любом сбое и не сценарий записи registry после event commit.

## Другие повторённые probes и поверхность typecheck

После подготовки отчётов главный проход повторно выполнил все четыре скрипта,
каждый завершился с кодом 0:

```powershell

node docs/reviews/2026-10-04/map-library-probe.mjs

```

- [Архитектурная проба](architecture-probes.mjs) подтверждает несовпадение
  state/metadata в commit-first, принятие неизвестного события, fallback
  неизвестной редакции, отсутствие проверки `entity_refs` и shadowing rule IDs.
  Это низкоуровневые контракты, не доказательство обхода обычного player HTTP.
- [Проба карты](map-library-probe.mjs) возвращает `PROP_OUT_OF_BOUNDS` верхнего
  этажа при `picked: true`. `NO_PARTY_SPAWN` на верхнем этаже также попадает в
  общий аудит, но сам по себе не является дефектом: вход отряда может быть
  только на ground floor. Основание finding — выход prop за границу.
- [Проба projection/trace](projection-trace-probes.mjs) подтверждает принятие
  caller-supplied hash с `pending_after_ack: false` и потерю trace после
  инъецированного отказа сохранения; commit остаётся, повтор идемпотентен.
  Отдельный временный HTTP-эксперимент проверил lifecycle duplicate при
  искусственном same-version drift: следующий GET восстановил проекцию.
  HTTP-эксперимент не упакован в этот probe, а воспроизводимые assertions в
  файле ограничены FileEventStore и GameOrchestrator.

Это архивные воспроизведения поведения проверяемого среза. Они намеренно
проверяют наличие некоторых дефектов и **не должны** становиться бессрочным CI
gate: после исправления ожидается изменение результата и новый regression test
на правильное поведение.

Команда `pnpm exec tsc --noEmit -p tsconfig.server.json --listFilesOnly` и
сопоставление с первой строкой отслеживаемых `.mjs` подтвердили **31 из 36**
opt-in-файлов в программе. Отсутствуют `party-exit-intent.mjs`,
`reveal-transport.mjs`, `routes/map-import-routes.mjs`, `world-ontology.mjs`,
`world-template-catalog.mjs`. Проверялся реальный CLI установленного компилятора,
а не только массив `include`: часть остальных файлов попадает через импорты.

## Изолированная проверка SSE backpressure

В [`server/index.mjs:2405`](../../../server/index.mjs#L2405)
`writeCampaignStream` отмечает `narrationBackpressured` при `write() === false`,
но следующий `room`/`presence` снова вызывает `write()`. Защита в
[`server/narration-stream.mjs:93`](../../../server/narration-stream.mjs#L93)
касается потока текста. Проба исполняет извлечённую функцию исходного среза,
не копию её реализации:

```js
import { readFileSync } from 'node:fs'
const source = readFileSync('server/index.mjs', 'utf8')
const fn = source.match(/function writeCampaignStream\(connection, event, payload\) \{[\s\S]*?\n\}/)?.[0]
if (!fn) throw new Error('Функция не найдена')
const write = new Function(`let campaignStreamSequence = 0; ${fn}; return writeCampaignStream;`)()
let writes = 0
const connection = { closed: false, res: {
  destroyed: false, write() { writes++; return false },
} }
write(connection, 'room', { version: 1, state: {} })
write(connection, 'room', { version: 2, state: {} })
console.log({ writes, backpressured: connection.narrationBackpressured })
```

Запущено через `node --input-type=module` в проверяемом worktree.
Результат: `{ writes: 2, backpressured: true }` без промежуточного `drain`.
Это подтверждение отсутствия остановки записи в данном пути; это **не**
нагрузочный тест, доказательство OOM или измерение доступности production.
Семантика `write(false)` и ожидания `drain` описана в
[официальной документации Node.js](https://nodejs.org/api/stream.html#streamwritablewritechunk-encoding-callback).

Безопасное исправление должно учитывать `connection.mapHash`: нельзя просто
выбрасывать дельты и продолжать считать, что клиент получил их базовую карту.
Самый небольшой вариант — ограничить очередь/время задержки, закрывать слишком
медленное соединение и на reconnect отправлять полную разрешённую проекцию.

## Границы доказательств

Рабочие `.env` и `storage/` не использовались. Проверки работают без реального
ключа LLM; сценарии, которым нужен провайдер, используют локальные заглушки.
Поведение реальной модели, новый браузерный сценарий двух игроков, мобильная
производительность, доступность интерфейса со screen reader, crash при потере
питания и несколько серверных процессов этим аудитом не сертифицированы.
Исторические JSON из `eval/` — свидетельства прошлых запусков, а не сегодняшние
замеры; повторные результаты приводятся отдельно.
