# Стоимость передачи состояния в полном HTTP-ответе

Этот проход отвечает на два вопроса: какие части реально занимают ответ
`POST /api/campaigns/:code/commands`, и какие стадии видны внутри запроса. Это
замер фактического текущего контракта ответа, а не предложение обрезать
авторитетную память.

## Объём и воспроизведение

Проба запускает production `server/index.mjs` в отдельном дочернем процессе.
Хранилище, dotenv-файл и локальный порт временные; ключ модели пустой, LLM не
вызывается. Большая кампания строится тем же способом, что и исходный HTTP
стенд: synthetic world-memory с теми же счётчиками, `LegacyStateImported` через
`FileEventStore`, затем production snapshot projector. Запросы идут
последовательно, по три для маленькой и расширенной кампании.

Срез ревью зафиксирован на baseline `e1d927f5aa68dc9eca912b527cccf3974ba3e9e7`.

```powershell
node docs/reviews/2026-10-04/round-2/state-transfer-cost-probe.mjs `
  --output=docs/reviews/2026-10-04/round-2/state-transfer-cost.json
```

Сырые измерения находятся в
[`state-transfer-cost.json`](state-transfer-cost.json), а probe-only предзагрузчик —
в [`state-transfer-preload.mjs`](state-transfer-preload.mjs). В отчёт не
попадают cookies, пароли, HTTP-заголовки или логи.

Фикстура содержит 600 entities, 2 501 facts, 2 501 relationships, 400 quests,
600 threads, 2 501 epistemic claims, 1 200 summaries и 6 001 knowledge-ledger
entries. После расширения состояние кампании занимает 8 623 855 байт.

## Что действительно передаётся

Для трёх расширенных ответов размер составил 6 165 403–6 166 219 байт,
p50 — 6 165 811 байт. Клиентское время от вызова `fetch` до полного
`response.text()` составило 2 751,615–2 817,217 мс, p50 — 2 765,704 мс.
Это максимум малой выборки, а не production SLO. Отдельное серверное время от
события `request` до `ServerResponse.finish` приведено ниже; это другая граница
измерения и его нельзя смешивать с клиентским временем.

В первом ответе расширенной кампании разбор UTF-8 байт такой:

| Поле верхнего уровня | Значение, байт | Доля полного ответа |
| --- | ---: | ---: |
| `authoritative_state` | 6 162 448 | 99,952% |
| `mechanics` | 1 349 | 0,022% |
| `visible_state_changes` | 742 | 0,012% |
| `verification` | 142 | 0,002% |
| прочие поля envelope вместе | 722 | 0,012% |
| полный JSON-ответ | 6 165 403 | 100% |

`authoritative_state` — главный источник объёма. Внутри него:

| Поле | Значение, байт |
| --- | ---: |
| `worldMemory` | 6 100 155 |
| `players` | 20 601 |
| `social` | 20 278 |
| `courier_letters` | 10 843 |
| `worldMap` | 4 790 |
| `mechanics` | 1 306 |
| все остальные поля состояния вместе | 4 475 |

Итого `worldMemory` занимает 98,94% полного ответа и 98,99% значения
`authoritative_state`. При этом это не доказательство утечки закрытой памяти:
в синтетической фикстуре герой `hero-1` имеет записи знания по всем 2 501
фактам, поэтому проекция игрока закономерно сохраняет весь набор фактов и
связанных сущностей.

Внутри этой публичной памяти обнаружено точное повторение двух массивов:

| Поля | Каждый массив, байт | Две копии, байт | Избыточно сверх одной копии |
| --- | ---: | ---: | ---: |
| `worldMemory.knowledge_revealed` и `worldMemory.knowledge_ledger` | 1 783 871 | 3 567 742 | 1 783 871 |

Это около 58,5% `worldMemory` и 57,9% полного ответа. Это byte-identical
повторение после `worldMemoryForViewer`, а не предположение по именам полей.
Оба поля сейчас являются частью совместимого публичного shape, поэтому
удалять одно без версии контракта нельзя.

Проверка крупных значений верхнего уровня против полей
`authoritative_state` не нашла других byte-identical повторов. В частности,
верхнеуровневый `mechanics` (1 349 байт) и `authoritative_state.mechanics`
(1 306 байт) — разные формы: первый содержит события ответа, второй — карту
механик состояния. Их нельзя считать дубликатом только по одинаковому имени.

## Стадии запроса

В дочерний HTTP-процесс передан небольшой `--import`-предзагрузчик. Он связывает
каждый запрос через `AsyncLocalStorage` с inclusive-временами production
`FileEventStore.load`, `commit`, `acknowledgeProjection` и с единственным
`JSON.stringify` тела ответа. В расширенных запросах наблюдалось:

| Стадия | Фактический диапазон на 3 запросах |
| --- | ---: |
| серверное время `request` → `finish` | 3 008,669–3 174,294 мс |
| `load`, 7 вызовов | 654,975–965,284 мс |
| `commit`, 1 вызов | 389,381–499,338 мс |
| `acknowledgeProjection`, 1 вызов | 44,255–45,570 мс |
| сумма inclusive persistence-вызовов | 1 171,691–1 423,307 мс |
| residual после этой суммы | 1 750,987–1 860,671 мс |
| сериализация именно HTTP-ответа | 15,591–17,619 мс |
| все `JSON.stringify` внутри запроса | 171,237–263,760 мс, 172–187 вызовов |

`residual` — остаток от серверной границы `request` → `finish`, а не чистое
CPU-время projection: туда
попадают проекция, оркестрация, прочие операции маршрута, планирование и
завершение HTTP. Клиентское `fetch`-время измеряет другую границу и поэтому
не должно использоваться как знаменатель для этой таблицы. Включающие времена
нельзя складывать с низкоуровневыми
вызовами, если добавить их в будущий preloader: вложенные операции тогда будут
посчитаны дважды.

Отдельный same-fixture замер без HTTP и файлов показал `turnResultForViewer`
в 91,428 мс p50 и `JSON.stringify` его результата в 16,376 мс p50. Эти числа
помогают отделить стоимость самой проекции и сериализации, но их нельзя
складывать с любой HTTP-границей и нельзя выдавать за профиль всего маршрута.

## Что делать дальше

1. Убрать повтор `knowledge_revealed`/`knowledge_ledger` из транспорта через
   версионированный public schema. Внутренние aliases в `world-memory.mjs`
   сохранить для replay и старых данных; изменение нужно делать только на
   транспортной границе. На границе v1 продолжать выдавать оба поля, а для v2
   выбрать одно и зафиксировать совместимость в клиентских типах и тестах.
   Потенциальная экономия на этой фикстуре — около 1,78 МБ на каждый ответ.

2. Ввести режим ответа `snapshot + event cursor` для уже синхронизированного
   клиента. Полный `authoritative_state` нужен на initial load/reconnect, а
   обычная команда может возвращать `state_version`, `projection_revision`,
   новые механические события и точечные изменения. Граница должна зависеть
   от подтверждённой версии и видимости событий: нельзя решать «отдавать ли
   память» по типу `MoveActor`, потому что перемещение способно раскрыть факт,
   запустить мировые последствия или изменить разрешённую проекцию.

3. Для `worldMemory` рассмотреть cursor/page endpoint, keyed by viewer,
   `state_version` и knowledge revision. При смене knowledge revision сервер
   обязан вернуть новый видимый набор; при обычном ходе без изменения ревизии
   клиент получает только cursor/ack. Это сохраняет права просмотра и не
   превращает сокращение ответа в молчаливую потерю истории.

4. Сократить повторные загрузки в одном command request: семь `load` вызовов
   на большой фикстуре — отдельный серверный рычаг. Нужен request-local
   memoization с проверкой последнего commit id/version и явной отменой при
   derived commit или гонке. Кэш нельзя подменять простым глобальным объектом:
   инварианты replay, state-version conflict и восстановление после другого
   процесса должны остаться прежними.

Каждый из этих шагов требует сохранения текущего полного ответа как
совместимого пути на время миграции и тестов visibility, idempotency, replay,
нового раскрытия памяти и браузерного сценария. Текущий замер подтверждает
стоимость передачи и повтор памяти; он не оправдывает слепое обрезание
состояния по имени команды.

## Ограничения уверенности

Это три последовательных локальных HTTP-запроса на общей Windows-машине с
пустым ключом модели. Полного suite одновременно не было, но машина не была
выделена под benchmark. Значения пригодны для поиска доминирующих компонентов
и проверки воспроизводимости, не для production percentile/SLO. Probe не
меняет `server/`, `storage/` или `data/`; изменены только отчёт и probe-файлы
этого ревью.
