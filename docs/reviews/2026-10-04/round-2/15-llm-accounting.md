Это дополнение к [AI-02 первого прохода](../05-ai-world-and-maps.md):

## COST-01 — известный usage теряется при ошибке содержания

**Тип:** подтверждённый разрыв учёта. **Приоритет:** P1 для достоверности
квоты. **Уверенность:** высокая в кодовом поведении; реальный счёт поставщика
не проверялся.

В [RouterAIClient.complete](https://github.com/Anyukhin/skazanie-dnd/blob/e1d927f5aa68dc9eca912b527cccf3974ba3e9e7/server/llm-client.mjs#L518-L520)
сначала разбирается тело HTTP-ответа, затем вызывается
`normalizeAssistantMessage`, и лишь после этого возвращается `payload.usage`.
Если JSON-содержание неверно, нормализатор бросает `LLM_JSON_INVALID` раньше
возврата usage. [MeteredLLMClient](https://github.com/Anyukhin/skazanie-dnd/blob/e1d927f5aa68dc9eca912b527cccf3974ba3e9e7/server/usage-ledger.mjs#L259-L276)
вызывает `ledger.fail`, который освобождает резерв; failed entry не учитывается
в дневной сумме. Смешиваются два вопроса: потрачены ли ресурсы provider и
пригоден ли ответ для игры.

Граница finding узкая: ошибка возникает **до возврата** результата из
RouterAIClient — при разборе JSON-содержания или assistant-message validation.
Если metered-вызов уже вернул ответ, а затем его отклонил нормализатор роли,
usage к этому моменту записан. Основные production-модели используют этот
wrapper, а fallback допускает повтор JSON-ошибки на следующей модели.

Выполненная [проба](usage-boundary-probe.mjs) подменяет только `fetchImpl`:
реальные клиент, парсер и ledger остаются. Три ответа HTTP 200 содержат
`usage.total_tokens=100`, `usage.cost=0.25` и некорректное JSON-содержание.
Все корректно отклоняются, но результат учёта следующий:

| Величина | Результат |
| --- | ---: |
| Вызовы подставного provider | 3 |
| Токены, указанные в трёх ответах | 300 |
| `daily_token_limit` фикстуры | 200 |
| `committed_tokens` | 0 |
| `reserved_tokens` | 0 |
| `provider_cost` | 0 |
| `failed_requests` | 3 |

Это не измерение реальной стоимости. Доказано, что известный usage из ответа
теряется и не участвует в следующей проверке квоты. Само отклонение неверного
JSON правильно и должно сохраниться.

Минимальное исправление — отделить фиксацию расхода попытки от валидации
содержания. После разбора provider envelope передавать нормализованный usage
в структурированной `LLMResponseError`; существующий `ledger.fail` может
сохранить известные tokens/cost при статусе `rejected` или `failed`, а
quota/report — учитывать их. Альтернатива — callback расхода до нормализации.
Второй ledger и новый orchestration framework не нужны.

Timeout без полученного usage — другая ситуация: расход неизвестен. Нельзя
автоматически присвоить ему точную стоимость или обещать нулевую. Conservative
reservation, состояние `unknown` и последующая сверка должны быть явной
политикой. [Существующий тест](https://github.com/Anyukhin/skazanie-dnd/blob/e1d927f5aa68dc9eca912b527cccf3974ba3e9e7/test/usage-ledger.test.mjs#L56-L66)
проверяет освобождение failed/expired reservation, а не достаточность этой
политики для всех ошибок.

Критерии будущего PR: успешный ответ учитывается один раз; HTTP 200 с usage и
неверным JSON учитывает расход и сохраняет отказ; ошибка до отправки ничего
не списывает; timeout получает явно определённое состояние; fallback не
теряет usage отдельных попыток. Проверки работают только с local/fake provider.

## COST-02 — повтор ID повторяет provider, но не учёт

**Тип:** подтверждённый риск интеграции интерфейса. **Приоритет:** P2 перед
добавлением устойчивых usage IDs. Текущий production caller с явно
повторяемым `usageRequestId` не найден.

`reserve` при существующем ID и совпавших параметрах
[возвращает прежнюю запись](https://github.com/Anyukhin/skazanie-dnd/blob/e1d927f5aa68dc9eca912b527cccf3974ba3e9e7/server/usage-ledger.mjs#L144-L164).
Wrapper не проверяет её статус и повторно вызывает provider. `settle` для
`completed` возвращает прежнюю запись. В пробе два успешных вызова с одним ID
дают два ответа по 100 токенов, но ledger показывает одну entry и 100 токенов.
Контроль с двумя различными ID показывает две entry и 200 токенов.

Поиск `usageRequestId` по production `server/` обнаружил только реализацию
обёртки; обычные вызовы получают новый UUID. Поэтому это не заявление о
массовом сегодняшнем недоучёте успешных ответов. Однако предлагать единый turn
ID всем ролям/повторам как готовую идемпотентность было бы ошибкой.

Нужно выбрать семантику: ID попытки provider уникален, а turn ID — correlation;
либо ID обозначает операцию, для которой completed результат возвращается без
нового provider call. Первый вариант проще и достаточен для учёта. Второй
требует хранения результата и политики неопределённого исхода, а при разных
моделях ещё и отдельных attempt IDs. Повтор ID reservation не означает
внешний exactly-once.

Критерий: calls, attempt records и settled usage согласованы при
последовательном и одновременном повторе; один turn не склеивает разные
оплачиваемые вызовы. Ошибка одной попытки не освобождает резерв другой.
Хранение raw prompts/ответов для простой корреляции не требуется.
