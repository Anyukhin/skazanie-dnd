## Какие выводы требуют осторожности

VOICE-01 подтверждён исполнением настоящего скомпилированного клиентского
модуля с подставными ресурсами. В заданном сценарии `track.stop` не вызывается.
Это не реальная браузерная запись, не измерение вероятности ошибки устройства
и не доказательство отправки аудио после отказа.

AP-01 — статический ресурсный риск: лимит декодированного изображения не
ограничивает весь JSON envelope до его разбора. Огромный ответ и OOM не
воспроизводились. Пробы 46/47 используют короткие синтетические RIFF/WEBP
байты: принятие сервисом не означает валидность декодирования изображения.

Оба `prepare` намеренно означают новую генерацию. Две параллельные прямые
операции не доказывают второй расход по одному клиентскому намерению:
ни потеря HTTP-ответа, ни повтор key, ни реальный provider bill не моделировались.
Наблюдение 46 и AP-03 — один вопрос будущего контракта, а не две независимые
находки. Аналогично cap по числу запрошенных позиций — действующая политика,
а не автоматически ошибка из-за пропуска уже готовых файлов.

Для нового формата изображения можно будет использовать небольшой descriptor
у существующего генератора/кеша/serving. Пока второй формат не нужен, отдельный
рефакторинг этого пути не обоснован. GET инвентаря и итоговый per-item report
уже помогают восстановить текущую готовность; новая очередь фоновых задач
не требуется только из-за отсутствия live progress.
