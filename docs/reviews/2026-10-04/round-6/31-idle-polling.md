# UI-02: фактический polling при открытом SSE

Срез `88c620e6011ae607913efb224cb8f850b4ee5028`. Проверена настоящая игровая
страница production build в Codex In-app Browser, один обычный тестовый игрок,
карта 16×16. Сервер использовал временные данные, отдельный порт и пустой LLM
ключ. Действия игрока во время наблюдения не отправлялись.

**Подтверждён одновременный SSE и регулярный GET состояния.** За 121,443 с
после открытия SSE прошли восемь периодических запросов комнаты с неизменными
версиями. Карта из ответов уже исключалась по `map_hash`; остальное состояние
оставалось. Это уточняет [UI-02 первого прохода](../04-client-and-rendering.md),
но не доказывает, что repair polling можно безопасно удалить.

## Что наблюдалось

| Показатель | Результат |
| --- | --- |
| Состояние документа в начале и конце | `visibilityState: visible` |
| SSE | Один успешный stream, начальный `room`, затем шесть heartbeat/comment chunks |
| Периодические GET после открытия SSE | 8, все HTTP 200 |
| Промежутки между GET | 14 984–15 002 мс |
| Версии в каждом ответе | `room.version: 1`, `state.state_version: 0` |
| Тело одного периодического ответа | 37 549 байт |
| Суммарные тела этих восьми ответов | 300 392 байта |
| Карта | `map_unchanged: true`, поле `scene.map` отсутствует |
| Остальное состояние | Поле `state` присутствует во всех восьми ответах |
| Страница после наблюдения | Та же «Тихая площадь», поле действия доступно |

Два начальных GET до открытия SSE в эти восемь не входят: первый принёс карту
(38 111 байт), второй уже отправил `map_hash` и получил `map_unchanged`
(37 537 байт). Затем открылась SSE-подписка и presence изменился. Поэтому
нельзя считать все начальные и последующие ответы одинаковыми байт-в-байт.
Записаны размеры и версии, а не digest содержимого.

Байты посчитаны внешним loopback proxy по телам room-ответов. Заголовки,
HTTP framing, загрузка JS/CSS, прочие API-запросы и трафик SSE в сумму
300 392 не входят. Наблюдавшиеся 13–17 мс до завершения периодического ответа
включают proxy и инструментирование; это не профиль CPU сервера.

Сохранены [сырой журнал метаданных](31-idle-browser-requests.json) и
[сводка наблюдений](31-idle-browser-observations.json). Они не содержат
cookie, тел ответа или содержимого мира. Вкладка закрыта после чтения DOM;
процессы стенда завершены и его временное хранилище удалено.

## Почему карта уже экономится, а состояние продолжает приходить

`useGameSession` открывает EventSource отдельно от эффекта `setInterval(sync,
15_000)`. Polling не проверяет, что SSE открыт; полученный JSON читается, но
room snapshot применяется только при более высокой версии:
[`useGameSession.ts#L729`](https://github.com/Anyukhin/skazanie-dnd/blob/88c620e6011ae607913efb224cb8f850b4ee5028/src/useGameSession.ts#L729),
[`useGameSession.ts#L762-L792`](https://github.com/Anyukhin/skazanie-dnd/blob/88c620e6011ae607913efb224cb8f850b4ee5028/src/useGameSession.ts#L762-L792).

Серверная `compactSceneFor` умеет исключать неизменную карту, а
`compactStateForTransport` сохраняет остальные поля состояния:
[`reveal-transport.mjs#L132-L157`](https://github.com/Anyukhin/skazanie-dnd/blob/88c620e6011ae607913efb224cb8f850b4ee5028/server/reveal-transport.mjs#L132-L157).
Следовательно, предложение «добавить map hash/delta» дублировало бы уже
работающий механизм. Измеренная следующая граница — объём ответа комнаты и
частота repair-запросов.

## Варианты небольшого улучшения

1. Сначала отдельно считать periodic repair, reconnect и explicit refresh,
   включая байты и длительность. Не смешивать их с обновлениями от действий.
2. Сравнить условный ответ для неизменного **viewer-specific** состояния с
   более редким repair при здоровом SSE. Одного `state_version` недостаточно:
   права доступа и presence могут меняться отдельно от игровых событий.
3. Сохранить обязательное полное восстановление при пропущенном/неизвестном
   hash, reconnect и смене кампании. Один флаг «TCP открыт» не доказывает,
   что клиент получает правильную проекцию или что сессия ещё действительна:
   см. [LIVE-01/02](../round-2/11-live-access.md).

Выбор между условным ответом и изменением частоты должен следовать замеру
реальной большой кампании. Здесь 300 КБ за две минуты на маленькой фикстуре
не доказывают production bottleneck. Переносить размер expanded response из
[отчёта 14](../round-2/14-state-transfer-cost.md) на каждую idle-вкладку без
такой проверки нельзя. Серверный repair также может намеренно закрывать
пропуски push; его удаление требует сценариев потери/восстановления связи.

## Воспроизведение и пределы

После `pnpm build` запустить существующий helper:

```powershell
node docs/reviews/2026-10-04/round-3/browser-smoke-server.mjs --observations=docs/reviews/2026-10-04/round-6/idle-observations.local.json
```

Он печатает URL и синтетические данные входа. Войти, выбрать готовую кампанию,
не отправлять действий около двух минут, затем закрыть вкладку и создать
файл по напечатанному пути `stop`. Флаг `--observations` добавляет только
метаданные room/SSE; каталог назначения должен существовать. Этот helper —
стенд аудита, а не дополнительный runtime endpoint.

Не проверены `visibilityState: hidden`, throttling фоновых вкладок, несколько
игроков, пропуск событий, большие миры и браузерная CPU/GPU-нагрузка. Скрытое
окно самого браузерного инструмента не означает скрытый документ: именно
поэтому в протоколе сохранён фактический `visibilityState`.
