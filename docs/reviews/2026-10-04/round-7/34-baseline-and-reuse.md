## Почему политика реакций — узкая подходящая граница

`heroReactionModesFor` строит один перечень для команды и проекции.
`planReactionByPreference` не решает, хватает ли ресурса, действует ли цель
или какое окно открывать. После его решения движок исполняет обычный
`UseCombatAction`. Ответ не прошёл проверку — окно остаётся для ручного выбора.
Режимы по умолчанию не меняют старое состояние: пустой реестр не сохраняется.

Это ограниченный пример общего подхода из [отчёта 19](../round-3/19-extension-seams.md):
вынести повторяемый выбор, сохранив существующего владельца механики и порядок
событий. Из него не следует необходимость одного универсального callback API
для всех правил. У реакций есть явный текущий набор разрешённых вариантов;
у свободного творческого действия такого набора может ещё не быть.

Проверены положительные и отрицательные контроли: `ask` ждёт игрока, `auto`
оплачивает ячейку и реакцию, `never` отказывается; неподдержанный ответ оставляет
вопрос открытым. HTTP-проверка использует приглашение и обычного игрока:
чужой герой получает 403, неподходящая реакция — 400, same-key возвращает replay,
после restart режим сохранён. Чужая настройка не уезжает в проекцию
([API test](https://github.com/Anyukhin/skazanie-dnd/blob/cb045a8466f35696ff24abe9020d6f39dee89462/test/reaction-preferences-api.test.mjs#L66-L120)).
Это не доказательство произвольных цепочек контрзаклинаний или всех сочетаний
нескольких одновременно предлагаемых реакций.

## Остаточные границы

- Реакции ограничены цепочкой из восьми автоматических ответов и сохраняют
  ручной путь при отказе. Это защитный предел реализации, не новое игровое
  правило. Перед расширением списка нужны сценарии цепочки и replay.
- Подпись решения всё ещё участвует в повторном разборе назначения:
  `resolvePartyDecision` получает результат `interpretResolvedPartyDecision`.
  Для будущих богатых карточек можно хранить версионированное семантическое
  намерение рядом с подписью, сохранив legacy-разбор старых карточек. Текущая
  правка длинных названий этим аудитом не объявляется неработающей.
- `event-store.mjs`, `backup-service.mjs`, `roll-registry.mjs`,
  `world-memory.mjs`, `llm-client.mjs` и `usage-ledger.mjs` не изменились в этой
  дельте. Это результат сравнения файлов, не повтор всех прежних probes.
  Проекция и входные маршруты изменились, поэтому прежние HTTP/UI-находки
  нельзя считать автоматически перепроверенными только по этому списку.

Новая поверхность JSDoc проверена отдельным `tsc --listFilesOnly`: теперь
**33 из 38** файлов с `// @ts-check` входят в программу. Новый
`reaction-preferences.mjs` включён; прежние пять пропущенных файлов остались.
Это тот же QA-02, не шестой пропуск.

## CI шестого прохода: отдельный отказ боевого стенда

[Запуск 37212546476](https://github.com/Anyukhin/skazanie-dnd/actions/runs/37212546476)
для head `435bba3d` завершился неуспешно: `combat-lab-api.test.mjs:287`
ожидал HTTP 200 от `MakeAttack`, но получил `400 TARGET_OUT_OF_RANGE`.
Метаданные отказа сохранены в [краткой квитанции](34-ci-observation.json).
Бюджетный этап прошёл 13/13; функциональный — 5 696 passed, 1 failed,
6 skipped. Typecheck и build в этом CI были пропущены после отказа.

Существенная деталь checkout: CI исполнял virtual merge
`4856eccd9f2cd8e2f6569691437904a472f2c876` — объединение `435bba3d` с
`cb045a84`. Поэтому его нельзя называть повтором локального полного прогона
шестого прохода на `88c620e6`. Прикладной код текущего checkout соответствует
проверенному CI-коду. Однократный точечный запуск
`node --test test/combat-lab-api.test.mjs` здесь дал **1/1 passed**; сам
[CI main на cb045a84](https://github.com/Anyukhin/skazanie-dnd/actions/runs/37212047520)
тоже успешен. Ни один из этих результатов не означает, что причина отказа
исправлена.

Тест использует состояние предыдущего ответа и без нового расчёта дальности
отправляет атаку по первой живой цели
([цикл](https://github.com/Anyukhin/skazanie-dnd/blob/cb045a8466f35696ff24abe9020d6f39dee89462/test/combat-lab-api.test.mjs#L256-L287)).
Есть возможное окно конкуренции между `onRoomSaved`/coordinator и продолжением
боя внутри HTTP-маршрута. Однако лог отказа не показывает, изменились ли
координаты именно из-за него. Сами случайные грани кубика такой причинности
не доказывают; точечный прогон падение не воспроизвёл.

Следующая диагностическая правка теста — сохранять на отказе ограниченную
квитанцию: фазу, request/state version, actor/target, их позиции, выбранную
команду и события после последнего ответа. Затем воспроизвести конкретное
расписание продолжения боя. Один дополнительный GET перед атакой не устраняет
гонку между чтением и командой: нужен проверяемый контракт версии/конфликта и
выбор допустимого действия. Удалять проверку дальности или принимать любой
400 как успех нельзя. В этом отчётном PR ни тест, ни runtime не исправлялись.
