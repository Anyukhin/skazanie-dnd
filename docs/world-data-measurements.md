# Измерения сохранности мира и поиска

Проверочный harness: [eval/world-data-measurements.mjs](../eval/world-data-measurements.mjs). Он работает только с временным каталогом, не читает и не изменяет `storage/` и не вызывает LLM. По умолчанию `node --expose-gc eval/world-data-measurements.mjs --all` запускает production storage-срез и независимый retrieval-срез:

- production storage: initial state с 600 сущностями, 2501 фактом, 2501 связью, 400 заданиями, 600 сюжетными нитями, 2501 belief/rumor, 1200 summaries и 6001 записями knowledge ledger, затем 10 обычных world-memory tail events через `applyGameEvent + normalizeCampaignState`;
- fixed RU corpus `world-data-ru-v1`: rules отдельно через `RuleRetriever`, memory отдельно через `retrieveWorldMemory` после `worldMemoryForViewer`.

Числа превышают прежние пределы (500 / 2000 / 300 / 500 / 2000 / 1000 / 5000).
Основной прогон начинает с уже наполненного состояния и измеряет запись ещё
10 событий. Поэтапное пересечение границ доступно в дополнительном синтетическом
прогоне; его результаты не подменяют измерение штатного reducer.

Storage-срез измеряет JSON-размер состояния, event log, snapshots и metadata, задержки initialize/commit/load/normalize/full replay/snapshot replay, память процесса (`rss`, `heapUsed`, `external`), а также байты player/admin projection и ограниченных контекстов Worldkeeper, NPC, Director и Narrator. `replay_identical`, `snapshot_replay_identical` и `retention.passed` — обязательные проверки отчёта. Флаг `--synthetic-storage` добавляет отдельный microbenchmark append-only persistence для всех 16 k событий; его commit latency нельзя подменять production latency.

Поиск фиксирует recall@5, top-1, число нерелевантных и устаревших записей, privacy violations, no-answer и задержку. Изоляция кампаний запускается двумя отдельными memory inputs; результат другой кампании считается утечкой.

## Обученные embeddings

Кандидат измеряется только при явном флаге `--trained`. Harness использует уже доступный `fetch`, без новой зависимости, и OpenAI-совместимый endpoint RouterAI: `baai/bge-m3`, `POST https://routerai.ru/api/v1/embeddings`, `encoding_format: float`. Официальная страница модели указывает 1024-мерные векторы и оплату по входным токенам: [RouterAI bge-m3](https://routerai.ru/models/baai/bge-m3).

Индексы корпуса векторизуются один раз на домен и viewer, затем кэшируются; запросы векторизуются отдельно. Отчёт сохраняет только числовой `usage`, если его вернул провайдер. Ключ никогда не попадает в отчёт. Порог no-answer кандидата задаётся `--trained-threshold` в API harness (по умолчанию `0.35`) и должен интерпретироваться как экспериментальный параметр.

Текущий минимум настройки — существующий `ROUTERAI_API_KEY` из `.env`; при необходимости endpoint/model можно переопределить `DND_EMBEDDING_URL`, `DND_EMBEDDING_MODEL`, `DND_EMBEDDING_API_KEY` (см. `.env.example`). Без `--trained` сеть не вызывается.

## Текущий статус

Отчёты сохранены в [eval/world-data-storage-report-2026-09-16.json](../eval/world-data-storage-report-2026-09-16.json) и [eval/world-data-retrieval-report-2026-09-16.json](../eval/world-data-retrieval-report-2026-09-16.json).

Прогон со штатным reducer (`600/2501/2501/400/600/2501/1200/6001` записей,
затем ещё 10 событий) дал следующие результаты:

| Показатель | Результат |
| --- | ---: |
| Полное состояние | 8,60 МБ |
| Суммарный размер двух снимков | 25,25 МБ |
| Проекция для игрока | 6,10 МБ |
| Запись одного пакета из 10 событий | 13,70 с |
| Загрузка / нормализация | 0,84 / 0,32 с |
| Полный replay / replay со снимком | 13,38 / 0,81 с |
| Пиковый RSS процесса по `resourceUsage.maxRSS` | 841 МБ |

Записи сохранены точно (`retention.exact=true`), оба способа replay дают одинаковое
состояние. В игровых контекстах остаётся ограниченная выборка; полный ответ
клиенту пока велик. Ограничение размера контекста модели не решает эту нагрузку.

Стенд: Node v24.19.0, Windows 10.0.26200, x64, 16 логических CPU, 33,35 ГБ RAM.
Это единичный прогон на общей машине разработки. Конкурирующие игровые запросы
не моделировались; значения не являются p95 или оценкой пропускной способности.

Базовый поиск проверен на 23 документах правил и памяти из 9 фактов, одного
слуха и одной записи знания. Всего 13 размеченных запросов. Для запросов с
известным ответом recall@5 и точность первого результата равны 1,0; правильно
вернуть отсутствие ответа не удалось в трёх случаях из трёх. Найден один
устаревший слух, утечек в проверочных случаях нет, изоляция кампаний — 2/2.
Это небольшой искусственный набор, недостаточный для вывода о качестве на
реальных кампаниях. Возврат старого слуха при запросе о нём сам по себе допустим:
его статус опровержения должен оставаться частью контекста.

Обученный `baai/bge-m3` реально проверен через RouterAI: 1024-мерный endpoint вернул 4318 input tokens за 20 запросов. Индексация заняла 6.19 s (3.43 s rules, 1.32/1.43 s memory viewer), query p50 — 0.79 s для rules и 0.60 s для memory. Recall@5/top-1 — 1.0; no-answer — 0/1 rules и 1/2 memory, obsolete rumor — 1, privacy violations — 0, campaign isolation — 2/2 без чужих ID. Векторный кандидат улучшил один memory no-answer случай, но не решил общий порог no-answer; стоимость и качество требуют большего корпуса и калибровки threshold 0.35.

По опубликованной 16 сентября 2026 года цене 1,10 ₽ за миллион входных токенов
стоимость этого набора оценивается в 0,00475 ₽. Это расчёт по тарифу, а не
подтверждение списания из баланса; тестовые запросы вне сохранённого отчёта в эту
сумму не входят. Источник: [тариф RouterAI bge-m3](https://routerai.ru/models/baai/bge-m3).

## Решение по дальнейшему развитию

- Сначала уменьшать стоимость полной нормализации и объём клиентской проекции;
  затем проектировать активную область и архив с точным чтением по ID. Замер
  показал практическое ограничение для большой кампании.
- Embeddings оставлены в экспериментальном инструменте. Текущий небольшой
  корпус не доказывает достаточный выигрыш для включения в игровой путь;
  следующий эксперимент требует более трудных запросов и настройки отказа
  при отсутствии ответа.
- PostgreSQL и отдельная графовая БД не внедряются: этот прогон не проверял
  несколько серверных процессов и не доказывает, что смена БД устранит
  стоимость нормализации и большой HTTP-ответ.
