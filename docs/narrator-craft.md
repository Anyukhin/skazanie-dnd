# Ремесло Рассказчика v4

`narrator/v4` — активный контракт художественного текста. Исторические v1–v3
сохранены рядом как версионированные контракты, но загрузчик и метаданные роли
указывают только на v4.

## Что получает модель

Рассказчик по-прежнему видит только `NarrationBrief`, прошедший проекцию
зрителя. В `story_context` дополнительно приходят:

- до двух последних решений приключения в публичной форме;
- идентификатор, тип и текст двух последних видимых резюме сцен, поэтому
  доступна сцена N-2;
- до четырёх party-видимых разговоров с присутствующими NPC;
- речевой профиль каждого присутствующего NPC: `pace`, `lexicon`,
  `mannerism`;
- класс и предыстория только текущего героя; у соратников остаются имя и id;
- `memory_focus` — вычисленная перед вызовом наиболее тесно связанная запись
  прошлого.

`specific_player`-разговор другого героя не попадает ни в личную, ни в
отрядную память NPC. Присутствие NPC вычисляется по viewer-safe расписанию:
скрытая запись `gm_only` не может выдать тайное местоположение самим фактом
появления имени в `story_context`.

`memory_focus` не создаёт нового знания. Сервер выбирает его только из уже
видимых решений, обещаний, резюме и разговоров. Приоритет:

1. обещание, если его предметы прямо повторяются в цели текущей сцены;
2. прошлая реплика NPC, если она совпадает с текущим фактом или целью;
3. связанное резюме, причём при равенстве выбирается N-2, а не автоматически
   более свежее N-1;
4. связанное решение отряда.

Модель обязана назвать не меньше двух конкретных слов из выбранной записи.
Если она пропускает связь, production-режим делает repair-попытку, а после
неудачи использует детерминированный текст с безопасным напоминанием.

## Проверяемый стиль

Промпт требует:

- один-два предложения для обычного исхода и компактный абзац для перехода;
- конкретную наблюдаемую деталь вместо атмосферной вводной;
- отсутствие чисел броска, СЛ, ОЗ, КД, урона, лечения, цены, расстояния,
  времени и ресурсов;
- отсутствие повторяющихся конструкций начала;
- отсутствие действий и мыслей за героя;
- отсутствие реакций NPC вне `permitted_npc_reactions`.

Промпт не считается защитой сам по себе. Базовый
`DeterministicNarrationVerifier` проверяет подтверждённые события, механику,
предметы, смерть, скрытое знание и `rule_id`. Поверх него bounded lexical
craft-guard отклоняет server-owned набор явных форм: видимые механические
числа; фразы из фактического каталога клише; известные глагольные шаблоны
нового действия героя (`проверяет`, `отпирает`, `закрывает`, `уходит`);
известные реакции и действия NPC
(`кивает`, `отворачивается`, `покидает`) вне allowlist; несовпадение с
разрешённым описанием. Открытое обещание нельзя закрыть распознаваемым
косвенным утверждением состояния вроде «карта лежит под кружкой»: нужен
соответствующий `NpcPromiseResolved`. Guard также требует `memory_focus`.

Каталог клише хранится в `server/narrator-craft-quality.mjs`: он не
подсказывается модели в prompt и применяется после каждого асинхронного ответа
провайдера. Совпадение становится обычным нарушением craft-guard, поэтому
первый ответ уходит в bounded repair-попытку, а повторное нарушение — в
детерминированный fallback. Offline craft-eval импортирует тот же server-owned
каталог и не держит отдельную копию.

Список форм конечный и намеренно не заявлен как полный семантический
классификатор: новая перифраза или глагол вне server-owned словаря может
потребовать отдельного корпуса и правила. Ещё одна проверка сравнивает ответ с
тремя последними текстами той же кампании: Jaccard 3-грамм выше 5% вызывает
обычную repair-попытку. Предыдущие тексты берутся из серверных turn traces и
используются только локально для сравнения — в prompt и модель они не
передаются. При идемпотентном replay сохранённый старый текст проходит текущий
craft-guard заново; прежняя отметка `verification.valid` не считается
доверенной.

Если модель не исправилась, deterministic fallback выбирает из четырёх
равнозначных безопасных формулировок вариант с минимальным пересечением с тем
же окном. Базовый `DeterministicNarrationVerifier` остаётся отдельной границей
для механики, предметов, смерти, скрытого знания и `rule_id`.

## Голоса NPC

`speech_profile` хранится в серверном профиле NPC и переживает event/replay.
Все три поля обязательны при явном обновлении профиля. Старые кампании
совместимы: профиль детерминированно выводится из прежних `voice` и `role`.
Конкретные поля имеют приоритет над общим `voice`.

Социальный контроллер получает профиль как данные и обязан показать
`mannerism` хотя бы один раз. Два NPC в одной сцене сохраняют независимые
профили; это проверяется не общим списком характеров в промпте, а двумя
server-owned объектами.

## Свободный следующий ход

`narrator/v4`, `map_architect/v3` и `campaign_creator/v3` не запрашивают
`suggestions`. Рассказчик завершает подтверждённый исход, но не предлагает
следующий выбор: игрок формулирует действие сам. Старое поле игнорируется при
чтении сохранённого модельного ответа, не попадает в viewer projection и не
переносится клиентом между обновлениями состояния.

## Измерение

`eval/narrator-craft-eval.mjs` делает четыре вызова Рассказчика и два вызова
социального контроллера на синтетических данных, не читая `storage/`. Жёсткий
`--max-calls` ограничивает каскад провайдеров. Сохранённые ответы можно
пересчитать без сети. Режим `--replay` отдельно подаёт сохранённый финальный
production output каждой сцены в текущий `Narrator`, последовательно сохраняя
то же окно из трёх предыдущих результатов. Исходный after смешанный: три
narrator-образца — принятые provider model outputs, четвёртый (`forward-hook`)
— уже `deterministic-fallback`. Production использует две попытки.
Сохранённого нового model repair в исходном отчёте нет, поэтому offline-клиент
возвращает
`OFFLINE_REPLAY_REPAIR_OUTPUT_UNAVAILABLE`, а настоящий production-код
выбирает `deterministic-provider-fallback`. Replay записывает SHA-256 исходного
отчёта и реализации, `network_calls: 0`, `live_calls: 0`, нулевые токены и
отдельно отмечает, что два social-образца скопированы без изменений.

Основные пороги набора:

- среднее попарное пересечение 3-грамм — не выше 5%;
- клише — 0;
- связанная память — не ниже 90%;
- различимые пары голосов — не ниже 80%.

Метрики suggestions сохранены только для сравнения исторических отчётов v3 и
больше не входят в quality gate активного контракта.

Сохранённый live-after показал регрессию 0,67% → 3,73% по четырём финальным
production outputs: три из них дала модель, один уже был deterministic
fallback. Это не чистая метрика модели. Отдельно три provider model samples
дают 6,41%; на тех же трёх сценариях baseline был 0,55%. Исходный отчёт не
переписан.

Offline safety replay на тех же финальных outputs даёт **0,00%**; клише
остаются на нуле, память и голоса — на 100%. Harness повторно
подаёт каждый output как candidate текущему guard. Все четыре
narrator-образца в новом отчёте завершились
`deterministic-provider-fallback` после отклонённого candidate и недоступного
несохранённого repair-output. Поэтому 0,00% измеряет финальный безопасный
текст этой воспроизводимой offline-ветки, а не улучшение model repair или
качества `narrator/v4`. Три подтверждённых успеха и одна неудача исходных
серверных событий сохранены.

Полные числа и сырые образцы находятся в `docs/live-narrator-eval.md` и
`eval/narrator-craft-{baseline,after,production-after}.json`. Исходный
live-after не переписывался: production-after хранит его byte SHA-256
`bc9d03d9fd20fd9fb8152bed316a05f80894ce600d728f6170eab9345dd9efb0` и
canonical-JSON SHA-256
`c52bcdf6e32b23d912e3a21b4867ea0bbb23258bd6cfa9afa210c14c6981002f`.
Потерянные сырые payload и несохранённые repair-ответы провайдера не
реконструируются.
