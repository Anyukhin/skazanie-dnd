# Исполнитель №12 — экземпляры эффектов и снятие

Статус: patch-кандидат, не приёмка. Работа выполнена относительно базового SHA
`c4e570921edea08f8952edef7c437bc5c9182ab3`; координаторские изменения в рабочем
дереве не менялись. В репозитории изменён только этот отчёт. Исполняемые
кандидаты находятся в `%TEMP%/skazanie-agents25/12/`.

## Источник

Прочитана карточка [dnd.su — «Метка охотника»](https://www.dnd.su/spells/164-hunters-mark/).
Для редакции D&D 2014 источник указывает выбор видимого существа в пределах 90
футов, дополнительный `1d6` к попаданию оружием заклинателя и длительность
«концентрация, вплоть до 1 часа». Значит, состояние цели является экземпляром
конкретного наложения и должно исчезать вместе с концентрацией его источника.

## Проверенные зависимости и найденный дефект

- В `server/rules-engine.mjs` ветка `UseCombatAction` для `hunters-mark` уже
  создаёт концентрацию с `effect_id = hunters-mark:<command_id>`.
- Следующее событие `ConditionAdded` записывало на цели
  `hunters-mark:<actor_id>` без `effect_id`. Поэтому `clearConcentrationEffect`
  не мог сопоставить метку с концентрацией: после `EndConcentration` карта
  концентрации очищалась, а условие цели оставалось.
- Имя условия содержит `actor_id`, поэтому два кастера уже могут иметь две
  разные метки. Без идентификатора снятие не является source-specific; после
  исправления два `effect_id` (`hunters-mark:mark-a` и
  `hunters-mark:mark-b`) снимаются независимо.
- `Dispel Magic` сейчас ищет `mechanics.active_effects`; Hunter’s Mark не
  является площадью и отдельного маршрута снятия этим заклинанием нет. Это
  оставлено отдельным долгом: выбранный patch чинит подтверждённое снятие через
  концентрацию и не маскирует отсутствие общего Dispel-контракта.
- Истечение общего срока концентрации для не-площадных заклинаний также не
  имеет единого deadline-маркера в `mechanics.concentration`. Это более широкий
  контракт, требующий изменений события `ConcentrationStarted` и времени; его
  здесь не дублирую. Текущий кандидат ограничен дефектом уже существующего
  `effect_id` источника.
- Повторное наложение той же метки одним кастером удаляет прежнее имя условия и
  создаёт новый `effect_id`; regression проверяет именно независимость двух
  кастеров и снятие только первого.

Воспроизведение на текущем дереве: после двух `UseCombatAction` у цели оба
условия имели `effect_id: null`; `EndConcentration` первого оставлял обе метки.
После добавления поля условие первого кастера удаляется, условие второго остаётся.

## Предложенный patch

Файл `%TEMP%/skazanie-agents25/12/hunters-mark-lifecycle.patch`, SHA-256
`b01fb3ac30115982aeaa93f59e12a37e4b766b67440eb8f50d3e888a17a20132`.
Меняется одна строка в ветке `hunters-mark`: в `ConditionAdded` передаётся тот же
`effect_id`, что и в `ConcentrationStarted`:

```js
effect_id: `hunters-mark:${command.command_id}`
```

Профили данных, Rules Engine в рабочем дереве и UI не разблокировались.

## Regression-тест и проверки

Тест-кандидат `%TEMP%/skazanie-agents25/12/hunters-mark-lifecycle.test.mjs`,
SHA-256 `ee564be5b424ac94cfe8c9dcd73a9fa27e5e80a1d76cd4fa5a59b1b41b18cb1c`.
Он поднимает двух следопытов и одну цель, накладывает одну и ту же метку двумя
кастерами, проверяет уникальные `effect_id`, завершает концентрацию первого и
проверяет, что остаётся только метка второго.

Фактический результат:

- тест в Temp-копии до patch — падает на `effect_id: null`;
- тест в той же Temp-копии после patch — **1/1 pass**;
- `git apply --check hunters-mark-lifecycle.patch` — успешно, hunk применился к
  текущему dirty-дереву с offset 25 строк;
- тот же `git apply --check` на копии файла из базового SHA — успешно;
- общий `pnpm verify` не запускался: координация запрещает общий gate при
  параллельной работе №08.

## Браузерная проверка

Собственный сервер был поднят на свободном порту `8892` с
`DND_STORAGE_DIR=C:\\Users\\anton\\AppData\\Local\\Temp\\skazanie-agents25\\12\\web\\storage`
и пустым ключом LLM. В собственной фоновой вкладке CUA `agent12Tab` открыт
маршрут `http://127.0.0.1:8892/`; после загрузки fresh storage интерфейс показал
«Первоначальная настройка → Создать администратора» и поле кода из
`ADMIN_SETUP_TOKEN`. Это конкретный блокер обычного сценария: без локального
создания администратора и кампании до боевого интерфейса Hunter’s Mark не дойти.
Секрет и пароль не вводились. Кадр состояния был показан inline из CUA
(PNG, 63 729 байт); API CUA не возвращает абсолютный путь файла, а попытка
сохранить его через `data:` URL была отклонена политикой URL браузера. Поэтому
абсолютный путь бинарного кадра отсутствует; маршрут, состояние и AX-дерево
зафиксированы выше. Вкладка и сервер после проверки закрыты.
