# Wave 10 №01 — круговая геометрия

Дата среза: 2026-09-24. Владелец: `geometry_core`.

## Источник и решение

В [D&D 2014 Spellcasting: Areas of Effect](https://www.dndbeyond.com/sources/dnd/basic-rules-2014/spellcasting#AreasofEffect)
сфера задаётся радиусом от исходной точки, а цилиндр имеет круговое основание
с радиусом из описания. [Правила игры на квадратной сетке](https://www.dndbeyond.com/sources/dnd/basic-rules-2014/combat#PlayingOnAGrid)
фиксируют клетку 5 футов. Русская справочная версия [dnd.su: Использование
заклинаний](https://dnd.su/articles/mechanics/157-spellcasting/) использована
как пользовательская сверка терминов и пяти форм областей; она не заменяет
первичный источник. Перевод круговой области на клетки и правило покрытия не
менее половины сверены с [DMG 2014: Areas of Effect](https://www.dndbeyond.com/sources/dmg/running-the-game#AreasofEffect).

Принята отдельная версия `circle-grid-v2`: центр круга лежит на пересечении
сетки, клетка `[x, x+1] × [y, y+1]` входит при покрытии не менее 50%.
Legacy Chebyshev-геометрия в этой задаче не менялась.

## Интерфейс

`server/circular-area-geometry.mjs` экспортирует:

- `CIRCULAR_AREA_GEOMETRY_VERSION: 'circle-grid-v2'`;
- `gridOriginForTargetCell({x, y})`, который возвращает полы координат
  выбранной клетки;
- `circularCellCoverage({x, y}, radiusCells)`, точную площадь пересечения
  круга с относительной клеткой в диапазоне `0..1`;
- `circularCellCovered(cell, radiusCells)`, проверку `coverage >= 0.5`;
- `circularAreaCells({origin, radiusFeet, cellFeet?, bounds?})`, стабильный
  список `{x, y}` в порядке `y`, затем `x`;
- `circularAreaLineOfEffect(origin, targetCell, options)`, где `options` содержит
  `radiusFeet`, необязательный `spreadsAroundCorners` и защитные коллбэки
  `isOpenCell`/`isBlockedEdge`.

Площадь считается аналитически по вертикальным срезам: на точках пересечения
круга с горизонтальными рёбрами клетки срез разбивается, а каждый участок
интегрируется первообразной `sqrt(r² - x²)`. Адаптивное численное
интегрирование и внешние зависимости не используются.

Входы с нечисловым/неположительным радиусом и нечисловым origin дают пустой
результат. Скан
ограничен радиусом 128 клеток (640 футов при стандартной клетке), что покрывает
серверный максимум 600 футов и не позволяет ошибочному вводу создать
неограниченный цикл. Bounds включаются по целым клеткам.

`circularAreaLineOfEffect` проверяет прямой луч точным DDA от origin-
пересечения до центра клетки. В точном проходе через вершину сетки проверяются
обе боковые клетки и все четыре ребра вокруг вершины: два со стороны текущей
клетки и два со стороны диагональной. Для `spreadsAroundCorners` используется
четырёхсвязный BFS только по покрытым `circularCellCovered` клеткам и открытым
рёбрам. Его старт — связная компонента четырёх квадрантов вокруг origin,
достижимая из выбранной SE-клетки. Одно закрытое ребро не объявляется целой
перегородкой, если вокруг его конца остаётся открытый путь; чтобы закрытая
комната действительно не пропускала эффект у origin, должны быть закрыты оба
пути входа. В direct-режиме connected component не используется: SE остаётся
текущей клеткой, NE/SW требуют прямого открытого ребра из SE, а NW проверяет
обе боковые клетки и все четыре ребра начальной вершины.

## Воспроизведение и доказательства

Профильный запуск:

```text
node --test test/circular-area-geometry.test.mjs
21/21 passed
node --check server/circular-area-geometry.mjs
pnpm exec tsc --ignoreConfig --noEmit --skipLibCheck --target ES2022 --module ESNext --moduleResolution Bundler server/circular-area-geometry.d.mts
git diff --check
```

В тесте независимые ручные строки дают 4, 12, 52 и 112 клеток для радиусов
5, 10, 20 и 30 футов соответственно. Дополнительно проверены симметрия по
обеим осям origin-пересечения, точная четверть единичного круга `π/4`,
порог 50%, перенос origin, inclusive bounds, дробный радиус 7.5 футов,
`NaN`/`Infinity` и bounded input.

Замер без нового benchmark framework: полный круг 600 футов (`120` клеток
радиуса) в локальном Node-процессе — `~3.5 ms` на 57 600 просмотренных
клеток; тест требует менее 2 секунд и проверяет, что результат непустой.
Включённый corner-BFS до клетки `(100, 0)` при том же радиусе занял `~11 ms`;
очередь реализована указателем, без `shift()`-деградации.

## Границы интеграции

В исходном candidate-срезе модуль не менял `rules-engine.mjs`, клиентские
адаптеры, старые replay или storage. Root использует
`circularCellCovered(point - origin, radiusFeet / cellFeet)` для точечной
проверки и `circularAreaCells` для полного bounded-растра. Для self-origin
крупных существ выбор нескольких origin остаётся отдельным решением root.

### P1 — прямой луч обходил закрытое ребро у origin (исправлено)

До исправления `directGridRayClear` получал `seedKeys` из
`accessibleOriginSeeds`. Seed-обход стартовал в SE-клетке выбранной точки и
связывал четыре квадранта через открытые рёбра. Поэтому при origin `(10,10)` и
цели `(10,9)` закрытое ребро между этими двумя клетками само по себе не
проверялось: если три других ребра у вершины открыты, северная клетка попадала
в `seedKeys`, и прямой DDA сразу возвращал `true`, не проходя ветку перехода
через ребро.

До фикса чистый модуль воспроизводил симптом:

```text
circularAreaLineOfEffect(
  {x: 10, y: 10}, {x: 10, y: 9},
  {radiusFeet: 30, spreadsAroundCorners: false,
   isOpenCell: () => true,
   isBlockedEdge: (from, to) => edgeIsBetween(from, to, {x: 10, y: 10}, {x: 10, y: 9})}
) === true
```

Тот же случай через серверный путь возвращал `['e']` для `mass-cure-wounds`,
хотя цель стояла за закрытой дверью на ребре origin. Это не vertex-ветка DDA:
она проверяет четыре ребра следующей вершины, а здесь луч начинает движение
через ребро origin. Исправление убрало flood component из direct DDA: SE
остаётся стартовой клеткой, NE/SW требуют прямого открытого ребра из SE, NW
проверяет обе боковые клетки и все четыре ребра начальной вершины. Guard
закрытой выбранной SE-клетки теперь возвращает `false` для обоих режимов.
Connected-component политика сохранена только в
`spreadsAroundCorners:true`, где открытый обход вокруг одного origin-door
является ожидаемым поведением.

После исправления чистый geometry-тест проходит `21/21`. Через серверный путь
на карте с одной закрытой дверью у origin `spellTargetsAt` возвращает `[]` для
`mass-cure-wounds` (`spreadsAroundCorners:false`) и `['e']` для `fireball`
(`spreadsAroundCorners:true`); при полной перегородке оба пути возвращают `[]`.

Остальные проверенные границы не дали находок: старые области без версии
остаются Chebyshev-геометрией после replay, новые события восстанавливают
`circle-grid-v2`, а projection не отдаёт geometry-поля для скрытого
server-generated origin/target.
