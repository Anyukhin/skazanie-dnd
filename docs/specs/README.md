# Спецификации

Спецификация описывает один небольшой законченный результат: какую проблему он
решает, какое поведение требуется, что не входит в работу и как доказать
готовность. Она не предписывает точный diff и не заменяет описание текущей
архитектуры после реализации.

## Когда создавать

Спецификация нужна, если выполняется хотя бы одно условие:

- меняется наблюдаемое поведение игрока или API-контракт;
- работа проходит через несколько подсистем;
- добавляются или меняются игровые правила, события либо сохранённые данные;
- перед реализацией нужно согласовать границы или критерии приёмки;
- результат достаточно важен, чтобы его место было видно в дорожной карте.

Для небольшой локальной ошибки без изменения контракта достаточно задачи,
теста и записи в PR.

## Имена и статусы

Имя файла: `YYYY-MM-DD-short-slug.md`. Дата обозначает создание спецификации, а
смысловой slug не конфликтует между параллельными ветками так часто, как общий
последовательный номер.

Жизненный цикл:

```text
черновик → согласована → в работе → реализована → проверена
                         ↘ отклонена
реализована или проверена → заменена
```

Статус `реализована` означает, что изменение находится в основной ветке, но
часть приёмочных доказательств ещё может отсутствовать. Статус `проверена`
ставится только после выполнения всех применимых критериев и записи результатов
проверки. Если поведение позже существенно меняется, создаётся новая
спецификация, а прежняя получает статус `заменена` и ссылку на преемника.
