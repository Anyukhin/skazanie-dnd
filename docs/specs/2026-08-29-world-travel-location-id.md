## 1. Зачем это нужно

После прояснения переходов на карте конечная точка всё ещё определялась по
отображаемому имени. Одноимённые места было невозможно различить надёжно, а
текстовое название могло разойтись с узлом server-owned карты, который выбрал
игрок. Цель путешествия должна иметь устойчивую идентичность на всём пути от
клиента до события и replay.

Изменение поддерживает общую цель проекта: свобода ухода в выбранное игроками
место должна сохранять причинность мира и не зависеть от неоднозначного текста
или догадки модели.

## 2. Текущее поведение

До изменения клиент передавал отображаемое имя места. Голосование, одиночный
выход и Архитектор сцены работали с текстом, поэтому одинаковые имена создавали
неоднозначность. Сервер не получал устойчивую ссылку, по которой можно было бы
канонически восстановить имя, вид места и сегмент маршрута.

Проблема и исходное состояние зафиксированы в описании PR #67 и в предыдущей
редакции [`../world-map-plan.md`](../world-map-plan.md).

## 3. Желаемое поведение

- Клиент передаёт выбранный узел как URI-кодированный
  `destination_location_id`.
- ID сохраняется в `PartyDecisionOpened` и проходит без потери через
  голосование, одиночный путь и replay.
- Архитектор сцены принимает решение только после сверки ID с server-owned
  `worldMap` и использует канонические имя, вид и маршрут найденного узла.
- Узлы с одинаковыми отображаемыми именами различаются по ID.
- Старые клиенты без ID и повреждённые либо неизвестные ID сохраняют
  совместимый разбор по имени.

## 4. Пользовательский сценарий

1. Игрок выбирает открытую точку на карте мира.
2. Клиент передаёт её `location_id`; при групповом решении сервер сохраняет ID
   вместе с вариантом голосования.
3. После принятия решения сервер повторно находит узел в своей карте и строит
   переход к канонической цели.
4. Игроки видят выбранное место даже при наличии другого места с тем же
   названием; повтор запроса не создаёт второй переход.

## 5. Объём и границы

### Входит

- транспорт `destination_location_id` от UI до серверного решения;
- сохранение ID в событии и восстановление при replay;
- серверная канонизация цели;
- совместимость со старыми клиентами и текстовыми целями;
- проверки конфликтующих имён, повреждённого URI и идемпотентного повтора.

### Не входит

- полная маршрутизация между далёкими регионами;
- открытие скрытых узлов или обход правил видимости карты;
- выполнение нескольких сегментов дальнего маршрута одним переходом;
- изменение общего контракта группового голосования.

## 6. Правила и ограничения

- `location_id` считается недоверенным клиентским полем: сервер обязан найти
  его в собственной карте и не принимает переданные клиентом имя, вид или
  маршрут как авторитетные.
- Доступность узла и сегмента остаётся server-owned решением.
- Дальний маршрут по-прежнему исполняется по одному открытому сегменту.
- Совместимый разбор по имени сохраняется для старых данных, но при корректном
  известном ID именно ID определяет цель.

## 7. Совместимость и данные

`destination_location_id` добавлен как совместимое поле. Сохранённые решения и
старые клиенты без ID продолжают разбираться по имени. Неизвестный или
повреждённый ID не ломает запрос и переводит его в тот же совместимый путь.

ID проходит через событие `PartyDecisionOpened`; replay и повторный HTTP-запрос
проверены отдельными тестами. Миграция сохранённых кампаний не потребовалась.

## 8. Технический план

Ретроспективно реализована следующая цепочка:

1. UI добавляет ID к намерению путешествия.
2. Роутер и разбор выхода сохраняют его в ограниченном контракте.
3. Групповое или одиночное решение переносит поле в событие.
4. Архитектор сцены сверяет значение с картой мира и канонизирует цель.
5. Тесты закрепляют транспорт, replay, идемпотентность и конфликт ID с именем.

Основные владельцы: `src/world-travel.ts`, `server/party-exit-intent.mjs`,
`server/party-decision.mjs`, `server/player-request-router.mjs`,
`server/scene-architect.mjs` и соответствующие тесты.

## 11. Итог реализации

Цель перехода получила устойчивый `location_id` на всём пути от клиентского
выбора до события и Архитектора сцены. Сервер канонизирует сведения о месте по
своей карте, одинаковые имена больше не смешиваются, а старый путь по имени
сохранён для совместимости. Реализация совпала с описанием PR; миграция данных
не понадобилась.

## 12. Открытые вопросы

- Полная маршрутизация между далёкими регионами остаётся отдельной работой.
- Совместимый поиск по имени намеренно остаётся менее строгим и может быть
  удалён только вместе с версионированным отказом от старых клиентов и данных.
