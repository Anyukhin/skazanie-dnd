Документ адресован тому, кто будет это реализовывать. Он содержит **проверенный**
реестр текущего состояния, порядок работ, критерии выхода для каждого шага и
список того, что делать запрещено.

Состояние проверки: ветка `codex/integration-wave-2` = `9e8b2fe`, 2026-07-31 —
это `main` плюс вся вторая волна (PR #9–#32). Ссылки вида `файл:строка`
относятся к этой ревизии.

## Что чинится и зачем

Основа архитектуры правильная: модель не владеет механикой, состояние проходит
через Rules Engine и Event Store. Проблема не в «слабой связи агентов», а в том,
что вокруг одного авторитетного ядра выросло **шестнадцать независимых
писателей** с разными политиками устойчивости.

`AGENTS.md` уже декларирует: «Второго авторитетного пути быть не должно».
Девять прямых `commit` в `server/index.mjs`, минующих Rules Engine, — нарушение
этого инварианта. Работа ниже формулируется не как «улучшение архитектуры», а
как приведение кода в соответствие с собственным контрактом.

Целевая формула:

```
Агент предлагает
→ политика ограничивает
→ Rules Engine рассчитывает
→ Event Store подтверждает (единственный исполнитель, два входа)
→ PostCommit выводит последствия (ключ от event_id или от позиции)
→ Рассказчик описывает
```

## Шаг 0. Зафиксировать текущее поведение

**Один PR. Только тесты. Ноль изменений в `server/`.**

Матрица: 16 писателей × 5 проб. Девять производных группируются по назначению —
решения отряда, часы, жизненный цикл и откат, публичные броски.

Пробы:

1. `STATE_VERSION_CONFLICT`;
2. повтор ключа с тем же содержимым → возврат прежнего коммита;
3. повтор ключа с другим содержимым → `IdempotencyConflictError`;
4. пустой набор событий;
5. восстановление после прерванного продолжения.

**Как индуцировать гонку.** Обёртка над `EventStore`, которая перед первым
`commit` вставляет чужой коммит и тем делает `expected_state_version`
устаревшим. Приватных полей в `event-store.mjs` нет, `Proxy` с привязкой методов
к цели безопасен.

**Где какой харнесс.** Командные писатели — в процессе, по образцу
`test/game-orchestrator.test.mjs` (`FileEventStore` + `RulesEngine` +
`SequenceDiceRng`). Производные — через HTTP, по образцу
`test/narrate-room-version-race.test.mjs`, потому что
`persistAuthoritativeProjection` и маршруты приватны для `index.mjs`.

**Тест фиксирует расхождения как факт, а не как норму.** У каждой ячейки, где
поведение хуже эталонного (строки 2–7 первой таблицы, строка 9 второй), — пометка
«унифицируется на шаге 4/5». Это нужно, чтобы шаг 4 обновлял тест осознанно, а
не «чтобы позеленело».

**Критерий выхода:** 16 писателей описаны, каждая проба даёт зафиксированный
результат, `pnpm verify` зелёный.

## Шаг 1. Закрыть риск проекции комнаты

**Тот же первый PR. Тоже только тест.**

Инвариант:

```
инкрементальная проекция после события
=
полная проекция того же авторитетного состояния
```

`persistAuthoritativeProjection` вручную сливает авторитетное состояние в
«комнату», причём набор обновляемых полей зависит от списков типов событий:
`refreshInventory` перечисляет `Item*`-типы, `characterBuildChanged` — четыре.
Забыли тип в списке — интерфейс молча показывает устаревшие данные. Вторая волна
добавила в эти списки новые типы (`ItemChargesSpent`, `ItemDawnRechargeResolved`,
`MagicItemActivationChanged`, `HitPointDieSpent`), и это ровно тот способ
ошибиться, о котором говорит шаг.

Тест обязан покрыть каждый тип из обоих списков **и** контрольную выборку типов
вне списков: именно вторые дают молчаливое устаревание.

**Важно для оценки риска.** Смягчение уже существует:
`reconcileCampaignProjection` сверяет хэш через `compareProjection` и при
расхождении делает полный пересчёт. То есть инкрементальный путь —
необязательная оптимизация, а не источник истины, и его можно удалить без риска
для корректности.

**Решение принимается по данным, а не по догадке.** Замерить полный пересчёт.
Если он укладывается в бюджет хода — удалить оба списка отдельным PR после
первого, и класс багов исчезает вместе с необходимостью сопровождать allowlist.
Если не укладывается — тест остаётся сторожем навсегда.

## Шаг 3. Общий исполнитель с двумя входами

```js
executor.executeCommands({ campaignId, idempotencyKey, commands, capability, actorIds })
executor.commitDerived({ campaignId, idempotencyKey, events, producerCapability, derivedFrom })
```

`executeCommands` единолично владеет цепочкой: `resolvePlan` → optimistic retry →
проверка повторного ключа → `commit` → reload результата.

Одной сигнатуры недостаточно: девять путей `index.mjs` производят **события**, а
не команды, и пути через `resolvePlan` у них нет. Отсюда второй вход.

**Capability — только неподделываемые символы**, по образцу существующего
`DIRECTOR_COMMAND_CAPABILITY`:

```js
PARTY_DECISION_CAPABILITY
CAMPAIGN_LIFECYCLE_CAPABILITY
PUBLIC_DICE_CAPABILITY
ECONOMY_CLOCK_CAPABILITY
CAMPAIGN_CONTROL_CAPABILITY   // добавлено: откат хода из PR #14
```

Строковое имя производителя недостаточно — JSON-запрос его подделает.

**Инвариант `commitDerived`.** Формулировка «запретить броски» неверна:
`PublicDieRolled` и групповой бросок легитимно приходят из серверного
`DiceService`. Точная формулировка:

> `commitDerived` не может изменить ничего, чем владеет Rules Engine: hp,
> ресурсы, позиции, инвентарь, порядок инициативы, состояния, экономику хода.

Бросок, решающий только исход голосования отряда, не трогает ничего из списка и
потому легитимен. Бросок, влияющий на урон, — нет. Инвариант проверяется тестом
на каждое событие из allowlist, а не описанием в документе.

**Отдельный случай — `CampaignRewound`.** Он по определению переписывает всё
состояние целиком, то есть нарушает инвариант `commitDerived`. Он не производное
событие и не команда: это владельческая операция над журналом. Ему нужен
собственный вход `executor.commitControl` с `CAMPAIGN_CONTROL_CAPABILITY`,
проверкой полномочий владельца и границами арки — иначе allowlist шага 5
придётся ослабить до бессмысленности.

## Шаг 4. Перевести командные пути

На `executeCommands` переводятся: `GameOrchestrator` (**оба** его писателя),
`AutonomousCampaignOrchestrator` (**все три**), `NpcTurnScheduler`,
`CombatTurnCoordinator`.

**Здесь объявляется изменение поведения.** Строки 2–7 реестра получают retry,
которого у них не было.

**Найдено при переводе (2026-07-31).** Три писателя
`autonomous-orchestrator.mjs` — не механическая миграция, и вот почему:

- часы боя (`combat-turn-coordinator.mjs`) переведены с `maxAttempts: 1`: у них
  **свой** ограниченный экспоненциальный retry по таймеру, и внутренний
  синхронный цикл исполнителя подменил бы его горячими попытками подряд.
  Унифицируется путь записи и обработка повторного ключа, а не политика ожидания;
- стадии наград встречи (`EncounterOutcomeRecorded`, `EncounterCoinsRolled`,
  `EncounterRewardsDistributed`) пишут **опыт, монеты и инвентарь**, то есть
  ровно то, чем владеет Rules Engine. Через `commitDerived` они не пройдут и не
  должны: их инвариант это прямо запрещает. Правильный путь — типизированные
  команды награды в Rules Engine, и это отдельная работа, а не строка в таблице
  миграции. До неё `commitEventsWithRetry` остаётся своим путём с собственной
  проверкой контракта стадии.

Это не отговорка, а уточнение объёма: план писался до того, как награды стали
пятистадийными, и «перевести все командные пути» для них означает сначала
завести команды. Тесты шага 0 обновляются явными коммитами с обоснованием
в сообщении коммита. Это не маскируется под рефакторинг.

`server/rules-engine.mjs` (11 400 строк после второй волны) не рефакторится.
Записано как решение, а не как умолчание, — чтобы на шаге 7 никто не начал
«заодно».

## Шаг 5. Перевести производные события

Девять путей `index.mjs` → `commitDerived`, по явной таблице, а не по общей
эвристике:

| Производитель | Разрешённые события |
| --- | --- |
| Party decision | `PartyDecisionOpened`, голос, истечение, разрешение |
| Presence | только изменения состава голосующих |
| Economy clock | только серверные события часов; restock остаётся через Rules Engine |
| Campaign lifecycle | только события жизненного цикла и summary |
| Public dice | только публичный внеигровой бросок от `DiceService` |
| Campaign control | `CampaignRewound` — через отдельный `commitControl`, см. шаг 3 |

Экономические часы — гибрид, и таким остаются: restock идёт через
`executeCommands`, событие часов — через `commitDerived`. Это единственный путь,
который расщепляется на два.

**Открытый вопрос, решаемый здесь, а не позже.** Групповой бросок влияет на исход
решения отряда, то есть на ход истории. Рекомендация — перевести его в
типизированную команду в этом же шаге. Иначе `PUBLIC_DICE_CAPABILITY` навсегда
останется с двумя разными смыслами.

**Замок шага — статический тест-сторож:** production-код вне executor не
вызывает `eventStore.commit`. Исключения: сам Event Store, `server/migrations/`,
тестовая инфраструктура. Сторож ценнее самой миграции: он не даёт появиться
семнадцатому писателю. За время второй волны их прибавилось трое — при живом
стороже ни один не появился бы незаметно.

## Шаг 6. PostCommitCoordinator

Координатор получает только подтверждённые события и запускает детерминированную
последовательность:

```
commit
  → quest consequences
  → combat continuation
  → encounter completion
  → world/director trigger
  → visible projection
  → narration
```

**Два вида ключей, не один.**

| Вид | Ключ | Примеры |
| --- | --- | --- |
| Одноразовое последствие | от стабильного источника / `event_id` | разрешение квеста, завершение встречи, награда |
| Продолжение цикла | от позиции в состоянии | `campaign + encounter + round + initiative index + actor + phase`; `campaign + arc + chapter + director beat` |

Обоснование различия: `event_id` по умолчанию генерируется случайно и стабилен
только благодаря идемпотентности коммита — для одноразового последствия этого
достаточно. Планировщик NPC и координатор боя уже сегодня ключуются по позиции, и
это сделано верно: цикл должен возобновляться после падения на середине очереди
инициативы. Ключ от события дал бы повторный проход.

Отдельно учесть стадии наград встречи (`outcome → xp → coins → loot →
distribution → transition` из PR #28): это уже готовый пример одноразовых
последствий с сохранённым payload, и координатор обязан их не дублировать.

Режиссёр вызывается по детерминированным триггерам — цель сцены разрешена, бой
окончен, нет следующего шага, достигнут лимит темпа, — а не после каждого хода.

## Шаг 7. Разгрузить `index.mjs`

**Разбор объёма (2026-07-31), сделанный после шагов 5 и 6.** Координатор из шага
6 готов и покрыт тестами, но подключать его нужно не «везде сразу»: в `index.mjs`
последствия после коммита собраны в десяти местах с разным контекстом — маршрут
хода, автономный ход, продвижение автономии, награды, откат, решения отряда.
Порядок подключения, при котором каждый шаг проверяем отдельно:

1. **Автономное продвижение** (`/api/campaigns/:id/autonomy/advance`) —
   выполнено: завершение встречи ключуется
   `encounter-completion:<id>:transition`, то есть ровно как одноразовое
   последствие координатора.
2. **Обычный ход** (`/api/narrate`) — **пересмотрено после разбора кода
   2026-07-31.** Здесь переносить нечего: в маршруте после коммита остались
   ровно два вызова — `persistAuthoritativeProjection` и отдельный
   `appendRoomJournal`, причём журнал вынесен отдельно намеренно (он пишется и
   на ходе без изменения состояния). Пропустить их через координатор — значит
   добавить косвенность, не убрав ни одного дублирующего пути. `persistAuthorita‑
   tiveProjection` и без того один на весь модуль: 23 вызова одной функции, а
   не 23 реализации.
3. **Продолжение боя** — здесь и лежит настоящая работа шага 7. Сейчас решение
   «кто ходит дальше» размазано по трём местам: `runNpcTurnScheduler` в маршруте
   хода, `CombatTurnCoordinator.nudge` по таймеру и `autonomousCampaign.runCombat`
   в автономном пути. Именно это должно стать стадией `combat-continuation` с
   ключом от позиции — и именно поэтому переносить его нужно отдельным PR с
   живым прогоном боя, а не «заодно» с проекцией.

**Вывод по объёму.** «Разгрузить `index.mjs`» — это не перенос вызовов проекции,
а перенос **сценариев**: продолжения боя и триггера Режиссёра. Косметическая
часть выполнена и остановлена сознательно; оставшаяся требует прогона живого боя
и потому вынесена в собственный PR.

Только после этих трёх `index.mjs` перестаёт содержать игровые сценарии, и
разделение на три процесса становится механическим. Раньше — нет: перенос
«всего сразу» смешал бы рефакторинг с изменением поведения, чего план
последовательно избегает.

Три процесса, не четыре:

```
Bootstrap
Turn
PostCommitContinuation
```

Бой и автономный Режиссёр — разновидности post-commit continuation, а не
равноправные конвейеры: оба запускаются после коммита хода. Четыре равноправных
конвейера воспроизвели бы ровно ту множественность путей, которую убирают шаги
3–5.

`index.mjs` остаётся composition root: собирает LLM-клиент, внедряет зависимости,
маршрутизирует. Без сценариев перехода сцены и продолжения боя.

## Шаг 8. Трассы, descriptors, контексты

- `turn-trace/v2` и сквозной `proposal_id` через всю цепочку: предложение агента →
  решение политики → команды → события → повествование. Тогда `/why` сможет точно
  разделить, что предложила модель, что изменил сервер и что сохранилось.
- Миграция сохранённых трасс в `server/migrations/`. Здесь же снимается долг
  `prompt_versions` и легализуется имя `scene_architect` из шага 2.
- Descriptors рядом с **реальными** загрузчиками промптов. Реестр собирается из
  модулей, тест сверяет реестр с содержимым `prompts/`; сегодня сторожем работает
  список `covered` в `test/security.test.mjs`, и он уже дважды расходился с
  кодом при слиянии веток.
- `PLAYER_REQUEST_ROLES` остаётся **отдельной сущностью**. Это роли маршрутизации
  ввода игрока, а не исполнители; множества не совпадают.
- Контексты агентов унифицируются **по одной роли**, попутно с шагами 6–7.
  `state_version` в контексте взять сразу — это дёшево, и ответ агента,
  построенный для устаревшей версии, нельзя применять без повторной проверки.
  Единовременный перенос всей проекции не делать: `server/agent-context.mjs`
  крошечный, а «единая граница на шесть ролей» дублирует часть
  `server/viewer-projection.mjs` и `security.mjs:buildNarrationBrief`, с высоким
  риском утечки `gm_only`.

## Чего делать нельзя

Ограничения по проекту, а не пожелания.

- Не рефакторить `server/rules-engine.mjs`.
- Не давать Рассказчику и Режиссёру доступ к `commit`.
- Не вводить прямые сообщения `Director → NPC → Narrator`.
- Не заводить общую изменяемую «память агентов» вне Event Store.
- Не добавлять отдельный вызов LLM на обычный ход NPC и вообще в горячий путь
  хода.
- Не делать агента, который сам решает, когда ему запускаться.
- Не превращать проект в микросервисы. Для игры важнее причинность и replay, чем
  самостоятельность агентов; модель «агенты предлагают, сервер решает» надёжнее.
- Не разбирать в рамках этого плана пересечение `adventure-director.mjs` с
  `director-agent.mjs` — отдельная работа.
- Не ломать сохранённые кампании и старый replay без явной миграции в
  `server/migrations/`.

## Критерий готовности всего плана

1. `eventStore.commit` вызывается ровно из одного модуля; сторож это проверяет.
2. Все 16 писателей имеют одинаковую политику идемпотентности и retry.
3. Каждое производное событие разрешено явной таблицей и неподделываемой
   capability.
4. Последствия после коммита выводятся одним координатором с двумя правилами
   ключей.
5. Проекция комнаты либо доказана тестом эквивалентности, либо удалена в пользу
   полного пересчёта.
6. `index.mjs` не содержит игровых сценариев.
7. `pnpm verify` и `pnpm cutover:audit` зелёные на каждом PR.
