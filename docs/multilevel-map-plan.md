# План: многоуровневые локации и внешний вид карты

Статус: утверждённые развилки (2026-08-02, решения владельца):
- Переход между этажами — **явное действие** у лестницы/люка, не автоматика при шаге.
- Партия перемещается между этажами **вся вместе**; активный этаж один на локацию.
- В бою переход **запрещён** (MVP); снятие запрета — отдельное решение позже.
- Внешний вид: освещение и тени, разнообразие пола и декора, анимации и переходы,
  UI этажей. Новые растровые текстуры/стампы владелец готов генерировать отдельно —
  план фиксирует спецификацию для них.

Связанные документы: `docs/tactical-map-plan.md` (базовый контракт карты),
`docs/known-limitations.md`, `docs/current-architecture.md`.

## 1. Цель и критерий приёмки

Локация может иметь несколько этажей (надземных и подземных). Игрок подводит
персонажа к лестнице или люку, жмёт «Подняться/Спуститься» — вся партия
оказывается на другой карте той же локации, с сохранением тумана войны,
предметов и противников на каждом этаже независимо. Возврат на этаж
возвращает его ровно в том состоянии, в каком его покинули.

Критерий приёмки: таверна с погребом и вторым этажом — партия поднимается в
спальни, спускается в погреб, возвращается в зал; после перезапуска сервера
(replay событий) все три этажа восстанавливаются бит-в-бит; бюджеты
`test/tactical-map-budget.test.mjs` зелёные.

## 2. Ключевые решения

- **Этаж = отдельная `TacticalMap`** той же локации. Никакого 3D и никакой
  многоэтажности внутри одной сетки — `elevation` остаётся тем, чем был
  (возвышенность ±5/10 футов в пределах этажа).
- **Активный этаж живёт в `state.scene.map`**, как сейчас. Весь существующий
  код движения, раскрытия, проекции и рендера не знает про этажи и не меняется.
- **Неактивные этажи лежат в `state.locationMaps`** под составным ключом.
  Это переиспользует память локаций, `MapStore`, reveal-дельты и клиентский кэш.
- **Переход — новая лёгкая команда `UseLevelTransition`**, а не `AdvanceScene`.
  `AdvanceScene` сбрасывает бой/врагов и требует решения группы — для лестницы
  внутри здания это неправильно.
- **Крючок — существующие ассеты** `stairs_up` / `stairs_down` / `trapdoor`,
  которые уже помечены `interactive: true` в `server/asset-registry.mjs:207-210`,
  но ни к чему не подключены.
- **Генерация этажа — ленивая и детерминированная**: этаж строится при первом
  переходе, из стабильного сида; в событие кладётся готовая карта
  (по прецеденту `SceneAdvanced`), replay ничего не перегенерирует.

## 3. Модель данных

### 3.1 Ключ этажа

```
level: целое. 0 — этаж входа (как сегодня), +1, +2 — вверх, −1 — подвал.
levelKey(locationId, level) = level === 0 ? locationId : `${locationId}@L${level}`
```

Ключ уровня 0 совпадает со старым `locationId` — все существующие сохранения
валидны без миграции. `normalizeLocationMaps` (`server/adventure-director.mjs:150`)
принимает новые ключи как есть; лимит 100 записей общий (этажи считаются).

### 3.2 Расширение контракта карты (`server/tactical-map.mjs`)

Только аддитивные необязательные поля, версия `skazanie:tactical-map-v1`
сохраняется:

- `TacticalMap.levelIndex?: number` — этаж этой карты (по умолчанию 0).
- `TacticalMap.levelLabel?: string` — «Второй этаж», «Винный погреб».
- `TacticalProp.transition?: { toLevel: number, label?: string }` — предмет
  является переходом. Валидация: `toLevel` — целое, `|toLevel| ≤ 3`,
  `toLevel !== levelIndex`; предмет с `transition` обязан быть одним из
  ассетов реестра с флагом `interactive` (`stairs_up`, `stairs_down`,
  `trapdoor`, позже `ladder`, `rope`).

Пустые клетки над двором на верхнем этаже кодируются существующим слоем
`present` (бит 0 = клетки нет) — новых типов клеток не нужно.

Зеркала: `src/types.ts:724-750` (тип `TacticalMap`), `src/tactical-map-client.ts`
(`decodeTacticalMap` — пробросить новые поля).

### 3.3 Состояние движка

- `state.scene.level = { index, label }` — текущий этаж (для проекции и UI).
- `state.locationLevels[locationId] = [{ index, label }]` — известные партии
  этажи локации (пополняется при первом переходе; UI-индикатор строится из него).
- `state.levelEntities[levelKey] = { enemies, entities, props-state }` — стэш
  «жителей» неактивного этажа. При уходе с этажа сущности складываются сюда,
  при возвращении — восстанавливаются. Противники не преследуют партию между
  этажами (следствие запрета перехода в бою).
- `state.locationMaps[levelKey]` — карта неактивного этажа с накопленным
  раскрытием (формат записи прежний, `rememberSceneMap`).

`AdvanceScene` при уходе из локации сперва выполняет ту же консервацию, что и
переход этажа (запомнить карту + стэш сущностей текущего этажа), затем работает
как раньше. Возврат в локацию приводит на **этаж 0** (вход снаружи всегда на
уровень входа).

## 4. Механика перехода

### 4.1 Команда `UseLevelTransition`

Игровая команда (доступна игрокам вне боя; добавить в политику
`server/index.mjs:320` рядом с существующими):

```
{ command_type: 'UseLevelTransition', actor_id, prop_id }
```

Валидация в `resolveCommand` (`server/rules-engine.mjs`, рядом с
`OperateSceneObject` `:8366`):

1. Есть тактическая карта, `prop_id` существует, у предмета есть `transition` —
   иначе `TRANSITION_NOT_FOUND`.
2. Идёт бой → `LEVEL_TRANSITION_IN_COMBAT` («сначала завершите бой»).
3. `actor_id` — персонаж партии, стоит в Чебышёв-дистанции ≤ 1 от футпринта
   предмета → иначе `TRANSITION_TOO_FAR`.
4. Целевая карта: `state.locationMaps[levelKey(locationId, toLevel)]`, а при
   отсутствии — **генерация этажа** (раздел 5) прямо в resolve. Сид:
   `stableLocationMapSeed(locationId)` ⊕ `toLevel`.
5. Точка прибытия: на целевой карте ищется парный предмет с
   `transition.toLevel === fromLevel` (генератор обязан его ставить,
   предпочтительно в тех же координатах — лестницы стоят «стопкой»).
   `party_positions` считаются BFS от парного предмета по walkable-клеткам,
   как при `SceneAdvanced`.

### 4.2 Событие `MapLevelChanged`

```
{ type: 'MapLevelChanged', location_id, from_level, to_level,
  map: <сериализованная карта этажа>, level_label,
  arrival_prop_id, party_positions: [{actor_id, x, y}] }
```

Применение (`applyGameEvent`):

1. `rememberSceneMap(state, levelKey(from_level))` — законсервировать старый этаж.
2. Стэш сущностей старого этажа в `state.levelEntities`, восстановление стэша
   нового (если был).
3. `state.scene.map` = карта из события; `state.scene.level` = `{to_level, label}`;
   `syncSceneCells` (единственная точка записи `scene.cells` сохраняется —
   охраняется `test/tactical-map-state.test.mjs`).
4. Расстановка партии по `party_positions`, `revealSceneCells` вокруг прибытия.
5. Пополнение `state.locationLevels[locationId]`.
6. Нарративная строка в журнал («Партия поднимается по скрипучей лестнице…» —
   шаблон, без вызова LLM; директор увидит смену этажа в следующем брифе).

Проекция: `publicSceneFor` (`server/viewer-projection.mjs:277`) дополнительно
отдаёт `scene.level` и `locationLevels` текущей локации. Больше ничего —
неактивные этажи игроку не видны.

### 4.3 Директор и нарратив

- В сцен-бриф директора добавить строку «Этаж: {label}; известные этажи: …»,
  чтобы LLM не выдумывал геометрию.
- `director-scene-transition` не трогаем: переход между этажами — не смена
  локации, решение группы не требуется (утверждено: партия ходит вместе, но
  инициирует переход один игрок — остальных «перевозит» вместе с ним; это
  осознанный компромисс темпа удалённой игры).

## 5. Генерация этажей

### 5.1 Заявка архитектора

Промпт `prompts/map_architect/` → v4: необязательное поле

```
"levels": [ { "offset": 1, "hint": "спальни и кабинет хозяина" },
            { "offset": -1, "hint": "винный погреб" } ]   // максимум 3 доп. этажа
```

Отсутствие поля = одноэтажная локация (обратная совместимость). Схема-валидация
в `server/scene-architect.mjs` — отбрасывать лишнее, зажимать `|offset| ≤ 3`.

### 5.2 Правила построения

Новый модуль `server/level-generator.mjs` (чтобы не раздувать
`building-generator.mjs`), переиспользующий его примитивы:

- **Верхний этаж здания**: наследует внешний контур здания с этажа ниже
  (клетки двора → `present = 0`, «пустота»); комнаты нарезаются заново от сида;
  `stairs_down` ставится в координатах `stairs_up` нижнего этажа с
  `transition.toLevel = fromLevel`; окна по внешним стенам.
- **Подвал**: контур ≤ контура первого этажа; материал `stone`/`earth`;
  тема crypt/cave-примитивы; `stairs_up`/`trapdoor` в координатах спуска.
- **Пещеры**: `layoutOrganicCave` с дополнительным констрейнтом «точка
  прибытия обязана быть walkable и связана с основной полостью» — иначе код
  отказа по образцу `GEOMETRY_LOST_TOPOLOGY` и перегенерация с соседним сидом.
- Инвариант связности: на каждом этаже, кроме 0, есть хотя бы один предмет
  с `transition`, и он достижим из точки прибытия (проверка `scene-graph`-
  утилитами достижимости).
- Гарантия существующего теста «обязательный выход нельзя вытеснять POI»
  распространяется на переходы (`test/scene-points-of-interest.test.mjs`).

### 5.3 Детерминизм

Один и тот же `(locationId, level, seed)` даёт байт-в-байт одинаковую карту —
это условие честного replay (генерация в resolve, событие несёт карту, но
тест дополнительно фиксирует детерминизм самого генератора).

## 6. Клиент

### 6.1 Переход

- `src/useGameSession.ts` — новая команда `useLevelTransition(propId)` по
  образцу `movePlayer` (`:1090`).
- `src/DungeonMap.tsx` — в существующем меню предмета: если у предмета есть
  `transition`, персонаж игрока рядом (≤1) и боя нет — кнопка
  «Подняться на {label} / Спуститься в {label}». В бою — кнопка задизейблена
  с подсказкой причины.

### 6.2 Индикатор этажей

Компактный вертикальный виджет на доске (стек «2 этаж / 1 этаж / Погреб» из
`locationLevels`), активный подсвечен. Кликов нет (вид следует за партией);
это же место в будущем станет переключателем «подглядывания» для ведущего.
Рендер — DOM поверх канвы, рядом с существующими контролами `DungeonMap`.

### 6.3 Камера и кэш

- Ключ камеры `cameraByLocation` (`src/TacticalBoard.tsx:206,240-254`)
  расширяется до `levelKey` — у каждого этажа своя запомненная камера.
- `src/scene-map-cache.ts` уже ключуется хешем карты — этажи кэшируются
  бесплатно; проверить, что лимит 8 записей не выбивает этажи при частой
  беготне (поднять до 12 при необходимости).

### 6.4 Анимация перехода

Кроссфейд на канве: перед заменой карты снять `ImageBitmap` текущего холста,
рисовать поверх нового с убывающей альфой и лёгким сдвигом по вертикали
(вверх при подъёме, вниз при спуске), ~400 мс, только на
`board-effects-canvas` — тайловый кэш не трогается.

## 7. Внешний вид (четыре потока)

### 7.1 Освещение и тени

Принцип: свет **запекается в тайловый кэш**, а не считается в кадре — бюджет
кадра ≤ 16 мс неприкосновенен.

- Сетка освещённости `Uint8Array` на карту: амбиент по теме и `zoneId`
  (interior у crypt/cave/dungeon тёмный, exterior светлый; позже — время суток),
  плюс радиальные источники от предметов (`torch_wall`, `campfire`,
  `fireplace`, `candelabra`, окна днём) с затуханием и обрезкой по стенам
  (грубо: по рёбрам `wall`, без честного raycast в MVP).
- Рендер: множительный слой поверх тайла в `drawFloorTiles`/`syncTileCache`
  (`src/board-render.ts:409-663`); пересчёт только затронутых тайлов при
  открытии двери / изменении предметов / раскрытии.
- Мягкая тень у стен: затемнение полосы в 0.25 клетки вдоль рёбер `wall` —
  дёшево, сильно добавляет объёма.
- Подвалы/верхние этажи получают свои амбиенты через `levelIndex` + тема.

### 7.2 Разнообразие пола и декора

- Активнее использовать существующий слой `variant`: генераторы должны
  раскидывать 3–4 варианта текстуры пола по шуму от сида (сейчас пол монотонный).
- Декали поверх пола (трещины, пятна, ковры, солома, лужи) — расширение
  `drawDecals` (`src/board-render.ts:700`) и `prop-placement` (декали не
  занимают клетку).
- Сглаживание границ материалов между зонами: ряд дизеринга в 1 клетку на
  стыке `material`-зон в `drawFloorTiles`.
- **Спецификация для генерируемых владельцем текстур** (пайплайн уже есть —
  `pnpm terrain:tiles` / `pnpm props:atlas`, манифесты
  `/assets/maps/terrain/terrain-tiles.json`, `/assets/maps/props/prop-atlas.json`):
  - тайлы пола/стен: PNG 128×128, бесшовные (seamless по обеим осям),
    по 3–4 варианта на материал; приоритет — wood (доски двух тонов),
    stone (кладка + плиты), earth, marble;
  - декали: PNG с альфой, 128×128 или 256×128 (ковры), мягкие края;
  - стампы предметов: PNG с альфой, вид сверху, 256×256 на клетку футпринта;
    первые кандидаты — кровать, шкаф, бочки, винный стеллаж, ткацкий станок;
  - список нужных ассетов ведём в `docs/map-library.md`, владелец генерирует
    партиями, подключение — правкой манифеста без кода.

### 7.3 Анимации

Всё — на `board-effects-canvas` (`src/TacticalBoard.tsx:944`), базовый холст
статичен:

- мерцание огня: осцилляция радиуса/альфы глоу у огненных предметов
  (шум по синусам от времени, без rAF-цикла когда предметов нет на экране);
- блики воды на клетках `surface: water`;
- анимация двери: поворот створки 150 мс при `OperateDoor`;
- кроссфейд этажа (раздел 6.4).

### 7.4 UI и читаемость

- индикатор этажей (6.2);
- тултип у лестницы: «Ведёт: {levelLabel}» (из `transition.label`);
- подписи зон (`zones[].label`) при среднем/дальнем зуме, полупрозрачной
  плашкой, скрываются при сильном приближении;
- мини-легенда (сворачиваемая): цвета поверхностей, укрытия, опасности.

## 8. Хранение и производительность

- **Предварительное условие всего плана**: довести вынос карт из снимков —
  `externalizeMaps`/`internalizeMaps` (`server/map-store.mjs:160,200`) должны
  применяться к снимкам event-store. Сегодня «прирост снимка от карты» —
  174,7 КБ при плановом пороге 5 КБ (храповик 220 КБ,
  `test/tactical-map-budget.test.mjs:237-255`). Умножение карт на число этажей
  без этого взорвёт снимки. После выноса — затянуть храповик.
- Событие `MapLevelChanged` несёт карту (~70 КБ на 100×100) — в поток событий
  это попадает один раз на первую генерацию этажа; повторные переходы должны
  нести только `map_hash` + брать тело из `MapStore` (по образцу
  `externalizeMaps`). Зафиксировать бюджет: повторный переход ≤ 2 КБ события.
- Новые пороги в `tactical-map-budget.test.mjs`:
  - resolve `UseLevelTransition` с генерацией этажа ≤ 150 мс, без генерации ≤ 15 мс;
  - пересчёт сетки освещённости 100×100 ≤ 30 мс;
  - размер стэша `levelEntities` на этаж ≤ 8 КБ.
- Локальные пороги строгие, на общем раннере — существующий
  `SHARED_RUNNER_TOLERANCE` (решение владельца о разведении бюджетов по средам).

## 10. Риски

- **`rules-engine.mjs` — 11,7 тыс. строк**: правки точечные (новый case +
  apply), никакого рефакторинга попутно.
- **Снимки**: без L0 этажи умножат красный бюджет; L0 идёт первым.
- **Стэш сущностей**: призванные существа, компаньоны, эффекты зон при смене
  этажа — в MVP стэшируются как есть; граничные случаи выписать тестами
  (саммон на старом этаже не должен «умереть» при возвращении).
- **Старые кампании**: отсутствие `levelIndex` = этаж 0; `normalizeLocationMaps`
  обязана переварить и старую, и новую форму (replay-тест на смешанном логе).
- **Директор-LLM**: без строки об этаже в брифе начнёт «выдумывать» географию;
  правка брифа входит в L3.
- **Бюджет LLM не растёт**: заявка `levels` — часть существующего вызова
  архитектора, отдельных вызовов на этаж нет (генерация процедурная).

## 11. Открытые вопросы (не блокируют MVP)

- Подглядывание ведущего на неактивные этажи (read-only вид) — кандидат в L8+.
- Переход в бою «за действие» с преследованием — отдельное решение владельца
  после обкатки MVP.
- Дальнобойные атаки/заклинания между этажами (балконы, пролёты) — вне рамок.
- Время суток как источник амбиента для окон — после появления мировых часов.
