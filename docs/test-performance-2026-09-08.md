# Продолжение оптимизации — 8 сентября 2026

Предыдущий этап и его ограничения: [замеры 7 сентября](test-performance-2026-09-07.md).
Все измерения ниже относятся к текущему рабочему дереву на Node 24.19.0 в Windows.

## Хранилище событий

`FileEventStore._applyEvent` больше не создаёт дополнительную JSON-копию
состояния перед reducer. Оба вызывающих пути — загрузка и коммит — передают
ему уже проверенный приватный JSON-объект и затем заменяют его результатом
обработки. Копия события сохранена: исходное событие ещё должно попасть в журнал.
Обе защитные копии вокруг нормализатора также сохранены.

Тесты проверяют мутацию и захват аргументов reducer/нормализатором, независимость
ответов и записанных событий, повтор команды, историческую версию, снимок,
повторное открытие и полный replay. Ошибки после изменения состояния — throw,
undefined, Promise, BigInt и циклическая ссылка — не сохраняют часть пакета.
Схема событий и снимков, контрольные суммы, блокировки и fsync не менялись.

## Глобальная карта

При сборке дорожной сети имена мест нормализуются один раз на список мест.
Прежний код повторял нормализацию при поиске каждого конца каждой дороги.
Порядок выбора точки по имени или идентификатору сохранён, включая неоднозначное
совпадение имени ранней точки с идентификатором более поздней. Обработка строк
использует `toLowerCase()` без повторного выбора русской локали.

Старый и новый варианты дали одинаковые результаты создания и согласования
карт на 56 наборах данных: разные регистры, пробелы, Unicode и ссылки на места.
Дополнительный тест проверяет выбор точки, обратный дубликат дороги, неизвестное
место и петлю в одной точке.

## Удалённый код

- `server/engine-mode.mjs` и три его теста: модуль не вызывался приложением.
  Рабочий runtime уже использует `enforce`; прежний HTTP endpoint по-прежнему
  отвечает `410 ENGINE_MODE_RETIRED` и остаётся под тестами.
- `server/persistent-hazards.mjs` и два его теста: универсальные операции
  `apply_hazard`/`resolve_hazard` не подключены к командам и событиям. Сценовые
  `ignite`/`topple`, зоны заклинаний и урон импровизации используют другие,
  действующие модули. Их код и тесты сохранены.

Исправлены устаревшие утверждения в README, таблице покрытия и описании
архитектуры. Исторический аудит и руководство по старой миграции сохранены
с их существующими пометками об историческом статусе.

## Запускатель тестов

В параллельной ветке `tools/run-test-suite.mjs` функциональный корпус запускается
асинхронно. Ранее `spawnSync` блокировал чтение stdout/stderr фонового MVP:
заполненный pipe задерживал сценарий до окончания основного корпуса.

Если функциональный корпус упал, запускатель теперь дожидается MVP, выводит его
буфер и возвращает исходный ненулевой код. Ошибка корпуса возвращается позже,
зато MVP получает возможность исполнить штатную очистку. Его таймаут сохранён.
Проверки производительности по-прежнему идут первыми; concurrency остаётся 4;
в CI MVP работает отдельно и имеет один повтор при ошибке.

Поведенческие тесты запускают копию настоящего runner с маленькими временными
тестами: поток вывода 256 КиБ, завершение MVP при ошибке корпуса, порядок вывода
и ошибка самого MVP. Постоянные параметры и переменные окружения ради этих
фикстур не добавлялись.

## Следующий проход: снимки при пакетах событий

`snapshotEvery` раньше проверялся как `nextVersion % snapshotEvery === 0`.
Пакет событий мог перескочить кратную версию. Снимок тогда не появлялся,
а следующие чтения снова воспроизводили накопленный хвост журнала.

Теперь порог проверяется по числу событий после последнего пригодного снимка:
`current.events_applied + normalizedEvents.length >= snapshotEvery`.
Используется уже посчитанное загрузкой значение. Принудительный снимок начинает
новый интервал; `snapshotEvery=0` по-прежнему выключает автоматические снимки.
Формат, checksum, projector version, MapStore и полный replay не меняются.
Старые файлы не переписываются; дополнительные снимки создаются только новыми
коммитами. Цена ускорения — больше производных файлов снимков.

Внутри `commit` и повторного `importLegacySnapshot` также убрано второе чтение
тех же записей журнала. Уже проверенный массив передаётся `_load` отдельным
внутренним аргументом, пока удерживается блокировка. Публичные `load`/`replay`
не принимают этот массив через options. `getByIdempotencyKey` сохранил
повторное чтение: без блокировки между чтениями может записать другой процесс.
Кэша между вызовами нет.

Воспроизведение ошибки снимков занимало меньше секунды: при интервале 3 пакет
`2→4` оставлял четыре события для replay вместо готового снимка. После правки
тест проходит. Проверены некратный принудительный снимок, отключённый интервал,
историческая версия и перезапуск. Другой тест проверяет новый коммит второго
экземпляра хранилища, исторический ответ по старому ключу, игнорирование подложных
options и обнаружение повреждения журнала даже при наличии свежего снимка.

В том же сценарии концентрации, seed 2:

| Показатель | До прохода | После обеих правок |
| --- | ---: | ---: |
| Применения событий, включая обязательные проверки полного replay | 5036 | 3124 |
| Чтения и проверки набора коммитов | 382 | 330 |
| Созданные снимки | 8 | 17 |
| Время одного прогона | 23,016 с | 20,268 с |

Промежуточный прогон только с новой политикой снимков занял 16,025 с.
Время колеблется из-за параллельной нагрузки; детерминированные счётчики
показывают сокращение повторной обработки на 38% и чтений на 14%.
Все три прогона дали одинаковые 30 шагов и 150 событий. SHA-256 JSON бросков,
событий, команд и финального состояния совпал во всех трёх прогонах.
