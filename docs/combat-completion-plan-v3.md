# Принятый план поимённой приёмки магии и атак — версия 3

План прислан владельцем 21 сентября 2026 и заменяет порядок дальнейшей работы
из [версии 2](combat-completion-plan-v2.md). Ниже сохранён предоставленный текст;
его формулировки о правилах проверяются для каждого пилота по закреплённому источнику.

Исходная точка — [принятый срез общих механизмов](combat-foundations-progress.md):
`pnpm verify` 4153/4153, типы сервера и сборка; HTTP/restart и браузер двумя игроками.
Снимок дерева сохранён отдельно. Повторный прогон относится к новому окончательному
дереву, а исторические P0 не объявляются открытыми без воспроизведения.

Выполнение начато: `pnpm spells:acceptance` строит инвентаризацию 439 ID из
существующего каталога; подготовлены [паспорта четырёх пилотов](spell-pilot-acceptance.md).
Состояние этапов и проверки — в [журнале выполнения](spell-acceptance-progress.md).
Порядок: `longstrider` → `mass-cure-wounds` →
`protection-from-energy` → `destructive-wave`, с проверкой связанных `partial`.
Общий обработчик и снятие блокировки не увеличивают счётчик полностью принятых ID.

## Пометки стартовой сверки

- Все четыре пилота сейчас `heuristic`, без отдельного override. Перед включением
  проверяются реальные эффекты: прибавка скорости и срок `longstrider`; точка,

  домена или его административная выдача такого пути не подтверждает.

  сохраняются отдельно. Аналогично исправлена особая запись `gift-of-gab`;

  Реализация отдельной оплаты по источникам применения остаётся впереди.

Эти пометки уточняют зависимости и выполненные исправления импорта.
Статусы готовности заклинаний не повышены.

Главные изменения: разделить доступность и полную готовность; уточнить зависимости первой партии; отдельно спроектировать длительное накладывание, Ready и повторные действия; добавить условия совместимости сохранений и повторной проверки уже работающих карточек.

Числа **191 `heuristic`, 8 `ruling-only`, 240 `partial`**, наличие компонентов и остаток из 13 сложных требований принимаю из твоего сообщения — это не новый аудит текущего кода. Полного списка 199 ID и 13 требований в сообщении нет: его нужно получить из актуального каталога, а не восстанавливать предположениями.

# 1. Цель и границы

**Цель — все 439 заклинаний кругов 0–6, включая небоевые применения, и все заявленные виды атак.** Не только разблокировать оставшиеся 199, но и довести 240 частичных до подтверждённой готовности.

Круги 7–9 и развитие выше принятого ограничения 12-го уровня не добавляются автоматически. Правила задаёт закреплённый профиль D&D 2014; BG3 остаётся ориентиром управления, читаемости и постановки. Эти границы соответствуют исходной контрольной точке.

### Что необходимо поправить в предложенной последовательности

**Первая партия неоднородна.** `longstrider` действует час, а `protection-from-energy` требует концентрации и поддерживает выбранное сопротивление. Это не мгновенные эффекты, поэтому у них другие зависимости и проверки. ([D&D Beyond][1])

**Готовность компонентов не равна готовности всех способов их применения.** Остаток из 13 требований нужно связать с конкретными карточками, источниками магии, предметами и моментами расходования.

**`ruling-only` нельзя автоматически считать одним типом блокировки.** Нужно различать отсутствующий обработчик и настоящее требование решения ведущего. В первом случае реализуется механика; во втором — проверяемый порядок принятия и исполнения решения.

**Общий обработчик не сертифицирует всё семейство.** Он закрывает зависимость, но каждое заклинание сохраняет собственные исключения, пользовательские выборы и условия окончания.

# 2. Этап 0. Зафиксировать основу и закрыть блокирующие регрессии

**Результат этапа — проверенная версия, относительно которой можно безопасно расширять покрытие.**

Зафиксировать коммит и рабочий diff, версию пакета правил, каталога, тестовых данных и измерений. Незакоммиченные изменения сохранить; старые пояснения блокировок сопоставить с текущими обработчиками.

Полный `pnpm verify` должен относиться к окончательному дереву. Ранее зелёный прогон другого diff не подтверждает готовность нового. При этом уже исправленные проблемы не нужно реализовывать повторно.

Из предыдущей контрольной точки использовать следующий контрольный список: 0 ОЗ и последовательные области, общие модификаторы спасбросков, защитные реакции, расход конкретного одноразового эффекта, строгий выбор ячейки и других ресурсов, причина таймаута длинного сценария. **Это исторически зафиксированные риски, а не утверждение, что они до сих пор открыты.**

При ошибке запуска тестового сервера сохранять код выхода, сигнал и ограниченный хвост логов. При зависании игры — seed, последнюю команду, версию состояния, ожидаемое решение и стадию исполнения.

**Приёмка:** актуальные P0 закрыты; общий gate зелёный; нет пропущенного сценария или таймаута, скрытого увеличением лимита.

# 3. Этап 1. Создать единую поимённую матрицу всех заклинаний

## 3.1. Расширить существующий рабочий каталог

Не создавать вторую независимо поддерживаемую таблицу. У каждой карточки должен появиться компактный паспорт:

| Блок                   | Что фиксировать                                                                  |
| ---------------------- | -------------------------------------------------------------------------------- |
| **Идентичность**       | `spell_id`, названия, исходная группа статуса, отдельная доступность в игре      |
| **Источник**           | Редакция, публикация, карточка dnd.su, ревизия принятого описания, исключения    |
| **Текущая реализация** | Реальные обработчики и подтверждённые сценарии                                   |
| **Остаток**            | Конкретное неисполняемое правило и зависимости                                   |
| **Выборы игрока**      | Цели, точка, область, режим, тип энергии, источник ресурса, усиление, согласие   |
| **Жизненный цикл**     | Начало, применение, повторные действия, прерывание, длительность, прекращение    |
| **Взаимодействия**     | Зависимые общие механизмы и опасные сочетания                                    |
| **Доказательства**     | Тесты, основной HTTP/UI-путь, replay/restart, два игрока, 2D/3D, анимация и звук |

**Классифицировать по исполняемому эффекту.** Школа, цвет и визуальный образ не определяют тип серверной сущности. Одно заклинание может зависеть одновременно от предметов, длительного накладывания и скрытой информации.

Полную инвентаризацию ID можно сделать сразу, а подробные спецификации готовить для ближайших партий. Не нужно задерживать первый пилот до исчерпывающего описания всех взаимодействий 439 карточек.

## 3.2. Разделить доступность и доказанную готовность

Существующие статусы необязательно переименовывать. Но к ним нужны отдельные измерения готовности: **правила, пользовательский путь, устойчивость, права и представление**.

> **Снять блокировку** — разрешить подтверждённый путь применения.
> **Принять полностью** — закрыть все обязательные ветки конкретного ID в согласованном корпусе.

Если остаётся существенная неподдержанная часть, карточка остаётся частичной. Экспериментальное включение возможно только явно и не увеличивает число полностью готовых.

Галерея, административная выдача и прямой вызов обработчика не доказывают работоспособность для обычного игрока.

Для `ruling-only` отдельно фиксировать границы решения ведущего и исполнимый результат. Упрощение, меняющее правило источника, должно называться отдельным вариантом правил, а не полным соответствием D&D 2014.

**Приёмка:** каждому из 439 ID назначены актуальный остаток, зависимости и проверочные сценарии. Исходные группы 199 и 240 сохраняются для сравнения прогресса.

# 4. Этап 2. Доработать общие механизмы через пилоты

**Не требуется закончить весь этот этап перед первым заклинанием.** Каждый подраздел развивается в минимальном объёме, необходимом очередному пилоту, и сразу проверяется через него.

## 4.1. Ресурсы и сложные компоненты

Основу компонентов не переписывать. Довести оставшиеся требования: несколько предметов, количество, минимальную стоимость, наборы, расходование, частичный расход и особые платежи.

Для каждого требования определить, откуда берётся предмет, как проверяются владение и доступность, допускается ли деление, когда он резервируется и когда расходуется.

**Не подменять требования арифметикой цены.** Один дорогой предмет не заменяет автоматически набор предметов или расходуемое вещество. Допустимость замены устанавливается конкретным правилом.

Источник применения выбирается явно: обычная ячейка, pact, врождённая магия, предмет, свиток или другой поддержанный путь. Указанная недоступная ячейка не заменяется другой без предусмотренного выбора.

Проверки рук, речи и фокуса должны учитывать конкретный источник применения и его исключения. Одного общего признака «компоненты есть» недостаточно.

### Компонент А

При выборочной сверке выясняется, что **А — компонент авторских отчислений**. В карточке «Сверкающей монеты Джима» описано отдельное денежное требование, в том числе при применении через свиток или предмет. Его нельзя молча свести к обычному материальному компоненту. ([5e14.dnd.su][2])

Для соответствующих ID закрепить цену, плательщика, момент платежа, отсутствие средств и предусмотренные исключения. Не распространять этот механизм на остальные заклинания.

### Атомарность ресурсов

Два одновременно начатых действия не должны расходовать один экземпляр компонента. Ошибка, отмена и повтор запроса не создают второй расход или возврат.

Приёмка должна включать **цепочку доступности**, а не только само применение: получить или изучить заклинание предусмотренным способом, подготовить при необходимости, получить компоненты, выбрать действие и выполнить его.

**Приёмка:** 13 требований имеют поимённые положительные и отрицательные тесты; сложный компонент проверен через основной сайт, а не только подготовлен административной командой.

## 4.2. Длительное накладывание, Ready и повторное действие

Это три разные операции:

| Операция                             | Что нужно сохранять                                                                              |
| ------------------------------------ | ------------------------------------------------------------------------------------------------ |
| **Длительное накладывание / ритуал** | Начало, выполненные этапы, игровые часы, действия, концентрацию, прерывание и расход             |
| **Ready**                            | Подготовленное действие, наблюдаемый триггер, допустимое окно, реакцию и судьбу удержанной магии |
| **Действие существующего эффекта**   | ID экземпляра, право управления, цену повторного действия и оставшиеся применения                |

В правилах 2014 длительное накладывание требует действий по ходам и концентрации; её срыв прекращает попытку без расхода ячейки. Это нужно отражать отдельно от поддержания уже действующего заклинания. ([D&D Beyond][3])

Ready предусматривает обычное накладывание с удержанием энергии и выпуском реакцией; удержание требует концентрации. Поэтому его нельзя реализовать как бесплатное намерение «когда-нибудь потом вызвать `CastSpell`». ([D&D Beyond][4])

Момент расхода материалов сверять по конкретному ID. Правило о ячейке не доказывает автоматически такое же поведение всех компонентов.

Игровую длительность отделить от реального ожидания: закрытие вкладки или задержка LLM не должны незаметно продвигать календарь. При начале боя длительное накладывание продолжается по предусмотренной процедуре, а не завершается бесплатно.

**Атомарность зависит от границы действия.** Мгновенное действие без ожидания человека и его обязательные последствия сохраняются одним пакетом. Реакции и долгое выполнение требуют сохраняемых фаз; блокировка не удерживается до ответа человека.

Использовать существующий механизм ожидающих решений, а не создавать параллельный реестр.

**Приёмка:** restart восстанавливает ту же фазу, броски и расходы. Возобновление не создаёт второй эффект.

## 4.3. Экземпляры эффектов и повторные действия

У экземпляра нужны собственный ID, заклинатель, получатель, версия правил, начало и окончание, зависимость от концентрации, заряды, режим и причина прекращения.

**Разделить заклинателя, носителя эффекта и исполнителя повторного действия.** Они не обязаны совпадать; права определяются конкретной механикой.

Повторное действие ссылается на `effect_instance_id`, а не запускает новое накладывание. Снятие одного источника не удаляет чужой. Подавление, окончание и временная потеря возможности управлять эффектом — разные состояния.

Совмещение одинаковых и разных эффектов описать отдельной политикой. Не сводить его к сложению всех бонусов или удалению всех записей с одинаковым названием.

Проверять расход применения, предел суммарного результата, время срабатывания и окончание. После прекращения эффекта его дополнительные действия недоступны.

**Приёмка:** несколько источников и получателей корректно переживают перемещение, снятие, конец боя, смену сцены и восстановление.

## 4.4. Спасброски, урон и реакции

Использовать общие обработчики, а не создавать отдельную арифметику для каждого заклинания.

Для триггера определить окно реакции, доступные сведения, разрешённые действия, выбор ячейки, очередность решений, таймаут и продолжение. NPC проходят те же ограничения, даже когда решение принимает сервер.

Вложенная реакция не теряет исходное действие. Броски и принятые решения сохраняются. Защитная реакция должна влиять на соответствующую фазу результата, а не отменять уже окончательно зафиксированную смерть.

**Смешанный урон хранить по составляющим, связанным с одним воздействием.** Отдельно закрепить порядок сопротивлений, округления, временных ОЗ, концентрации и смерти. Несколько типов урона не превращаются автоматически в несколько самостоятельных ударов.

Одновременность, последовательность лучей, общий или отдельный бросок определяются правилом конкретного ID, а не порядком массива целей.

Защита от повторов не должна подавлять законное повторное срабатывание в другом ходе или при другом предусмотренном триггере.

**Приёмка:** игроки и NPC, несколько претендентов, вложенные реакции, 0 ОЗ и повтор после разрыва соединения проходят сквозные тесты.

## 4.5. Цели и геометрия

Расширять существующий пространственный слой. Явно описать допустимые цели: существо, предмет инвентаря, объект карты, дверь, тело, точка, область, секция стены или удалённая локация.

Разделить дальность выбора, точку происхождения, форму, размеры, ориентацию, высоту, занятость пространства, укрытие и требования видимости.

Предпросмотр и исполнение должны использовать согласованный расчёт. Но дополнительно нужны независимые эталоны клеток: **совпадение двух одинаково ошибочных реализаций не подтверждает правильность**.

Выбор нескольких целей делает игрок. Сервер не добирает их автоматически и не заменяет список заклинателем. Изменение режима или усиления пересчитывает черновик без исполнения.

Видимость и допустимость — разные вопросы. Скрытый участник может затрагиваться разрешённой областью, но не должен появляться в предпросмотре или его метаданных. Отказ по секретному свойству также не должен становиться способом узнать это свойство.

**Приёмка:** правильный результат для границ областей, крупных фигур, разных высот, препятствий и неизвестных игроку участников.

| **2**  | Концентрация/сопротивление и площадной смешанный урон                     | `protection-from-energy`, `destructive-wave`                              |
| **3**  | Повторные действия, ауры, триггеры и пределы                              | `aura-of-vitality`, `dragon-s-breath`, `guardian-of-faith`, `flame-blade` |
| **4**  | Предметы, ремонт, двери, свет и необходимые долгие действия               | `mage-hand`, `mending`, `arcane-lock`, `continual-flame`                  |
| **5**  | Информация, иллюзии, наблюдение и память                                  | `detect-magic`, `identify`, `minor-illusion`, `scrying`, `modify-memory`  |
| **6**  | Полёт, левитация, падение и защитные реакции                              | `fly`, `levitate`, `feather-fall`                                         |
| **7а** | Призывы, контроль, инициатива и поведение                                 | `find-familiar`, `find-steed`, `conjure-elemental`                        |
| **7б** | Изменения формы, отдельно от призывов                                     | `alter-self` и соответствующие ID каталога                                |
| **8а** | Тела, смерть, души и возвращение                                          | `revivify`, `raise-dead`, `reincarnate`, `soul-cage`                      |
| **8б** | Переходы и постоянные изменения мира                                      | `teleportation-circle`, остальные стены и защитные области корпуса        |

Это **очередь зависимостей, а не запрет параллельной работы**. Начинать ветку можно после готовности её оснований.

В каждой партии: сверить пилот → доработать минимальный общий механизм → пройти пилот через сайт → применить решение к зависимым карточкам → проверить каждый ID.

Карточки из 240 `partial`, использующие те же основания, включаются в соответствующую партию. Не нужно откладывать их до завершения всех 199.

# 6. Этап 4. Первые четыре заклинания принимать отдельно

## `longstrider`

Сверенное правило: касание, час действия, увеличение скорости и дополнительные цели при усилении. Это пилот длительного модификатора. ([D&D Beyond][1])

Проверить реальную доступную дистанцию движения, дополнительные цели, окончание по игровому времени, несколько источников, переход в исследование и restart.

**Не принимать:** иконка усиления появилась, но маршрут продолжает рассчитываться по прежней скорости.

## `mass-cure-wounds`

Сверенное правило предусматривает выбор точки и до шести существ в области, исключения по типам целей и усиление лечения. Старшая ячейка не должна автоматически увеличивать количество получателей. ([D&D Beyond][5])

Проверить число целей, геометрию относительно выбранной точки, усиление, предел максимальных ОЗ, недопустимые типы, одинаковые имена, повтор и однократный расход.

**Не принимать:** обработчик умеет лечить массив, но обычный игрок не может правильно собрать этот массив через интерфейс.

## `protection-from-energy`

Сверенное правило: согласная цель касанием, выбор одного вида сопротивления и концентрация до часа. ([D&D Beyond][6])

Проверить выбранный и другой типы урона, смешанное воздействие, пересечение с другими источниками защиты, срыв концентрации, время и снятие только соответствующего эффекта.

Согласие персонажа другого игрока обрабатывается принятой политикой, а не произвольным полем клиента.

## `destructive-wave`

По выбранному проектом источнику нужны выбор затрагиваемых существ, спасбросок Телосложения, две составляющие урона, выбор второго типа и различающийся по спасброску результат сбивания с ног. Поэтому это более сложный интеграционный пилот. ([D&D 5 Онлайн-справочник][7])

Проверить выбранные цели, смешанные сопротивления, успешные и проваленные спасброски, иммунитет к соответствующему состоянию и однократную смерть.

Подготовить персонажа, которому магия действительно доступна в выбранном профиле. Административный обход допустим в части тестов, но не доказывает пользовательскую готовность.

**Результат первой партии:** четыре индивидуально принятых ID, а не четыре одновременно изменённых статуса.

# 7. Этап 5. Проверить небоевые последствия и постоянный мир

Это обязательная часть покрытия, а не финальное украшение после боевых тестов.

### Предметы и помещения

Перенос, ремонт и зачарование работают с реальными ID. Нельзя создавать копию предмета вместо перемещения или чинить любой объект только потому, что LLM убедительно описала успех.

Масса, состояние, доступность и границы действия проверяются сервером. Стены, двери и защитные зоны изменяют реальные возможности прохода и взаимодействия там, где это предусмотрено.

Повреждение секции, физическое разрушение и рассеивание магии не подменяют друг друга.

### Информация, иллюзии и память

Разделить объективную запись мира, доступную персонажу информацию и его представление о произошедшем.

Изменение памяти NPC не переписывает журнал действий игрока и не отменяет объективные последствия. Дистанционное наблюдение формирует разрешённое представление удалённой сцены, а не выдаёт весь мир.

LLM формулирует описание или предлагает намерение. Источник раскрываемого факта, условия проверки и исполнимый результат задаёт сервер.

Для свободных иллюзий и других творческих применений требуется проверяемый контракт: допустимые размеры, свойства, наблюдатели, способы взаимодействия и дальнейшие изменения. Простого текстового описания недостаточно.

### Призывы и формы

Связать статблок, владельца, управляющего участника, инициативу, команды и срок. Присутствие фигурки на карте не доказывает, что существо умеет выполнять положенные действия.

Для форм определить, что сохраняется и заменяется: характеристики, ресурсы, экипировка, доступные действия и способ возврата. Не переносить целиком механику одного превращения на все остальные.

### Смерть и возвращение

Момент смерти, тело, душа, временные пределы, согласие и компоненты проверяются индивидуально.

Возвращение создаёт новое состояние **той же сущности**, а не откат истории или двойника с копией имущества.

Уже случившиеся последствия — смена получателя задания, должности, отношений и распространённых сведений — не отменяются молча. Их дальнейшее развитие должно иметь отдельную политику.

### Транспорт и постоянные эффекты

Нужны реальные адресаты и локации, условия перехода и сохраняемое прибытие. Новая генерация не должна случайно заменять уже известное место.

**Общая приёмка:** применение → изменение мира → уход → продвижение игрового времени → возвращение → restart/replay. Рассказчик, журнал, SSE, звук и анимация отражают разрешённую игроку часть результата.

# 8. Этап 6. Параллельно довести атаки

Это аудит существующих владельцев правил, а не повторная реализация всего боя. Согласованный объём включает оружие, метание, безоружные и природные атаки, классовые приёмы и действия противников.

| Семейство                  | Обязательная проверка                                                                                           |
| -------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Оружие**                 | Экземпляр, хват, свойства, владение, число атак, импровизированное применение                                   |
| **Дальний бой**            | Боеприпасы, заряжание, дистанции, соседние противники, укрытие                                                  |
| **Метание**                | Конкретный предмет, его положение после применения, попадание/промах, возврат; сеть отдельно                    |
| **Безоружные и природные** | Источник способности, формула, досягаемость, дополнительные эффекты статблока                                   |
| **Классовые действия**     | Основное/бонусное действие, Extra Attack, Sneak Attack, smite, manoeuvres, ограничения и расходы                |
| **Особые действия и NPC**  | Grapple, shove, Ready, реакции, multiattack, дыхание, перезарядка, legendary actions/resistance, права призывов |

Проверять не только попадание, но и крит, смешанный урон, иммунитет, защитную реакцию, временные ОЗ, 0 ОЗ, нокаут и однократность смерти.

Урон по спасброску не превращать в обычную атаку, которой назначили отсутствие промаха.

Партии атак связывать с изменениями общих механизмов: геометрия проверяет досягаемость и укрытие, эффекты — состояния оружия, реакции — opportunity attack и Ready.

# 9. Этап 7. Принимать интерфейс и представление вместе с ID

Сохранить управление на карте. Не возвращать отдельное плавающее «Применить», оружейную подсказку поверх режима магии и синтез звука осцилляторами.

Для сложных случаев допустимы встроенные параметры: ячейка, тип энергии, форма, статблок, предмет. Они не должны создавать второй несогласованный путь исполнения.

Проверять двойное нажатие, изменение ячейки после выбора целей, исчезновение цели, смену героя, устаревший черновик, фокус текстового поля и управление камерой. Отмена выбора до начала действия не расходует ресурсы; отмена уже начатого накладывания следует его правилам.

### Постановка должна соответствовать механике

Не всем заклинаниям нужен полёт снаряда. Фазы берутся из реального жизненного цикла: подготовка, разрешение, контакт, результат, поддержание и завершение — только там, где они применимы.

Постоянные эффекты восстанавливаются из состояния. Одноразовый удар или звук не повторяется при повторном HTTP/SSE, переключении 2D/3D или переподключении.

Скрытая магия не раскрывается через визуал, звук, панель реакции или автоматический поворот камеры. Обоснованная тишина — корректное решение, а не обязательно отсутствующий ресурс.

**Общие ассеты допустимы, но соответствие проверяется каждому ID.** Галерея помогает просматривать корпус; основной сайт подтверждает пользовательский путь.

**Приёмка:** реальные кадры или клипы, проверка 2D/3D, аудио или осмысленной тишины и двух независимых игроков. Не только наличие профиля.

# 10. Этап 8. Организовать доказательства и выпуск

## Уровни проверок

| Уровень             | Что подтверждает                                                        |
| ------------------- | ----------------------------------------------------------------------- |
| **Правило**         | Независимые ожидаемые значения при контролируемых бросках и времени     |
| **Интеграция**      | Команды, события, ресурсы, состояния и отсутствие частичного результата |
| **HTTP/SSE**        | Обычного пользователя, права, личные сведения, повторы и восстановление |
| **Браузер**         | Реальные выборы, двух пользователей, 2D/3D, звук и reconnect            |
| **Долгая кампания** | Сохранность и корректность после накопления истории и игрового времени  |

Ожидаемые значения не вычислять тем же обработчиком, который проверяется. При исправлении ошибки новый результат сверять с правилом; ошибочный baseline не должен становиться обязательным эталоном.

Не нужен полный перебор всех пар заклинаний. Нужны классы взаимодействий и конкретные регрессии: область с реакцией и 0 ОЗ; два источника эффекта; несколько срабатываний за ход; усиление и число целей; призыв со сменой сцены; скрытое событие с журналом и звуком; смерть с задачей и возвращением; конкурентный расход одного ресурса.

## Gate каждой поставки

Во время разработки — профильные тесты. Перед включением партии — проверки каталога, зависимых карточек, HTTP, replay и представления. Перед слиянием — полный `pnpm verify` и предусмотренные `spells:verify` / `content:verify` на окончательном diff.

**Результат относится к версии кода.** Изменение общего механизма определяет набор зависимых ID для повторного прогона. Старое «verified» не является достаточным доказательством после изменения его основания.

## Совместимость

Зафиксировать версии изменённых правил и событий. Старые кампании и незавершённые эффекты не получают другую семантику молча.

Replay не вызывает LLM, не повторяет броски и не генерирует заново производные последствия. Ошибка до commit не меняет исходное состояние; потеря ответа после commit обрабатывается возвратом сохранённого результата.

# 11. Этап 9. Организовать субагентов без конфликтующих изменений

Четыре направления сохраняются, но каждому нужен конкретный результат и границы ответственности:

| Направление              | Результат                                                      | Ограничение                                              |
| ------------------------ | -------------------------------------------------------------- | -------------------------------------------------------- |
| **Правила**              | Паспорта ID, исключения, независимые ожидаемые результаты      | Не подтверждает готовность по одному описанию            |
| **Сервер**               | Механизмы, события, ресурсы, совместимость                     | Один назначенный владелец интеграции общего Rules Engine |
| **UI и AV**              | Выборы, отказы, 2D/3D, анимация и звук                         | Не переносит формулы правил в клиент                     |
| **Независимая проверка** | Поимённая приёмка, регрессии, приватность и производительность | Не меняет ожидания ради прохождения ошибочного поведения |

В задании указывать точные ID, разрешённые файлы, исходный коммит и контракт общего механизма.

Центральные нормализаторы, реакции и типы событий интегрировать последовательно. Независимые данные, спецификации и тесты можно готовить параллельно.

**Не распределять сразу массовое редактирование 199 профилей.** Сначала принять пилот и общий контракт, затем раздавать независимые семейства. Иначе агенты будут закреплять разные решения одной и той же проблемы.

# 12. Этап 10. Проверять производительность без обязательного переезда стека

Измерять не только пустую арену, но и небольшую текущую сцену внутри большой кампании, несколько областей, максимальное предусмотренное число целей или призывов и двух SSE-получателей.

Раздельно измерять предпросмотр, подготовку, commit, проекцию, полный HTTP, SSE и применение состояния браузером. Ожидание человека и длительность анимации не должны скрывать медленную серверную работу.

Использовать принятые проектом бюджеты. Новые пороги задавать вместе со стендом и сценарием; ранее поставленная цель не считается достигнутой без нового прогона.

**Недопустимые способы ускорения:** отсечение истории, удаление реально поражённых целей из расчёта, уменьшение разрешённого числа призывов без изменения профиля правил или ослабление проверок.

Новые БД, embeddings и workers не являются предварительным условием покрытия. Подтверждённую блокирующую проблему производительности выносить в отдельную зависимость партии.

# 13. Как считать прогресс и завершение

В отчёте каждой партии показывать отдельно:

| Показатель                       | Что считать                                              |
| -------------------------------- | -------------------------------------------------------- |
| **Принятые из исходных 199**     | Полностью проверенные ранее заблокированные ID           |
| **Доведённые из исходных 240**   | Карточки, у которых закрыты обязательные ограничения     |
| **Доступные, но частичные**      | Исполняемые возможности с явно оставшимися ограничениями |
| **Ожидающие повторной проверки** | ID, затронутые изменением общего механизма               |
| **Открытые блокеры**             | Конкретные зависимости с условиями закрытия              |

Наличие компонента, VFX, иконки или обработчика не увеличивает счётчик готовых карточек.

### Готовность одного ID

Источник принят; обязательные варианты исполняются; есть обычный пользовательский путь; проверены ресурсы, права и сведения; работают повтор, restart/replay и небоевое сохранение; проверены 2D/3D, анимация и звук; общий gate успешен на соответствующей версии.

`N/A` допускается с обоснованием. У мгновенного эффекта может не быть поддержания, но ресурсы и повтор всё равно проверяются. Отсутствующую обязательную механику нельзя объявить неприменимой.

### Готовность всего объёма

Все 439 ID и заявленные виды атак приняты. Обязательные ограничения не спрятаны за общими статусами; поведение мира, ресурсы, текст и карта согласованы. Промежуточные выпуски могут быть частичными, но не называются полным покрытием.

## Ближайшая последовательность

**Актуальный зелёный baseline → паспорта четырёх пилотов → `longstrider` → `mass-cure-wounds` → `protection-from-energy` → `destructive-wave` → связанные `partial` → общий выпуск с доказательствами → следующие волны.**

Это приоритет по ожидаемой сложности, а не жёсткая привязка к названиям. После проверки существующих обработчиков порядок можно поменять, сохранив зависимости и индивидуальную приёмку.

**Главный принцип улучшенного плана: принимать не разблокированные кнопки, а законченные игровые возможности — от выбора игрока до устойчивого последствия в мире.**
