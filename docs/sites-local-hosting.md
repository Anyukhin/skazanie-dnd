# Sites с сервером на компьютере

Схема: `браузер → Sites Worker → бесплатный HTTPS-туннель Pinggy → Node на ПК`.
Игровое приложение, ИИ, аккаунты и сохранения остаются у прежнего сервера.
Sites передаёт существующие HTML, ассеты, API и SSE. Перенос `storage/` не нужен.
Хостинг на Render и Oracle не используется. Расход RouterAI остаётся прежним.

## Запуск и остановка

Перед первым запуском нужна актуальная сборка `pnpm build`, Node >=20.19 и
штатный Windows OpenSSH Client. `START_SITES_DND.cmd` запускает сервер и туннель
в фоне без Docker. `STOP_SITES_DND.cmd` останавливает только связанные процессы;
сохранения не удаляются. Повторный запуск не создаёт второго менеджера.
Если на 8787 уже работает сервер, менеджер использует его и при остановке
не завершает чужой процесс. Не запускать одновременно разные версии сервера
с одним файловым хранилищем.

Менеджер `tools/sites-local-server.mjs` слушает локальный сервер на
`127.0.0.1:8787`. Входящий порт на роутере открывать не требуется. Туннель
выдаёт HTTPS, его текущий адрес сохраняется в игнорируемом `PUBLIC_LINK.txt`.
Ключ SSH этого туннеля и журналы находятся в игнорируемом `tmp/sites-runtime/`.
Менеджер автоматически переподключается после разрыва туннеля и обновляет
адрес сервера у Sites. Пока туннель переподключается, связь с игрой прерывается.
Компьютер должен оставаться включённым и подключённым к интернету.
[Ограничения бесплатного Pinggy](https://pinggy.io/help/).

## Конфигурация Sites

В `.env` локального проекта: `DND_SITES_URL` и `DND_SITES_SERVICE_KEY`.
Служебный ключ не показывать и не коммитить; `.env.example` содержит только
имена переменных. `ROUTERAI_API_KEY` остаётся на компьютере и не передаётся
Sites. `tools/configure-sites-local.mjs` сохраняет URL и служебный ключ из
скрытого stdin. Это вспомогательный инструмент настройки, не игровой API.

Исходники шлюза — `deployment/sites/`. Зарегистрированный checkout Sites —
`tmp/sites/skazanie-game/`; `.openai/hosting.json` там сохраняет фактический
`project_id` и логический D1-binding `ORIGIN_DB`. Продолжать работу с этим
идентификатором, не создавать ещё один Site. Штатный Sites workflow собирает
`dist/server/index.js`, сохраняет исходники и публикует архив. Новые зависимости
не требуются. D1 хранит только один адрес туннеля; игровые данные там не лежат.

Runtime-переменные Sites: `SKAZANIE_ORIGIN` — исходный HTTPS-адрес Pinggy;
`SKAZANIE_LINK_KEY` — секрет обновления адреса. Менеджер использует существующий
служебный credential Sites, выданный владельцу; он хранится только в `.env`. Его ротация
требует синхронно обновить локальную настройку и runtime-секрет Sites.

`PUT /_skazanie/origin` принимает адрес только с серверным ключом, разрешает
только HTTPS-домены Pinggy и сохраняет одну запись в D1. SQL-миграция лежит
в `deployment/sites/drizzle/`; создание таблиц во время запросов не выполняется.
Здесь используется простая SQL-миграция без добавления зависимостей проекта.

Шлюз отклоняет чужой Origin, сохраняет `X-Idempotency-Key`, передаёт только
игровую cookie и нужные заголовки. Служебные cookies и токены Sites не уходят
в игру. API и изображения кампании не кэшируются, SSE передаётся потоком.
После потери ответа команда не повторяется автоматически: состояние может
уже измениться на сервере. Проверки — `test/sites-gateway.test.mjs`.

Проверить скорость можно командой `node tools/sites-load-check.mjs`; для набора
ресурсов сцены передать JSON-файл с массивом `paths` первым аргументом. 1 октября
2026 первоначальный набор из 45 файлов занял 6,2 с через сайт и 0,8 с локально;
он включал файлы прежнего 2D-просмотра. Свежий 3D-экран содержит 34 файла и около
8,3 МБ двоичных ресурсов. У попытки Cache API все 90 запросов в двух проходах
остались промахами, а первый проход стал медленнее (7,4 с), поэтому её откатили.
Нельзя считать прохождение unit-теста доказательством работающего кэша в Sites.
API и `/generated/` продолжают каждый раз проходить проверку игрового сервера.

## Доступ и границы

Сайт доступен по общей ссылке по выбору владельца; аккаунт ChatGPT для просмотра
не требуется. Доступ к кампании защищён игровыми аккаунтами и приглашениями.
Игровой вход и приглашения кампании продолжают проверяться прежним сервером.
Сам адрес Pinggy не заменяет аутентификацию игры и не следует считать секретом.
Публичная публикационная копия `Anyukhin/skazanie` не обновляется.

Размещение успешно: сервер отвечает через HTTPS, защищённое обновление адреса
работает после принудительного переподключения, повторный запуск менеджера
не создаёт второй процесс. `pnpm verify` и проверки шлюза проходят.
Полноценный вход двух игроков, поток партии и продолжение после перезапуска
через Sites требуют групповой приёмки. Длинная партия через Sites требует
отдельной приёмки группой. Node учитывает адрес соединения в лимите попыток
входа: у пользователей шлюза лимит может быть общим. Голосовая диктовка требует
локально установленных whisper.cpp и модели, как при обычном запуске.

После обновления с PR №87 служебный отпечаток механики заклинаний приведён к
точным байтам из GitHub. Аудит приёмки больше не ссылается на два отсутствующих
тестовых файла; существующие доказательства и сценарии остаются обязательными,
сводка учитывает восемь карточек `verified` из нового ПР. Механика не изменена.
