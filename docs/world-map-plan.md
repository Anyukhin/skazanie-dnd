# План доработки карты мира

Статус: черновик, к реализации. Переработка предложения «Этап 2: карта мира и
связь с кампанией» под фактическое состояние кода.

Смежные документы: `docs/tactical-map-plan.md` (тактические карты, пересечение
отмечено в разделе 8), `docs/product-principles.md` (принципы, которым план
обязан соответствовать), `AGENTS.md` (правила работы в репозитории).

Числа и имена — на момент написания. Проверять командами, а не текстом.

## 1. Главное: карта мира уже существует

`server/world-map.mjs` (346 строк) и `src/WorldMapView.tsx` реализуют бо́льшую
часть исходного предложения. Прежде чем добавлять типы, свериться с таблицей.

| Предложено | Уже реализовано |
| --- | --- |
| `WorldBlueprint` от LLM | `prompts/campaign_creator/v1.txt` запрашивает `worldMap` схемой; результат — `opening.worldMap` |
| «LLM предлагает, алгоритм размещает» | `createCampaignWorldMap({ concept, source })`, нормализация и fallback на каждый уровень |
| `Region[]` | `WorldMapRegion`: `id`, `name`, `biome` (8 значений), `x`, `y`, `radius` |
| `WorldLocation[]` | `WorldMapLocation`: `id`, `name`, `kind` (10 значений), `x`, `y`, `regionId`, `summary`, `known`, `visited` |
| Дороги и морские пути | `WorldMapRoute`: `kind` (`road`/`trail`/`river`/`sea`/`pass`), `distance`, `danger`, `discovered` |
| Логическая сетка, не пиксели | сетка 1000×640, отрисовка по координатам |
| Подписи из данных, не с картинки | так и есть: карта рисуется векторно, изображения нет |
| Постепенное открытие | `known` / `visited` на локации, `discovered` на маршруте |
| Сохранить seed и версию | `seed`, `version` в `WorldMapState` |
| Положение группы | `worldMap.currentLocationId` |
| Расстановка без наложений | `freePosition`: минимум 68 единиц между локациями, 24 попытки |
| Путешествие занимает время | `planServerTravel` → `TravelResolved` + `AdvanceTime` |

**Вывод:** `WorldBlueprint`, `Region`, `WorldLocation` из предложения — это
переименование существующих сущностей. Вводить их как новые типы означает
создать второй мир рядом с первым. План ниже расширяет существующие.

## 2. Настоящая проблема: два параллельных мира

Путешествия реализованы в `planServerTravel`
(`server/campaign-loop-policy.mjs:220`), но работают **на текстовых названиях**,
а не на графе карты:

```js
const from = clean(state.scene?.location, 180) || 'Текущая локация'
const wilderness = /(лес|тракт|дорог|пустош|болот|гор|ущель|перевал|пещер)/iu
  .test(`${from} ${to}`)
const distanceBand = ['near', 'regional', 'far'][entropy % 3]
```

Расстояние берётся из хеша. Местность — из регулярного выражения по названию.
При этом рядом лежит `worldMap.routes` с настоящими `distance`, `kind` и
`danger`, и `worldMap.locations` с координатами и регионами. Планировщик их не
открывает.

Это два авторитетных пути к одному факту — прямо запрещено `AGENTS.md`,
раздел «Карта кода». И это же объясняет, почему события в пути сводятся к
случайному бою: планировщик не знает, через какой биом, мимо какой фракции и по
какой дороге идёт отряд, поэтому наполнить пул событий ему нечем.

**Из этого следует порядок работ: сначала свести путешествия на граф, потом всё
остальное.** Шаг 1 меньше по объёму, чем любой другой, и снимает главную боль.

## 4. Терминология и полномочия

В исходном предложении «Рассказчик» задаёт мир и «может вручную изменить
координаты, тип, доступность, маршрут». С этим две проблемы.

**Коллизия имён.** `Рассказчик` — существующая агентная роль
(`server/narrator.mjs`, `prompts/narrator/v1.txt`), которой по
`docs/product-principles.md` запрещено менять состояние: она превращает
подтверждённые события в текст и только. Роль, создающая мир, — это
`campaign_creator` (`prompts/campaign_creator/v1.txt`). В коде и документах
использовать её имя.

**Ручной редактор мира.** Продукт заявлен как кампания без человека-ведущего,
игрок должен обходиться без административного вмешательства. Редактор
координат и доступности локаций — это возвращение мастера.

Решение по умолчанию в этом плане: **редактора мира нет**. Игрок влияет на мир
через ввод при создании кампании и через игру. Если ручной режим всё же нужен,
он оформляется отдельной продуктовой задачей и записывается как осознанное
исключение из принципов, а не протаскивается внутри карты мира.

## 5. Шаги

### Ш1. Свести путешествия на граф мира

Единственный шаг, который убирает архитектурный дефект. Делать первым.

`planServerTravel` получает `state.worldMap` и берёт:

- **расстояние** — из `WorldMapRoute.distance` между текущей и целевой
  локацией, а не из хеша;
- **тип местности** — из `route.kind` и `biome` региона, через который идёт
  маршрут, а не из регулярки по названию;
- **опасность** — из `route.danger`, дополняя её нынешним `risk_score` из
  темпа и давления квестов;
- **цель** — по `locationId`, а не по текстовому названию.

Если маршрута между локациями нет — построить его тем же способом, что
`reconcileWorldMap` (там это уже сделано), либо честно вернуть «прямого пути
нет» и предложить маршрут через промежуточную локацию.

Сохранить обратную совместимость: если `worldMap` пуст или локация не найдена,
работает нынешняя текстовая ветка. Это нужно для старых кампаний.

**Проверка:** `node --test test/campaign-loop-policy.test.mjs`,
`test/autonomous-campaign.test.mjs`. Детерминизм сохраняется: тот же
`idempotency_key` даёт тот же `travel_id` и ту же длительность.

**Готово когда:** `planServerTravel` не содержит регулярных выражений по
названиям локаций, расстояние и опасность приходят из графа, старые кампании
продолжают работать.

### Ш2. Фракции

Добавить в `WorldMapState`:

```
Faction {
  id, name, kind: 'realm' | 'order' | 'guild' | 'cult' | 'clan' | 'outlaws'
  summary, homeLocationId, attitude: 'hostile' | 'wary' | 'neutral' | 'friendly'
}
```

и `factionId` на `WorldMapLocation`.

Запросить у `campaign_creator` в той же схеме, что `regions` и `locations`.
Нормализовать и подставить fallback, как это уже делается для остальных
уровней в `createCampaignWorldMap`.

Связать с существующим `server/npc-social.mjs`: у него уже есть отношения,
обещания и позиции (`friendly`/`neutral`/`guarded`/`hostile`). Фракция даёт
NPC принадлежность, а отношение к фракции — начальное отношение к NPC.

**Готово когда:** фракции приходят от LLM, нормализуются, видны на карте, у
NPC появляется принадлежность, отношение отряда к фракции меняется событиями.

### Ш3. Пулы событий в пути

Только после Ш1 и Ш2 — до них наполнять пул нечем.

Событие выбирается **сервером** по контексту: биом региона, тип маршрута,
фракция на маршруте и её отношение, состояние квестов, время суток, ресурсы и
здоровье отряда, недавние события. LLM получает выбранный тип и структурные
данные, возвращает текст и варианты.

Обязательное требование: **у каждого события есть выбор или последствие** —
изменить маршрут, потратить время или ресурсы, открыть локацию, изменить
отношение фракции, начать локальную сцену. Событие без последствия не
добавляется.

Типы для первой версии: встреча с караваном или путником, следы разыскиваемого,
просьба о помощи, препятствие на пути (мост, обвал, разлив), спор или патруль
фракции, находка, непогода, засада. Бой остаётся одним из типов, а не
единственным.

Частота и веса — серверная политика, не решение модели. Отказ LLM не должен
ломать переход: детерминированный fallback уже есть в
`campaign-loop-policy.mjs`, расширить его.

**Готово когда:** пул выбирается из контекста, доля боевых событий
настраивается, каждое событие имеет проверяемое последствие, при отсутствии
LLM путешествие завершается корректно.

### Ш4. Валидатор мира

Проверять при создании и после `reconcileWorldMap`:

- поселения и крепости не стоят в непригодном биоме;
- порты находятся у воды (регион `coast` либо маршрут `sea`/`river`);
- обязательные локации существуют и достижимы по графу маршрутов от стартовой;
- каждая посещаемая локация имеет сцену или действие;
- локации не ближе 68 единиц друг к другу (правило уже есть в `freePosition` —
  вынести в валидатор);
- каждая подпись и интерактивная зона существует в данных.

**При ошибке:** перегенерировать проблемный уровень (регион, локацию, маршрут),
затем откатиться на детерминированный fallback. Мир не должен оставаться
несозданным — это блокирует старт кампании.

**Готово когда:** валидатор вызывается на обоих путях создания мира, на каждое
правило есть тест с заведомо плохим миром.

### Ш5. Видимость и story hooks

- `mapVisibilityMode: 'fully_revealed' | 'progressive_discovery'` в
  `WorldMapState`, выбирается при создании кампании. В открытом режиме всем
  локациям ставится `known: true`.
- `storyHooks[]` и `requiredLocationIds[]` — от `campaign_creator`, участвуют в
  проверке достижимости из Ш4.

**Расширение видимости локации.** Нынешние `known` и `visited` — два булевых
поля. Предложенное `visibility: 'known' | 'hidden' | 'locked' | 'discovered'`
богаче и его стоит взять, но **через миграцию, а не заменой**:

| Было | Стало |
| --- | --- |
| `known: false` | `visibility: 'hidden'` |
| `known: true, visited: false` | `visibility: 'known'` |
| `visited: true` | `visibility: 'discovered'` |
| — | `visibility: 'locked'` — новое, для мест за квестом |

`visited` остаётся отдельным полем: «побывали» и «видно на карте» — разные
факты. Миграция в `server/migrations/`, проверка на replay обязательна.

## 6. Положение группы и маршрут

Сейчас положение — `worldMap.currentLocationId`. Предложенный
`PartyTravelState` с `route[]`, `destinationId` и `travelState` нужен только
если путешествие становится процессом с промежуточными точками, где отряд может
остановиться, повернуть назад или быть перехвачен.

Решение: **не вводить на Ш1**. Путешествие остаётся атомарным переходом с
расходом времени. `PartyTravelState` добавляется на Ш3, когда события в пути
получат выбор «изменить маршрут» — до этого поля будут пустыми.

Пиксельные координаты для игровой логики не использовать: сетка 1000×640
логическая, изображение — проекция. Это правило уже соблюдается.

## 7. Фоновое изображение карты

Генерация изображений в проекте **есть**, но не там, где её искали: не в
`server/llm-client.mjs`, а в `server/index.mjs` — функция `generateItemImage`
ходит в `${ROUTERAI_BASE_URL}/images` моделью из `DND_IMAGE_MODEL`
(по умолчанию `openai/gpt-image-1`) и сохраняет webp в
`storage/generated/items`. Сейчас её вызывает только маршрут генерации картинок
предметов инвентаря. Проверено 2026-07-26.

Ограничение не в коде, а в настройке: в рабочем `.env` **нет
`ROUTERAI_API_KEY`**, поэтому этот путь не выполняется.

Прежде чем строить на ней, учесть то же, что в `docs/tactical-map-plan.md`:

- изображение недетерминировано, значит его нельзя перегенерировать при replay
  — только хранить как ассет с фиксированным идентификатором;
- карта обязана оставаться играбельной без изображения;
- подписи, значки и интерактивные зоны накладываются программно из данных —
  это в исходном предложении сказано верно и должно остаться правилом.

Сейчас карта рисуется векторно по данным и это работает. Рекомендация:
**отложить**, вернуться после того, как закроются Ш1–Ш4.

## 8. Пересечение с тактическими картами

Проверка достижимости обязательных точек по графу (Ш4) — тот же механизм, что
стадия 1 генератора в `docs/tactical-map-plan.md`, раздел 8: сначала граф зон и
проверка ключей, потом геометрия. Написать один раз и переиспользовать, а не
дважды.

Остальные шаги не пересекаются: Ш1 и Ш2 можно вести параллельно работам по
тактическим картам, они трогают разные файлы.

Связь мира и локальной сцены уже есть: `state.locationMaps` хранит карту по
`locationId`, `stableLocationMapSeed` даёт устойчивый seed, повторный вход
возвращает ту же карту. Отдельный `sceneBinding` из предложения дублировал бы
этот механизм — не вводить.
