# План технических работ по стеку

Документ написан для исполнения агентом. Каждая задача самодостаточна: цель,
шаги, проверка, критерий готовности. Задачи выполняются **по одной**, в порядке
номеров, каждая завершается отдельным коммитом.

Контекст: личный проект для игры с друзьями. Отсюда приоритеты — сначала то,
что снижает трение при разработке, а не то, что готовит к нагрузке.

Перед началом любой задачи прочитать `AGENTS.md`. Правила оттуда действуют
без исключений: сервер на `.mjs`, тесты `node:test`, финальный gate
`pnpm verify`, не трогать `storage/` и `.env`.

**Числа в этом документе — ориентиры на момент написания, а не истина.**
Размеры файлов, версии в локе и количество маршрутов проверять командами из
задач, а не доверять цифрам из текста.

---

## Вердикт по стеку

Стек менять не нужно. Оставить как есть: голый `node:http` без фреймворка,
React + TypeScript + Vite на клиенте, `node:test`, event sourcing, файловое
хранилище, pnpm.

**Явно не делать** (перечислено, чтобы не возвращаться к вопросу):

- не переезжать на Next.js, NestJS, Express, Fastify;
- не вводить Prisma, Postgres, MongoDB;
- не менять тест-раннер;
- не переписывать клиент;
- не переводить `server/` на `.ts` целиком (см. задачу 3 — там другой путь).

Отложено с явным триггером возврата — задача 7.

## Задача 1. Прижать версии зависимостей

**Приоритет: сделать первой.** Занимает минуты, устраняет невоспроизводимость
сборки.

**Проблема.** В `package.json` все зависимости указаны как `latest`. Лок-файл
пока удерживает установку, но любое его обновление может молча притащить
мажорную версию React или Vite и сломать сборку.

**Шаги.**

1. Прочитать фактические версии из `pnpm-lock.yaml` (не из `node_modules` —
   pnpm хранит пакеты в стороне).
2. Заменить в `package.json` каждое `"latest"` на диапазон вида `^X.Y.Z` с
   установленной версией.

   На момент написания в локе: `react` и `react-dom` 19.2.7, `vite` 8.1.4,
   `typescript` 7.0.2, `dotenv` 17.4.2, `lucide-react` 1.24.0. Версии
   `@vitejs/plugin-react`, `@types/react`, `@types/react-dom` взять из лока
   тем же способом. **Если версии в локе отличаются — брать из лока, а не
   отсюда.**

3. Выполнить `pnpm install --frozen-lockfile` и убедиться, что лок не изменился.

**Проверка.**

```bash
pnpm install --frozen-lockfile
git diff --exit-code pnpm-lock.yaml   # лок не должен измениться
pnpm verify
```

**Готово когда:** в `package.json` нет ни одного `"latest"`, лок-файл не
изменился, `pnpm verify` проходит.

## Задача 2. Убрать мёртвый код и разобраться с промптами

**Проблема.** В репозитории лежат файлы, на которые никто не ссылается. Они
выглядят рабочими и вводят в заблуждение — и человека, и агента.

**Что удалить** (проверено: ссылок из кода и инструментов нет):

- `server/index.mjs.orig`
- `prompts/director/v1.txt.orig`
- девять файлов `.codex-*.patch` в корне
- пустые каталоги `.agents/` и `prompts/legacy/`

**Что разобрать отдельно — промпты без потребителя.** Ни один модуль не
загружает:

- `prompts/adjudicator/v1.txt`
- `prompts/intent_parser/v1.txt`
- `prompts/verifier/v1.txt`
- `prompts/worldkeeper/v1.txt` — ссылка была только из мёртвого `index.mjs.orig`
- `prompts/game_master/v1.txt` — то же

Правка этих файлов сейчас не меняет поведение системы.

**Действие:** не удалять молча. Для каждого выяснить, читая
`server/agent-router.mjs` и соответствующие модули, что предполагалось:

- если роль реализована детерминированно и промпт не нужен — удалить файл и
  убрать `prompt_id` из `AGENT_ROLES`;
- если роль планировалась, но не подключена — оставить файл и добавить строку
  в `docs/known-limitations.md`, что контракт объявлен, но не исполняется.

**Проверка.**

```bash
grep -rn "index.mjs.orig\|codex-" server/ tools/ src/ package.json   # пусто
pnpm verify
pnpm content:verify
```

**Готово когда:** мёртвые файлы удалены, по каждому промпту без потребителя
принято и записано решение, `pnpm verify` и `pnpm content:verify` проходят.

## Задача 3. Включить проверку типов на сервере через JSDoc

**Это главная задача плана.** Около 27 500 строк серверной логики, включая
`rules-engine.mjs` на 7 100+ строк, не проверяются типами, при том что клиент
на TypeScript.

**Почему не переписывать на `.ts`.** Миграция 64 файлов — большой риск для
replay и сохранённых кампаний при неочевидной выгоде. JSDoc с `checkJs` даёт
проверку типов **без единого изменения в рантайме** и подключается файл за
файлом.

### Шаг 3.1. Инфраструктура

1. Создать `tsconfig.server.json`:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022"],
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "allowJs": true,
    "checkJs": true,
    "noEmit": true,
    "strict": true,
    "skipLibCheck": true,
    "resolveJsonModule": true
  },
  "include": []
}
```

`"include": []` — намеренно пустой. Файлы добавляются по одному, чтобы
проверка типов **никогда не была красной**.

2. Добавить путь в `references` в `tsconfig.json`.
3. Добавить скрипт `"typecheck:server": "tsc --noEmit -p tsconfig.server.json"`.
4. Включить его в `verify`: `"verify": "pnpm test && pnpm typecheck:server && pnpm build"`.

**Проверка шага:** `pnpm verify` проходит (проверять пока нечего — это норма).

### Шаг 3.2. Первые файлы

Подключать в этом порядке, по одному файлу за раз, добавляя его в `include`:

1. `server/contracts.mjs` — здесь описаны контракты, польза максимальна;
2. схемы событий и команд — те места, откуда `rules-engine.mjs` берёт формы;
3. `server/dice-service.mjs` и `server/roll-registry.mjs` — небольшие и
   критичные;
4. `server/event-store.mjs`;
5. `server/viewer-projection.mjs` и `server/security.mjs`.

Для каждого файла: добавить в `include` → прогнать `pnpm typecheck:server` →
расставить JSDoc-типы (`@typedef`, `@param`, `@returns`) до зелёного →
`pnpm verify` → коммит.

**Правило:** если файл требует правок рантайма, чтобы пройти проверку типов —
остановиться и вынести это отдельной задачей. Задача 3 не меняет поведение.

### Шаг 3.3. Остальное — фоном

`rules-engine.mjs` и `index.mjs` подключать **после** задач 4 и 5, когда они
разбиты на модули. Целиком 7 000 строк за раз не типизировать.

**Готово когда:** `pnpm typecheck:server` в составе `pnpm verify`, в `include`
не меньше шести файлов, поведение не изменилось (все тесты зелёные без правок
самих тестов).

## Задача 4. Разнести `server/index.mjs`

**Проблема.** Более 2 800 строк: HTTP-сервер, раздача статики, маршруты, SSE и
вся обвязка в одном файле. Это же единственный модуль, импортирующий
`llm-client.mjs`.

**Важно.** Это перенос кода, а не переработка. Поведение, порядок проверок и
формы ответов не меняются.

**Шаги.**

1. Составить список маршрутов. В файле сосуществуют **три** идиомы, искать надо
   все, иначе часть маршрутов потеряется:

```bash
grep -n "req\.url ===" server/index.mjs              # точные совпадения пути
grep -n "parsedUrl\.pathname ===" server/index.mjs   # то же, другая идиома
grep -n "pathname\.match(" server/index.mjs          # сегментные, /campaigns/:id/...
```

   Суммарно порядка тридцати веток. Точное число получить этими командами.

   Заодно это повод привести маршрутизацию к одной идиоме — но **отдельным
   коммитом после переноса**, не вперемешку с ним.

2. Сгруппировать по областям: `auth`, `campaigns`, `commands`, `narrate`,
   `merchant`, `encounter`, `admin`, `sse`, `static`.
3. Создать `server/routes/` и вынести по модулю на группу. Каждый экспортирует
   функцию вида `(req, res, ctx) => boolean | Promise<boolean>`, где `ctx` —
   уже собранные зависимости (store, engine, orchestrator, llmClient).
4. В `index.mjs` оставить: создание сервера, сборку `ctx`, список групп,
   раздачу статики, обработку ошибок.
5. `llm-client.mjs` по-прежнему импортируется **только** в одном месте — там,
   где собирается `ctx`. Не растаскивать по модулям маршрутов.

**Проверка.** После каждой вынесенной группы:

```bash
node --test test/api-integration.test.mjs test/mvp-player-cycle-api.test.mjs
pnpm verify
```

**Готово когда:** `index.mjs` меньше 400 строк, все тесты проходят без правок,
ручной сценарий с двумя игроками работает.

## Задача 5. Разнести `src/App.tsx`

**Проблема.** 2 127 строк, рядом `useGameSession.ts` на 1 181.

**Шаги.**

1. Выделить в отдельные компоненты по областям экрана: тактическая доска,
   журнал, панель действий, лист персонажа, хотбар.
2. Разбить `useGameSession.ts` по областям состояния: сессия и подключение,
   боевое состояние, инвентарь и торговля.
3. Состояние оставить на React-хуках. **Не вводить zustand, redux, jotai** —
   объём не требует, а зависимость останется навсегда.

**Проверка.**

```bash
pnpm build
```

плюс ручной проход основного сценария с двумя игроками.

**Готово когда:** ни один файл в `src/` не больше 600 строк, `pnpm build`
проходит, интерфейс ведёт себя как прежде.

## Задача 7. SQLite — отложено

**Сейчас не делать.** Для личной игры с друзьями файловое хранилище и
блокировка через `.commit.lock` работают нормально.

**Триггеры возврата** — любой из:

- понадобился второй процесс сервера;
- снимки состояния начали мешать по размеру (см. раздел 11 в
  `docs/tactical-map-plan.md`: карты 100×100 дают до 21.5 МБ на кампанию);
- появились заметные задержки на записи при нескольких активных кампаниях.

**Когда вернётесь:** брать `better-sqlite3`, а не встроенный `node:sqlite` —
последний в Node 22 помечен экспериментальным. Менять только реализацию за
интерфейсом `FileEventStore`, схема — append-only таблица событий плюс таблица
снимков. Postgres не рассматривать.

выполнения требуется изменить механику, состояние или схему событий — это
отдельная задача, и её нужно согласовать с пользователем.
