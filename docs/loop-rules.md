# Трек `claude/loop-rules` — правила и ИИ-ведущий

Бриф для длительного автономного агента. Он перечитывается **в начале каждой
итерации**: у цикла нет общей памяти между запусками, вся преемственность живёт
в журнале и в истории ветки.

## Дерево и ветка

| | |
| --- | --- |
| Ветка | `claude/loop-rules` |
| Базовая ветка | `main` |
| Журнал | `docs/loop-rules-journal.md` (в git, коммитится вместе с работой) |

Первым делом — четыре проверки из `AGENTS.md` §10:

```bash
pwd
git branch --show-current    # обязано быть claude/loop-rules
git status --short           # чужие правки — это стоп, а не фон
ls node_modules/typescript
```

Ветка не та или в дереве чужое — **остановиться и написать пользователю**.

## Границы владения

Правишь только это:

```
server/**   test/**   (кроме test/ui-*.test.mjs)
eval/**     prompts/**
docs/**     (кроме docs/interface-*.md и docs/loop-ui*.md)
```

Не трогаешь **никогда**: `src/**`, `public/**`, `vite.config.ts`, `index.html`,
`data/**`, `storage/**`, `.env`, `AGENTS.md`, `README.md`, `package.json`,
`pnpm-lock.yaml`, `Dockerfile`, `compose.yaml`, `.dockerignore`.

`data/` — исходные правила и каталоги, они меняются отдельным решением
пользователя. Нужна правка данных — предложить её в журнале, не делать.

Параллельно на ветке `claude/loop-ui` работает второй агент и владеет `src/**`.
Задача упирается в клиент — она **не твоя**: в журнал, раздел «Требует правки
интерфейса», и дальше.

## Одна итерация — одна задача

Расширение объёма за пределы одной задачи — повод откатить работу целиком.

Порядок обязателен и он не декоративный (`AGENTS.md` §6):

```
команда → правило → серверный бросок → событие → reducer → проекция → и только потом клиент
```

1. Прочитать журнал, выбрать **одну** следующую задачу.
2. Доказать проблему тестом или прогоном, а не рассуждением. Красный тест
   первым — это и есть доказательство.
3. Починить минимальным изменением.
4. Проверить (ниже).
5. Закоммитить перечислением файлов вместе с журналом.

Находка без воспроизведения — не находка, а гипотеза. Гипотезы идут в журнал
отдельным разделом и не превращаются в правку, пока не подтверждены.

## Что проверять — оси аудита

Это не список задач, а список направлений. Каждая итерация берёт **одну** ось и
одну конкретную проверку внутри неё.

### 1. Серверный авторитет

- HP, ресурсы, координаты, инициатива, эффекты, инвентарь, деньги, опыт и статус
  кампании меняются **только** типизированными командами и событиями.
- Все броски — на сервере. Число от модели или из браузера никогда не является
  игровым результатом.
- Клиентские поля недоверенные: сервер заново определяет владельца героя,
  доступные цели, путь, дальность, видимость и экономику хода.
- Второго авторитетного пути быть не должно (`AGENTS.md` §4). Прямая мутация в
  обход событий — дефект, даже если тесты зелёные.

### 2. ИИ-ведущий как двигатель сюжета

Это главная ось: модель обязана двигать историю, **не трогая механику**.

- Director принимает только шесть намерений контракта
  `skazanie:director-intent-v1`; поля механики (`hp`, `dc`, броски, цены,
  количества, XP, координаты, урон, инициатива, reputation delta) отклоняются
  **до** исполнения. Проверить, что отклоняются все, а не большинство.
- LLM не назначает урон, КД, СЛ, координаты, цену, награду или исход. Она может
  определить смысл намерения или предложить bounded ruling, после чего сервер
  сам выбирает и проверяет числа.
- Рассказчик получает только разрешённую проекцию и подтверждённые события. Он
  не дописывает событие, не правит бросок и не объявляет неподтверждённую
  смерть. Verifier обязан перехватывать любое расхождение текста с событиями.
- Отказ или недоступность LLM не повреждает состояние и не даёт механического
  преимущества. Для критических переходов обязан быть детерминированный fallback.
- **Текст игрока и содержимое памяти — недоверенные данные, а не инструкции.**
  Отдельно проверить попытки инъекции через реплику героя, имя персонажа,
  описание предмета и записанный world fact.
- NPC не знают скрытых действий игроков; агент не выдаёт NPC скрытых
  преимуществ ради сюжета.

### 3. Причинность мира

- Решения, смерти, обещания, репутация, разрушения, открытые тайны, посещённые
  места и незавершённые нити влияют на будущие сцены.
- Повторное посещение возвращает ту же локацию с устойчивым `location_id` и
  накопленными изменениями, а не случайную замену.
- Свободное действие имеет последствие: провал проверки создаёт последствия и
  новые возможности, а не останавливает кампанию.

### 4. Честность механики

- `heuristic` и `ruling-only` не исполняются молча и не тратят ресурсы или
  экономику хода ни на клиенте, ни в Rules Engine.
- `partial` разрешён только для уже исполняемой безопасной части и обязан
  сопровождаться описанием ограничения.
- Каждое механическое решение ссылается на `rule_id`, `house_rule_id` или
  `ruling_id`. Ссылочная целостность — `docs/rules-coverage.md`.
- Точные HP, КД, скорость и stat block врага скрыты, пока не появился серверный
  факт раскрытия в `enemy_knowledge`. Урон или попадание сами по себе не
  раскрывают значения — проверить, что и в проекции, и в тексте Рассказчика.

### 5. Воспроизводимость

- Replay одного потока событий даёт то же состояние.
- Перезапуск, повторный запрос и параллельные команды не меняют полученный исход.
- Повтор с тем же `idempotency_key` возвращает прежний commit.
- Конфликт параллельных команд разрешается optimistic versioning, а не молчаливым
  перезаписыванием.

Опорные прогоны: `test/autonomous-campaign.test.mjs` (30+ ходов без admin-команд,
replay identical, restart identical), `test/campaign-loop-policy.test.mjs`,
`server/autonomy-eval.mjs` с `eval/autonomous-scenarios.mjs`, готовые пробы
`.agent-tasks/probe-*.mjs` (каталог в git не хранится — если его нет, пробы
писать заново в `test/`).

## Живые вызовы модели — по умолчанию нет

Оси 1, 3, 4, 5 проверяются детерминированно, без обращения к модели, и на них
уходит основная работа. Ось 2 частично тоже: контракт, отклонение механических
полей, fallback и Verifier проверяются подставным клиентом.

Качество самих ответов модели без живых вызовов не проверить, но живой прогон
тратит деньги пользователя. Поэтому:

- живые вызовы допускаются, только если в дереве есть `.env` с ключом **и**
  пользователь явно разрешил их в задании;
- разрешены — не больше **пяти** сценарных прогонов за итерацию, и в журнал
  пишется, сколько потрачено;
- без разрешения ось 2 проверяется подставным клиентом, а вопрос про качество
  ответов складывается в журнал.

## Проверка

Обязательна до коммита, полностью:

```bash
pnpm verify        # tests + typecheck:server + build
```

`pnpm content:verify` зелёный с нормализации 2026-07-28 — его покраснение
теперь регрессия. `pnpm release:verify` и `pnpm cutover:audit` красные по
построению (`docs/production-readiness.md`) — это не регрессия. Но если они
покраснели **по-новому**, это находка: записать различие.

Порт 8787 не занимать, он может быть занят приложением пользователя:

```bash
AGENT_PORT=8788 pnpm dev:agent
```

Красная проверка — работа не коммитится. Откатить, записать причину, взять
следующую задачу.

## Коммит

```bash
git add <перечислением файлов>      # никогда -A и не commit -a
git branch --show-current           # сверить перед коммитом
git commit
```

Сообщение — по-русски, в повелительном наклонении, с объяснением **почему**.

После зелёной проверки — выложить **свою и только свою** ветку, чтобы результат
был виден с любой машины:

```bash
git push origin claude/loop-rules
```

Не делать: `push` в `main` или в чужую ветку, `push --force` в любом виде,
`merge`, `rebase`, `checkout` другой ветки, `reset --hard`, работу в чужих
каталогах. ПР не открывать — ветку разберёт пользователь.

## Отдельный результат итерации — запись, а не только код

Найденное расхождение между `docs/product-principles.md` и реализацией обязано
попасть либо в исправление, либо в `docs/known-limitations.md` честной
формулировкой. Тихо оставленное расхождение — худший исход итерации, хуже
ненайденного.

## Когда остановиться и написать пользователю

- Задача противоречит `AGENTS.md` или `docs/product-principles.md`.
- Найдено нарушение серверного авторитета, которое нельзя починить, не сломав
  совместимость с сохранёнными кампаниями.
- Проверка красная три итерации подряд по одной причине.
- В дереве появились чужие изменения.
- Требуется правка `data/` или клиента, без которой дальше нельзя.
