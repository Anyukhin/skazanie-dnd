# Сказание

Русскоязычный MVP кооперативной настольной RPG с виртуальным ведущим, общей историей и тактической картой. Вся игровая механика работает через один серверно-авторитетный контур: команды → события → reducer → снимки состояния → проверенное повествование. К нему подключены тактический цикл, событийная смена сцены, EncounterAssembler и торговля с серверными ценами, кошельком, складом и торгом; это всё ещё частичный срез, а не полная реализация D&D.

Ведущий поддерживает непрерывную кампанию без заранее записанного маршрута: агент создаёт только исходную ситуацию, а следующие главы возникают из подтверждённых решений игроков. При переходе агент-картограф получает публичный контекст сеттинга, героев и видимых врагов, выбирает физический масштаб, планировку и материал новой карты. Подтверждённое групповое решение превращается в системную команду `AdvanceScene` и событие `SceneAdvanced`: reducer переносит группу ко входу, очищает прежний encounter и сохраняет историю глав, посещённые места и незавершённые нити в `state.adventure`. Для распознанного поселения Директор одновременно запрашивает `ShopAssembler`; новая лавка создаётся событием `MerchantCreated` в том же commit, а повторный вход в уже известную строку локации использует существующего торговца без сброса stock. Решение группы имеет устойчивую ссылку `interaction_id + resolved_option_id`, исполняется ровно один раз даже при параллельных запросах, а повтор победившего idempotency key читается из committed events без нового вызова картографа/модели.

## Команда ИИ-ведущего

Ведущий разделён на четыре роли с отдельными версионированными инструкциями:

- **Хранитель мира** отвечает на вопросы о лоре только из видимой памяти кампании, истории глав и посещённых мест. Он не получает инструменты изменения мира, а вопрос не расходует действие.
- **Режиссёр** управляет темпом, развилками, групповыми решениями и переходами. Он может открыть голосование, предложить общий бросок судьбы или карточку выбора, а после принятого решения вызвать смену сцены.
- **Арбитр правил** подбирает правила из закреплённого русско-английского Rule Pack, назначает проверки и использует только серверные броски с `roll_id`/`check_id`.
- **Рассказчик** превращает уже подтверждённые результаты и события в художественный русский текст, но не меняет состояние напрямую.

Маршрутизатор выбирает роль по намерению игрока. Вопросы о лоре, открытие голосования и сам голос бесплатны. Проверка расходует действие только после подтверждённого броска, а реальная смена мира или локации завершает ход. Для решений, затрагивающих весь отряд, агент использует `request_party_decision`: большинство для маршрута, общий d20 для доверия судьбе и явный выбор для необратимых последствий. Принятое решение передаётся Режиссёру, который связывает исход старой главы с новой целью, картой и сюжетным крючком.
Длительные опасности среды записываются инструментом `apply_hazard` и сохраняются сервером между ходами. `resolve_hazard` снимает состояние с обязательной проверкой только после серверного броска с закреплённой характеристикой и достаточной СЛ; реплика игрока сама по себе опасность не отменяет.

Контракты ролей находятся в `prompts/worldkeeper/v1.txt`, `prompts/director/v1.txt`, `prompts/game_master/v1.txt` и `prompts/narrator/v1.txt`. Контекст передаётся им как недоверенные данные, отделённые от системной инструкции.

### Политика творческих вызовов

Обычные перемещения, атаки, магия, торговля, инициатива и стандартные ходы NPC не вызывают LLM: их полностью исполняет единый серверный движок. Агент подключается только там, где нужна новая творческая информация:

- создание открытой исходной ситуации кампании без заранее определённых будущих сцен и финала;
- проектирование каждой новой области с учётом масштаба места, сеттинга, героев и противников;
- перелом боя: смерть участника, а также одно решение морали тяжело раненого врага — продолжать бой, бежать или сдаться;
- свободное нестандартное действие, для которого действительно нужен Арбитр или Режиссёр.

Модель никогда не исполняет координаты, урон или команды напрямую. Даже бегство рассчитывается сервером как допустимый путь, а художественная реплика создаётся только после committed event.

## Что работает

- игровая комната с четырьмя героями, журналом, картой, туманом войны, инвентарём и редактором листа;
- аккаунты, `scrypt`-хеши паролей и HttpOnly-сессии; назначенный герой открывает кампанию, а действия от имени персонажа ограничены владельцем или администратором;
- RouterAI-рассказчик с локальным fallback и строго разрешёнными инструментами;
- один серверно-авторитетный движок для новых и загруженных кампаний, без переключателя режима в интерфейсе;
- серверные броски с `roll_id`/`check_id`, сроком действия, привязкой к кампании и защитой от повторного применения;
- частичный Rule Pack/Rules Engine: 14 правил формализованы детерминированно, ещё 7 структурированы частично; состояния, концентрация, ноль HP и отдых пока включают marker-only/упрощённые части;
- append-only event store, optimistic locking, idempotency keys, snapshots и replay;
- server-authoritative переход сцены: `AdvanceScene`/`SceneAdvanced` сохраняет новую карту, adventure history и позиции отряда, а bounded `scene_commerce` при входе в поселение может атомарно добавить каталожного торговца через `ShopAssembler`;
- единая player projection для room/command/narrate: private/GM memory, внутренние параметры торговца и особенности нераскрытых клеток не попадают в браузер, а Scene Architect получает отдельный public planning brief;
- BG3-подобные стадии карты: в исследовании выбранный герой свободно идёт к любой открытой достижимой клетке; при начале боя сервер бросает d20 инициативы для каждого участника, показывает `d20 + модификатор = итог` и включает пошаговый лимит скорости;
- server-authoritative combat slice: перемещение, ближние и дальние атаки, выбор оружия из инвентаря, смена экипировки, траектория с проверкой стен, normal/long range с помехой, метательные области и расход предметов; автобросок атаки можно отключить ради отдельной кнопки d20;
- BG3-подобная нижняя панель действий с экономикой хода, книгой заклинаний, поиском/фильтром по кругу и закреплением до 24 заклинаний; серверный каталог охватывает 439 карточек dnd.su уровней 0–6, 12 базовых классов, 114 официальных подклассов и 340 активируемых классовых кандидатов до 12-го уровня;
- поверх автоматически собранного каталога действует проверенный слой механик dnd.su: 79 боевых карточек (реакции, боевые заговоры и ключевые заклинания 1-го круга) имеют точные цели, спасброски, типы урона, состояния и краткие правила вместо эвристических догадок; среди отдельно разрешаемых сервером механик уже есть Волшебная стрела, Доспех Агатиса, Bless/Bane, Усыпление, защитные чары, наземные области, направленные конусы и кубы, принудительное перемещение, повторные спасброски, Жуткий смех Таши, Очарование личности, Вызов на дуэль, пять вариантов Приказа, кары паладина, Опутывающий удар, Град шипов, Удар Зефира, Героизм и Поспешное отступление; слой продолжает расширяться по кругам;
- лист персонажа включает конструктор развития: класс и подкласс открываются на соответствующем уровне, умения показываются по прогрессии, а известные/подготовленные заклинания выбираются поиском с классовыми лимитами;
- реакции вынесены из обычного хотбара в прерывающее окно: сервер приостанавливает автоматический ход противника, проверяет владельца и доступный ресурс, поддерживает отказ, атаки по возможности, Парирование, Ответный удар, Невероятное уклонение, Щит, Поглощение стихий, Адское возмездие, Искусную остроту и Контрзаклинание; Искусная острота позволяет выбрать союзника для преимущества, Щит работает и против атакующих заклинаний, а Контрзаклинание прерывает применение до разрешения его эффектов;
- общий движок боевой магии обрабатывает атаки, спасброски, дружественный огонь в областях, лечение, состояния, концентрацию, призыв, телепортацию, масштабирование заговоров и автоматический выбор ячейки повышенного круга;
- боевая магия на основной доске: server-owned spell profiles, атака/спасбросок/лечение, отдельное бонусное действие, ячейки и концентрация; `summon-beast` создаёт управляемого помощника с собственной фишкой и ходом сразу после владельца;
- карты семи базовых типов (`rooms`, `streets`, `open`, `winding`, `cavern`, `ruins`, `radial`) и девяти планировочных наборов (`small-room`, `great-hall`, `keep`, `courtyard`, `crypt`, `cave-cluster`, `village`, `bridge`, `natural`) с масштабами от комнаты до крепости, неровными силуэтами, связанными проходами и проверкой линии выстрела; клетки получают top-down материал и вариации камня, дерева, земли, травы, песка, металла, мрамора или льда;
- административный EncounterAssembler: UI/API принимают только ограниченные сложность `easy|medium|hard` и тему `generic|goblinoids|undead|beasts|raiders`, считают официальный XP budget SRD 5.2.1 по уровням 1–20 и выбирают противников из 12 server-owned профилей; враги размещаются только на раскрытых достижимых клетках не ближе 10 футов от героев, а `EncounterCreated` и `CombatStarted` входят в один event commit;
- общий initiative order для героев, врагов и призывов, детерминированный NPC scheduler до следующего управляемого участника, одно bounded-решение морали при 30% ОЗ и автоматическое завершение боя при поражении, бегстве или сдаче одной стороны;
- системный боевой журнал обычных действий без LLM и творческая реплика Рассказчика только для committed переломного события; оба сохраняются после reload/restart;
- меню торговца в текущей локации: покупка, продажа, серверная оценка нестандартного предмета и одна проверка торга; UI показывает кассу торговца и итог `цена за единицу × количество`, базовые цены берутся из небольшого versioned SRD-каталога либо из versioned server appraisal policy, а деньги героя, касса NPC, предметы и stock изменяются одним идемпотентным event commit;
- Rule Pack `srd_5_2_1` с русско-английским глоссарием, provenance metadata, ontology edges и гибридным поиском по русским формам, опечаткам и смешанным запросам;
- разделённые роли `IntentParser`, `Adjudicator`, `Narrator` и `Verifier`; модель предлагает структурированный результат, но не записывает состояние напрямую;
- turn traces с редактированием секретов и объяснение решения через `/why` или explanation API;
- совместимые старые API-поля и контролируемая проекция авторитетной механики обратно в legacy room.

## Единый движок

Глобальный default задаётся в `.env`:

```env
GAME_ENGINE_MODE=enforce
DND_DEFAULT_RULESET_ID=srd_5_2_1
DND_DEFAULT_RULESET_VERSION=5.2.1
```

`enforce` — единственный пользовательский режим. Валидированные команды и события являются источником истины для механики, после чего результат проецируется в совместимый формат ответа и комнаты. Старые значения `legacy` и `shadow` распознаются только внутренним слоем совместимости при чтении прежних данных; загруженное состояние нормализуется в `enforce`, а переключателя режима в интерфейсе нет.

Торговля остаётся vertical slice, но lifecycle торговца уже событийный: административный/агентный контур умеет создать, настроить, пополнить, переместить, открыть и закрыть магазин, а `purse_cp` ограничивает реальную сумму выкупа. Детерминированный `ShopAssembler` собирает лавку и стартовую кассу только из server-owned каталога и ограниченной policy; Директор автоматически включает его в атомарный переход к распознанному поселению. `AppraiseItem` создаёт серверную event-sourced аттестацию для нестандартного предмета по категории, редкости и состоянию, не принимая цену от клиента или агента. Сейчас повторное использование лавки определяется сравнением нормализованной строки локации, а не устойчивым `location_id`; групповое голосование до перехода всё ещё хранится в compatibility-room. Также нет полного каталога, electrum, услуг/полноценного диалога, репутации, supply/demand, автоматических restock clocks и полной derivation Persuasion proficiency/expertise из листа персонажа.

EncounterAssembler также остаётся ограниченным vertical slice. Его mini-compendium содержит 12 профилей с локальными миниатюрами, несколькими видами атак и исполняемыми особенностями: тактикой стаи, ловким отступлением, агрессивным рывком, воинским преимуществом, внезапной атакой, стойкостью нежити, ядом, сбиванием с ног и паутиной. Это всё ещё не полный набор stat blocks: нет полной поддержки saves/skills, resistances/immunities, multiattack, spellcasting, legendary/lair actions и recharge-механик. Создание встречи пока запускается вручную администратором, а не автоматически Директором; отсутствуют loot/rewards и realtime multi-browser синхронизация.

## Локальный запуск

Нужны Node.js `>=20.19.0` и pnpm.

```bash
pnpm install
pnpm dev
```

Vite покажет адрес интерфейса. При первом запуске задайте одноразовый `ADMIN_SETUP_TOKEN` или используйте Windows-лаунчер, который создаёт его автоматически. Обычные игроки регистрируются сами, затем администратор назначает им героев в разделе управления миром.

Настройка RouterAI остаётся серверной:

```env
ROUTERAI_API_KEY=...
ROUTERAI_BASE_URL=https://routerai.ru/api/v1
DND_AI_MODEL=anthropic/claude-haiku-4.5
DND_IMAGE_MODEL=openai/gpt-image-1
```

Ключ не передаётся браузеру. Детерминированная механика и безопасный fallback доступны и без ключа RouterAI.

## Проверка проекта

```bash
pnpm test
pnpm build
pnpm rules:verify
pnpm test:coverage
```

Тесты используют временные каталоги и не должны изменять рабочий `storage`. Актуальный suite покрывает reducer/replay, броски, P0-механику, idempotency и version conflicts, миграцию, Rule Pack/retrieval, границы LLM, security/verifier и traces. Отдельный domain integration flow проходит исследование, social ruling, проверки, магию, бой до явного `EndCombat`, лечение, состояние, отдых, restart/replay и `/why`. Real-HTTP сценарии проверяют совместимый API, авторитетный боевой цикл, административную сборку встречи, торговлю обычного игрока и связку Director → `SceneAdvanced` → `ShopAssembler`: forged stat blocks/координаты/participants и forged параметры/цены/системные команды, ownership/location, stale quote, торг, `AppraiseItem`, ограниченную кассу, buy/sell, атомарные `EncounterCreated + CombatStarted` и создание лавки, player visibility projection, долговечный журнал, идемпотентный event replay и replay после перезапуска процесса. Актуальный общий gate запускается командой `pnpm verify`.

## Миграция существующих кампаний

Сначала остановите запись, сделайте полную резервную копию `storage` вне дерева проекта и подтвердите редакцию правил кампании. Затем выполните только dry-run:

```bash
pnpm migrate:dry-run
```

Записывающая миграция запускается отдельно и создаёт byte-for-byte `.bak` перед изменением room JSON:

```bash
pnpm migrate
```

Она добавляет metadata. Новая кампания импортируется в event store при создании; существующая — идемпотентно при первом обращении к авторитетной механике. Перед использованием старой кампании нужны replay-сверка и проверка проекции. Полная процедура, критерии остановки и rollback описаны в [руководстве по миграции](docs/migration-guide.md).

## Основные API

- `GET /api/health` — provider, модель, режим, ruleset и инструменты;
- `POST /api/roll` — одноразовый серверный roll artifact; modifier/DC закреплены сервером только для выданного сервером `check_id`;
- `POST /api/narrate` — обратно совместимый ход; в `enforce` возвращает также события, версию и trace metadata, а подтверждённое решение группы о переходе может атомарно создать `SceneAdvanced` и `MerchantCreated`;
- `GET /api/rules/search?q=...&ruleset_id=...` — поиск только внутри разрешённого ruleset/pack;
- `POST /api/campaigns` — создание кампании администратором;
- `PATCH /api/campaigns/:id/engine-mode` — совместимый старый endpoint; всегда сохраняет единый режим `enforce`;
- `POST /api/campaigns/:id/commands` — typed commands: обычному игроку доступны безопасный combat set и `BargainWithMerchant`/`AppraiseItem`/`BuyItem`/`SellItem` от имени назначенного героя; администратору доступен расширенный диагностический набор;
- `POST /api/campaigns/:id/encounters/assemble` — admin-only сборка и немедленный старт встречи; принимает `difficulty`, `theme`, `expected_state_version` и idempotency key, но не принимает stat block, XP, участников или координаты противников;
- `GET /api/campaigns/:id/merchants/:merchantId?actor_id=...` — публичная витрина и серверные котировки для назначенного героя;
- `POST /api/campaigns/:id/merchants/:merchantId/commands` — `BargainWithMerchant`, `AppraiseItem`, `BuyItem` или `SellItem` с idempotency key и версией просмотренной котировки; для оценки клиент передаёт только `item_id`, не цену или policy;
- `POST /api/campaigns/:id/merchants/commands` — admin-only event-sourced `CreateMerchant`, `ConfigureMerchant`, `RestockMerchant`, `MoveMerchant`, `SetMerchantAvailability`;
- `POST /api/campaigns/:id/merchants/assemble` — admin/agent ShopAssembler: создаёт проверенный каталогом proposal для текущей сцены и коммитит его через `CreateMerchant`;
- `GET /api/campaigns/:id/turns/:turnId/explanation` — объяснение применённых правил, бросков и событий; campaign ACL уже действует, но event-level visibility результата пока не реализована.

Команда `/why` в поле действия запрашивает такое же объяснение и не расходует ход.

Граница доверия, формулы цены, provenance и известные ограничения торговли описаны в [контракте экономики](docs/economy-contract.md).

### Пример одного хода

Боевой UI обычного игрока отправляет только идентификаторы героя/цели или координаты назначения. Участники инициативы, модификатор атаки, AC, формула и тип урона, дальность и допустимость пути вычисляются сервером; присланные клиентом overrides этих полей не считаются доверенными.

Расширенный диагностический пример ниже с прямым `ApplyDamage` доступен администратору. Идентификаторы и часть полей сокращены:

```http
POST /api/campaigns/RUNE-742/commands
Content-Type: application/json
X-Idempotency-Key: turn-damage-42

{
  "message": "Герой наносит гоблину 3 рубящего урона",
  "command": {
    "command_type": "ApplyDamage",
    "actor_id": "hero",
    "target_id": "goblin",
    "amount": 3,
    "damage_type": "slashing"
  }
}
```

Сокращённый совместимый ответ:

```json
{
  "narration": "Гоблин получает 3 урона.",
  "engine_mode": "enforce",
  "turn_id": "…",
  "state_version": 2,
  "mechanics": [{
    "event_type": "DamageApplied",
    "target_ids": ["goblin"],
    "payload": { "raw_amount": 3, "applied_amount": 3, "hp_before": 8, "hp_after": 5 },
    "source_rule_ids": ["srd_5_2_1:combat:damage"]
  }],
  "explanation_url": "/api/campaigns/RUNE-742/turns/…/explanation"
}
```

`/why` или `explanation_url` возвращает ту же provenance-цепочку без повторного хода:

```json
{
  "engine_mode": "enforce",
  "rules_used": ["srd_5_2_1:combat:damage"],
  "commands": [{ "command_type": "ApplyDamage", "actor_id": "hero", "target_id": "goblin" }],
  "rolls": [],
  "events": [{ "event_type": "DamageApplied", "source_rule_ids": ["srd_5_2_1:combat:damage"] }],
  "ruling": null,
  "state_version_before": 1,
  "state_version_after": 2
}
```

## Данные и архитектура

- `storage/auth.json` — аккаунты и сессии;
- `storage/rooms/*.json` — совместимая legacy-проекция и room CAS version;
- `storage/engine/` — immutable event batches, metadata и snapshots;
- `storage/turn-traces/` — редактированные traces и shadow comparison;
- `storage/generated/` — runtime-generated изображения;
- `data/rule_packs/srd_5_2_1/` — Rule Pack;
- `prompts/*/v1.txt` — версионированные prompts ролей.

Файловое хранилище рассчитано на один процесс и небольшую кампанию. Event commit и legacy-room projection пока не образуют одну filesystem-транзакцию; при сбое между ними требуется reconciliation. Для нескольких серверов нужен транзакционный repository, например PostgreSQL.

Подробности: [аудит MVP](docs/mvp-audit.md), [текущая архитектура](docs/current-architecture.md), [целевая архитектура](docs/target-architecture.md), [покрытие правил](docs/rules-coverage.md), [модель безопасности](docs/security-model.md) и [известные ограничения](docs/known-limitations.md).

## Docker и Windows-лаунчеры

```bash
docker compose up -d --build
docker compose --profile public up -d --build --remove-orphans
docker compose logs -f skazanie
docker compose down
```

Приложение доступно на `http://localhost:8787`. Для обычного запуска достаточно дважды нажать `START_DND.cmd`: он сам запускает Docker Desktop, ждёт готовность движка, собирает сервер, поднимает исходящий SSH-туннель Pinggy, проверяет здоровье приложения, сохраняет ссылку в `PUBLIC_LINK.txt`, копирует её в буфер обмена и открывает игру. `STATUS_DND.cmd` показывает состояние, а `STOP_DND.cmd` останавливает игру. Бесплатный адрес Pinggy периодически меняется; не публикуйте setup-ссылку.
