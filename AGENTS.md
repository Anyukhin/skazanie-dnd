# Работа в репозитории «Сказание»

Операционные правила для агентов и разработчиков. Продуктовая цель, принципы
игры и требования к ИИ-ведущему — в `docs/product-principles.md`. Этот файл
описывает только то, **как** менять код.

## 1. Стек и жёсткие технические факты

Нарушение любого пункта ломает сборку или тесты.

- **`server/` — чистый ESM JavaScript (`.mjs`). TypeScript на сервере не
  используется.** Не создавать `server/*.ts`.
- **Проверка типов на сервере — по одному файлу, через JSDoc.**
  `pnpm typecheck:server` (`tsconfig.server.json`) входит в `pnpm verify`.
  Там стоит `checkJs: false`, поэтому проверяется **только файл с `// @ts-check`
  в первой строке**; импортируемые модули в программу попадают, но их ошибки не
  считаются. Так файл добавляется в проверку по одному и гейт никогда не красный.
  Типы описываются JSDoc-ом (`@typedef`, `@param`, `@returns`) и JSDoc-приведением
  `/** @type {T} */ (expr)` — рантайм при этом не меняется. Если для зелёного
  нужна правка поведения — остановиться и вынести её отдельной задачей.
  Проверяются: `contracts.mjs`, `dynamic-map.mjs`, `viewer-projection.mjs`.
  Форма тактической клетки (`SceneCell`) объявлена в `server/dynamic-map.mjs`.
- **`src/` — TypeScript + React + Vite.** Проверяется через `tsc --noEmit -p tsconfig.app.json`.
- **Тесты — встроенный `node:test`, файлы `test/*.test.mjs`.** Ни Jest, ни
  Vitest, ни Playwright в проекте нет; браузерный сценарий проверяется вручную.
- Node `>=20.19.0`, пакетный менеджер **pnpm**.
- Хранилище — файлы в `storage/` (по умолчанию `./storage`, переопределяется
  `DND_STORAGE_DIR`). Базы данных нет.
- Зависимости в `package.json` закреплены диапазонами `^X.Y.Z`, совпадающими с
  установленными версиями в `pnpm-lock.yaml`. Менять версию — только осознанно,
  вместе с обновлением лока. **Не добавлять новые зависимости без явного запроса
  пользователя**; предпочитать стандартную библиотеку Node.

## 2. Команды

```bash
pnpm dev              # клиент (vite :4173) + сервер (:8787) одной командой
pnpm dev:agent        # только сервер, server/index.mjs
pnpm dev:client       # только vite
pnpm start            # прод-запуск сервера

pnpm test                              # весь набор, node --test, concurrency 4
node --test test/rules-engine.test.mjs # один файл — так проверять точечные правки
pnpm build                             # tsc --noEmit + vite build
pnpm typecheck:server                  # tsc по tsconfig.server.json (только файлы с // @ts-check)
pnpm verify                            # ОБЯЗАТЕЛЬНЫЙ финальный gate: test + typecheck:server + build

pnpm rules:verify     # rule-pack + rule-retriever
pnpm content:verify   # целостность контента и лицензий
pnpm spells:verify    # сверка серверных override заклинаний с каталогом dnd.su:
                      # круг и ячейка не расходятся, вид исполним движком, у площадного
                      # есть радиус, формулы разбираются, ключи не дублируются.
                      # Обязательно после правки data/dndsu-spell-mechanics-overrides.json
pnpm cutover:audit    # расхождения room/snapshot/replay (не меняет данные)
pnpm props:atlas      # пересборка растрового атласа предметов из листов штампов:
                      # pnpm props:atlas --sheets assets-src/prop-stamps, затем pnpm props:rights.
                      # Листы лежат вне репозитория, поэтому в pnpm verify сборка не входит;
                      # собранный атлас сверяется тестом test/prop-atlas.test.mjs
pnpm props:rights     # хеши атласа в data/asset-rights.json (иначе content:verify падает на дрейфе)
pnpm terrain:tiles    # пересборка фактур пола, поверхностей и стен из assets-src/floor-wall-stamps:
                      # сшивает края, уменьшает, пишет палитровым PNG. Затем pnpm terrain:rights
pnpm migrate:dry-run  # прогон миграций без записи
pnpm backup           # СЛОМАН: запускает CLI без аргументов, печатает usage и выходит с 1.
                      # Рабочий вызов: node tools/storage-backup.mjs create ./storage <файл>,
                      # плюс DND_BACKUP_KEY от 32 байт — этой переменной в проекте нет.
                      # Подробности и обходной путь — docs/pre-m0-baseline.md.
```

Порт и хост задаются `AGENT_PORT` / `AGENT_HOST` (по умолчанию `8787` / `0.0.0.0`).

## 3. Секреты и данные

- **`.env` разрешено читать и править** для диагностики и настройки (разрешение
  владельца от 2026-07-25). Он остаётся в `.gitignore` и никогда не коммитится.
  Новые переменные добавлять и в `.env.example` — с комментарием и без значения.
- **Значения секретов не выводить.** Ключ LLM (`ROUTERAI_API_KEY`) и токены не должны
  попадать в логи, тесты, сообщения коммитов и текст ответов. Читать файл, проверять
  наличие и формат переменной, использовать её — можно; печатать саму строку ключа —
  нет: вывод сохраняется в транскриптах и историях, откуда его уже не отозвать.
  Если ключ нужно показать целиком — это делает владелец, а не агент.
- **`storage/` — рабочие данные пользователя.** Тесты обязаны использовать
  временный каталог; не редактировать `storage/`, `data/` и сгенерированный
  контент без явной задачи.
- Не удалять и не переписывать чужие изменения в dirty worktree.

## 4. Карта кода

Прежде чем добавлять модуль, найти существующий владелец задачи. **Второго
авторитетного пути быть не должно.** Создание кампании, загрузка, действия
игроков, ходы NPC и автономный Director используют один Rules Engine.

**Каталоги:** `server/` — авторитетная механика, оркестрация, persistence;
`src/` — интерфейс; `prompts/` — версионированные контракты агентов; `test/` —
исполняемые проверки; `docs/` — архитектура, покрытие и ограничения;
`tools/` — аудиты и обслуживание; `server/migrations/` — миграции данных.

**Ядро (единственные источники истины):**

| Файл | Ответственность |
| --- | --- |
| `server/rules-engine.mjs` | вся механика, допустимость, числа. ~7000 строк — точка входа для любого правила |
| `server/event-store.mjs` | события, commit, replay |
| `server/dice-service.mjs` | вся случайность; в тестах внедряется детерминированно |
| `server/roll-registry.mjs` | `roll_id`/`check_id`, срок действия, защита от повторного применения |
| `server/game-orchestrator.mjs` | оркестрация цикла `/api/narrate` |
| `server/index.mjs` | HTTP-сервер и маршруты, ~2700 строк |
| `server/store.mjs` | persistence поверх `storage/` |
| `server/security.mjs` | членство, владелец героя, полномочия |
| `server/viewer-projection.mjs` | что игрок имеет право видеть |

**Агентные роли.** Доступ к модели централизован: `server/llm-client.mjs`
импортирует **только** `server/index.mjs`, остальные модули получают клиент
внедрением (`this.llmClient.completeJson(...)`). Не импортировать `llm-client`
напрямую в новых модулях — это ломает тесты без ключа и детерминизм.

Промпт загружается модулем через `readFileSync` — таблица отражает **фактические**
привязки в коде:

| Файл | Промпт | Роль |
| --- | --- | --- |
| `server/director-agent.mjs` | `prompts/director/v1.txt` | темп, развилки, переходы |
| `server/npc-controller.mjs` | `prompts/npc_controller/v1.txt` | тактика NPC |
| `server/npc-social-controller.mjs` | `prompts/npc_controller/social_v1.txt` | социальные сцены |
| `server/narrator.mjs` | `prompts/narrator/v6.txt` | текст после commit |
| `server/scene-architect.mjs` | `prompts/map_architect/v1.txt` | новые области |
| `server/campaign-bootstrap.mjs` | `prompts/campaign_creator/v1.txt` | исходная ситуация кампании |
| `server/action-adjudicator.mjs` | `prompts/action_adjudicator/v1.txt` | прочтение свободного действия |

Больше промпты не загружает никто; ролей семь, и столько же файлов в `prompts/`.
Сторож соответствия — `test/security.test.mjs`. **Детерминированные модули без LLM:**
`adjudicator.mjs`, `intent-parser.mjs`, `world-memory.mjs`,
`projection-integrity.mjs`, `npc-turn-scheduler.mjs`, `campaign-loop-policy.mjs`.
Не описывать их как «агентов».

`server/agent-router.mjs` объявляет роли (`AGENT_ROLES`). `prompt_id` там стоит
только у ролей, которые действительно исполняет модель, и **не читается ни одним
модулем** — это метаданные, а не привязка; сторож — `test/agent-router.test.mjs`.
Роли `worldkeeper` и `game_master` объявлены без `prompt_id`: первую исполняет
детерминированный `answerKnownLore` в том же файле, вторую — Rules Engine.

**Автономный цикл:** `autonomous-campaign.mjs` (типы намерений Директора,
`DIRECTOR_INTENT_TYPES`) → `autonomous-orchestrator.mjs` (исполнение) →
`campaign-loop-policy.mjs` (детерминированный fallback без LLM).

**Домен NPC (не путать):** `npc-social.mjs` — модель профилей, обещаний и
отношений; `npc-social-check.mjs` — навыковые проверки; `npc-turn-scheduler.mjs`
— детерминированная боевая политика NPC (не LLM); `creative-director.mjs` —
мораль и перелом боя (бегство, сдача).

## 5. Инварианты и их сторожа

Каждый инвариант обязан оставаться проверяемым. При изменении механики
запускать соответствующий тест **до** `pnpm verify`.

| Инвариант | Сторож |
| --- | --- |
| Replay потока событий даёт то же состояние | `test/event-store.test.mjs`, `pnpm cutover:audit` |
| Повтор с тем же `idempotency_key` возвращает прежний commit | `test/api-integration.test.mjs`, `test/game-flow-integration.test.mjs` |
| Все броски серверные, один бросок не применяется дважды | `test/dice-service.test.mjs`, `test/roll-registry.test.mjs` |
| Клиентские поля недоверенные (путь, дальность, цель) | `test/tactical-command-guard.test.mjs` |
| Права, членство и владелец героя проверяются сервером | `test/security.test.mjs` |
| Игрок видит только разрешённое | `test/viewer-projection.test.mjs`, `test/viewer-projection-api.test.mjs` |
| Рассказчик не создаёт событий и не объявляет смерть | `test/narrator.test.mjs` |
| Параллельные команды не перезаписывают друг друга молча | `test/narrate-room-version-race.test.mjs`, `test/snapshot-projector-version.test.mjs` |

Если новый инвариант нельзя привязать к тесту — он ещё не инвариант, а намерение.

## 6. Порядок реализации механики

1. Серверная **команда** → **правило** в Rules Engine → **событие** → **reducer**.
2. Только затем проекция, промпт и UI.
3. Prompt или React-компонент **не компенсируют** отсутствующее доменное правило.
4. Тесты на: успех, отказ, права, идемпотентность, replay. Случайность —
   через внедрённый детерминированный Dice Service.
5. Схемы событий и контракты промптов **версионировать**. Сохранённые кампании и
   старый replay не ломать без явной миграции в `server/migrations/`.

### Словарь статусов механики

Обязателен для карточек заклинаний и действий (см. `docs/known-limitations.md`):

- `verified` — есть серверный handler, события, тесты replay/idempotency;
- `partial` — исполняется безопасная часть, ограничение описано в UI;
- `heuristic` / `ruling-only` — **блокируется** и клиентом, и Rules Engine до
  расхода ресурсов или экономики хода.

Приблизительный ответ LLM вместо правила не является реализацией. Если правило
не поддержано — запросить уточнение, применить явно отмеченный ruling или честно
сообщить об ограничении.

### Когда разрешено звать LLM

Обычные перемещения, атаки, магия, торговля, инициатива и стандартные ходы NPC
исполняются **только сервером, без вызова модели**. Модель подключается там, где
нужна новая творческая информация: исходная ситуация кампании, проектирование
новой области, перелом боя и мораль тяжело раненого врага, действительно
нестандартное свободное действие. Расход учитывается в `server/usage-ledger.mjs`.
Не добавлять вызов LLM в горячий путь хода.

## 7. Язык

- Интерфейс, повествование, документация, комментарии — **русский**.
- Идентификаторы, имена файлов, команды, события, поля API, `rule_id` — **английский**.
- Промпты — русский текст с английскими именами инструментов и полей.

## 8. Критерий готовности

Применять по типу изменения, а не целиком ко всему подряд.

**Механика, команда, событие, правило — все семь пунктов:**

1. действие доступно реальному игроку через основной сайт;
2. механика проверяется и рассчитывается сервером;
3. результат сохранён событиями, идемпотентен, совпадает после replay/restart;
4. права, visibility и недоверенные клиентские поля проверены;
5. Рассказчик описывает только подтверждённый результат;
6. есть тесты штатного пути и существенных отказов;
7. документация отражает реальное покрытие и оставшиеся ограничения.

**Изменение UI:** пункты 1, 4, 5 + `pnpm build` + проверка реального HTTP-пути
+ ручная проверка основного браузерного сценария с двумя игроками
(автоматизации браузера в проекте нет).

**Документация, тексты, стили:** достаточно `pnpm verify` и точности утверждений.

При любом изменении фактических возможностей обновлять `README.md` и
`docs/rules-coverage.md` либо `docs/known-limitations.md`. **Не заявлять
нереализованную полноту** — это нарушение, равное сломанному тесту.

## 9. Приоритет при конфликте требований

`безопасность и целостность данных → серверный авторитет → закреплённый ruleset →
свобода и непрерывность кампании → художественное и визуальное качество`.

**Остановиться и спросить пользователя**, если задача требует: миграции или
удаления данных в `storage/`, изменения схемы событий без обратной совместимости,
новой зависимости, ослабления любого инварианта из раздела 5 или отступления от
`docs/product-principles.md`.


## 10. Параллельная работа нескольких агентов

Codex и Claude запускаются одновременно на разные части проекта. Правила ниже
написаны не из осторожности: 2026-07-26 две сессии работали в одном каталоге,
вторая переключила ветку под первой, и `git add -A` унёс 176 чужих файлов в
чужой коммит.

### Перед стартом — четыре проверки

```bash
pwd                          # тот ли каталог, что назван в задании
git branch --show-current    # та ли ветка
git status --short           # чужие правки в дереве — это стоп, а не фон
ls node_modules/typescript >/dev/null && echo "зависимости свои"
```

Не совпало хоть одно — **остановиться и спросить пользователя**. Не переключать
ветку, не прибирать чужое, не «поправлять на ходу»: скорее всего рядом работает
другой агент, и каталог сейчас не ваш.

### Одно дерево — один агент

`PycharmProjects/Dnd` — основной каталог, он за пользователем. Агент работает в
отдельном worktree, имя которого названо в задании. Два агента в одном каталоге
не работают никогда: у worktree общая база объектов, но своя ветка, свой индекс
и свой рабочий файл — именно это и разводит сессии.

```bash
git worktree add ../Dnd-<задача> -b <исполнитель>/<задача>
cd ../Dnd-<задача>
pnpm install                 # свои зависимости, см. ниже
cp ../Dnd/.env .env          # .env под .gitignore и в дерево не переезжает
```

Ветка принадлежит одному агенту, и в имени видно исполнителя (`codex/…`,
`claude/…`, `agent/…`) — иначе по `git branch` не понять, чью работу трогаешь.

### `node_modules` в worktree — свои, не связь

**Не вешать junction или симлинк на `node_modules` основного дерева.**
`git worktree remove --force` проходит сквозь связь и удаляет настоящие
зависимости — разом у всех деревьев. Каталоги `Dnd-B`, `Dnd-D` и `Dnd-UI`
заведены именно так и остаются миной, пока связь не заменена на свой
`pnpm install`.

Свой каталог зависимостей стоит дёшево: store pnpm общий
(`AppData\Local\pnpm\store`), файлы кладутся жёсткими ссылками, а не копиями.

Снимать связь только `rmdir` — `rm -rf` идёт внутрь и удаляет цель:

```bash
cmd //c rmdir "C:\Users\anton\PycharmProjects\Dnd-B\node_modules"
```

### Git: что можно и чего нельзя

- **`git add` — перечислением файлов. Никогда `git add -A` и `git commit -a`.**
  В общей базе это забирает чужое.
- **Перед коммитом сверить `git branch --show-current`** с веткой, которую
  создавал. Ветка меняется под руками так же, как файлы.
- Не делать `checkout`, `stash`, `reset --hard` и `worktree remove` в чужом
  каталоге. Чужую ветку читать без переключения: `git show`, `git diff`,
  `git log`.
- В коммит не должно попасть ни одного файла, которого нет в задании. Перед
  коммитом смотреть `git diff --stat --ignore-cr-at-eol` — в репозитории
  смешанные переводы строк, без флага диффы нечитаемы.

### Тесты и замеры — только на застывшем дереве

**Прогон на дереве, которое пишет другая сессия, недействителен.** Растущий
между вызовами `git status` — признак живого агента, а не своей невнимательности.
Ни баг по такому замеру, ни вывод «зелено» из него не следуют.

Свой worktree от этого защищён по построению — это ещё одна причина не работать
в общем каталоге.

### Приложение: порты разводить, `storage/` разводится сам

Тесты портов не занимают, поэтому правки и `pnpm verify` параллелятся как есть.
Два запущенных приложения — нет: сервер занимает `8787`, клиент `4173`.

```bash
AGENT_PORT=8788 pnpm dev:agent
pnpm dev:client -- --port 4174
```

Оговорка: `vite.config.ts` проксирует `/api` и `/generated` на
`127.0.0.1:8787` жёстко, поэтому второй клиент всё равно постучится в первый
сервер. Пока прокси не читает порт из окружения, приложение параллельно не
поднять — правка мелкая, но её нет.

`storage/` у каждого дерева своё: путь относительный и каталог под `.gitignore`.

### Разграничение работы

Две задачи не должны править один модуль. Владельца задачи искать по карте кода
(раздел 4); если обе упираются в `rules-engine.mjs` или `index.mjs` — это одна
задача, а не две параллельные, и запускать их одновременно нельзя.

Финал у каждого агента свой: `pnpm verify` **в своём дереве**, затем ПР из своей
ветки. Чужие ветки не сливать и не перебазировать.

## 11. Два репозитория: приватный и публичный

С 2026-07-26 у проекта два адреса, и путать их нельзя.

| Репозиторий | Адрес | Что в нём |
| --- | --- | --- |
| приватный | `Anyukhin/skazanie-dnd` | вся разработка и полная история |
| публичный | `Anyukhin/skazanie` | только текущее состояние, история начата с чистого листа |

**Разработка идёт в приватном, как раньше.** Ветки задач ответвляются от `main`,
возвращаются через ПР.

**Почему история публичного начата заново.** В прежней истории лежат ассеты,
права на которые не подтверждены. Удаление файлов из рабочего дерева не убирает
их из коммитов, а публикация открывает историю целиком, а не только текущее
состояние. Поэтому публичный репозиторий начат одним коммитом, а приватный
оставлен нетронутым.

### Как обновить публичный

Переносится **состояние**, а не коммиты: истории у репозиториев разные и
сливаться не должны.

```bash
# 1. Экспорт только отслеживаемых файлов — игнорируемое не попадёт по построению
cd <приватный>
git archive HEAD | tar -x -C <публичный>

# 2. Ветка и коммит в публичном
cd <публичный>
git checkout -b release/<дата>
git add -A && git commit -m "<что изменилось>"

# 3. Только через ПР
git push -u origin release/<дата>
gh pr create --base main --fill
```

**Прямой push в `main` публичного не пройдёт.** Там включена защита: форс-пуш и
удаление ветки запрещены, слияние только через ПР с зелёной проверкой `verify`.
Это не совет, а настройка репозитория.

### Перед каждым переносом

- `pnpm verify` зелёный — иначе ПР не сольётся;
- в переносимом состоянии нет ассетов с неподтверждёнными правами; открытые
  вопросы по ним — в `docs/assets-to-regenerate.md`;
- секретов в отслеживаемых файлах нет. `.env`, `storage/` и `PUBLIC_LINK.txt`
  закрыты `.gitignore` и в экспорт не попадают, но проверять стоит: `git archive`
  берёт всё, что отслеживается, а не то, что вы помните.
